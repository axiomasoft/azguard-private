# Библиотека Code Guidance-паттернов для типовых классов item'ов

Три проверенных шаблона формулировок Code Guidance — plan-design при авторинге
item'ов этих классов ссылается сюда и подставляет конкретику, а не изобретает
формулировку заново (P0.3 рек#10). Источник — семантически одинаковые формулировки,
независимо изобретённые планами AGENTOOLS (P2.8/P3.8), FLEX-IMPL (P2.2),
THEMEON (P0.1). `<…>` — слоты подстановки.

## 1. Анти-подгонка — conformance/contract-items

Для items, где код проверяется против эталона: contract-тесты, golden-векторы,
совместимость со спекой/SDK.

```text
Никакого спец-кода «под вектор/тест»: реализация обязана проходить <эталон:
contract-тесты / golden-векторы / спеку> общим путём. Расхождение реализации
с эталоном = сигнал, а не помеха — разобрать до корня (ошибка в коде ИЛИ в
эталоне) и зафиксировать вывод в Completion Notes; молча подогнать <код / тест /
вектор> до зелёного ЗАПРЕЩЕНО.
```

## 2. Анти-самообман — gate-items

Для items-гейтов: предусловие обязано быть закрыто, прежде чем работа считается
сданной (миграции, фиче-флаги, внешние зависимости, чужие фазы).

```text
ЗАПРЕЩЕНО помечать item 🟢 при незакрытом предусловии <гейт: что именно должно
быть закрыто и как проверяется>. Обходить гейт (заглушкой, TODO, «проверю потом»,
ослаблением Validation) запрещено: гейт не пройден → статус остаётся 🟡/🔴 +
Pending Work с точной причиной. Прохождение гейта подтверждается <артефакт:
команда/лог/грепаемая строка>, не словами.
```

## 3. If-then эскалация к D#

Для items, стоящих на конкретном решении D-лога: обнаруженное условие X меняет
основание решения — исполнитель не продолжает самовольно.

```text
Если <условие X: факт, ломающий предпосылку> — НЕ продолжать самовольно:
остановиться и эскалировать по протоколу (SKILL раздел 10), это меняет решение
<D#>. Самовольный обход/замена решения = дефект исполнения; фиксация — ESCALATION-
блок в item + Escalation Needed: yes.
```
