# Согласованность чтений под записью: разбор и план для 1.0

Дата: 2026-10-09. Ветка: `review/v1-hardening` (HEAD `5d770428`). Документ — анализ, код не менялся.
Предмет: 20% / 44% отказов `consistency_error` в профиле `grant-revoke-load` при 1 / 2 писателях
(`bench/README.md`). Внешняя рекомендация (Perplexity, далее «P») проверена по коду. Ссылки вида
`файл:строка` — относительно `packages/core/src`, если не указано иное.

## 1. Как устроено сейчас (факты из кода)

### 1.1. Забор чтения (fence)

- **Версия общая на панель.** Токен состояния — `StateToken(storageId, panel, incarnation, version, generation,
  fingerprint)` (`Kernel/Decision/StateToken.php:14-58`). Его строит `DatabaseSource::token()` из строки
  `azg_panel_state` (`Sources/Database/DatabaseSource.php:992-997`). Таблица — одна строка на панель:
  `panel, version, incarnation, updated_at` (`Storage/Schema/StorageSchema.php:83-89`).
- **Каждая запись поднимает версию.** Корневая мутация в конце инкрементирует `version` всех затронутых панелей
  (`Storage/Storage.php:312-317`), после commit шлёт `StorageTouched` (`:320`), и request-мемо панели
  сбрасывается (`AzGuardServiceProvider.php:111-115`).
- **Записи сериализуются блокировкой строки панели.** `lockPanel()` берёт `SELECT … FOR UPDATE` по
  `panel_state`; на SQLite блокировки нет, там работает блокировка всей базы (`Storage.php:421-433`). Мутация
  повторяет попытку при deadlock и serialization failure (`Storage.php:244-276`).
- **Движок держит одну попытку чтения на операцию** (`Authorization/ReadAttempt.php`):
  - `begin()` открывает закреплённую сессию и читает токен (`:382-404`). При `StateRefresh::Request` токен
    берётся из request-мемо (`:401`), а перед материализацией перечитывается (`beforeMaterializing`, `:406-423`).
  - Чтения каталога, вкладов и выборок идут на той же сессии (`:82-138`, `:140-161`, `:164-253`, `:300-363`).
  - `confirm()` перечитывает токен (`:255-297`). Если он изменился — `ReadAttemptChanged`; если совпал —
    публикация в кэш.
- **`confirm()` вызывается в конце конвейера**, в `AccessPipeline::complete()` (`Authorization/Pipeline/AccessPipeline.php:86-104`).
  До него успевают выполниться membership-проверка (запрос к таблице хоста), политика (код хоста) и
  ограничения (`Pipeline/Stages/AuthorityStage.php:70-100`, `AccessPipeline.php:43-47`). Окно забора покрывает
  весь пользовательский код проверки.
- **Повтор — всей операции целиком, включая Prepare, хуки и политики, 3 раза**, затем
  `DecisionReason::ConsistencyError` (`Authorization/Authorizer.php:381-399`, `AccessPipeline.php:114-120`).
  Так же устроены `isSuperAdmin`, `roleNames`, `permissionSet` (`Authorizer.php:87-101`, `:205-223`,
  `:266-283`), батч (`Authorization/BatchEvaluation.php:48-80`, `:231-250`) и `visibleTo`
  (`Authorization/Visibility.php:69-87`, исключение `VisibilityNotSupportedException('consistency_error')`).
- **Собственный цикл `DatabaseSource`.** Вне движка (`fenced()`, `inspecting()`, `permissions()`) — тот же цикл
  «токен до / чтение / токен после», 3 попытки (`DatabaseSource.php:975-990`, `:791-810`, `:454-477`). Для
  внешних `FencesReads` — `AuthorityStage::readSource()` (`:320-358`).

### 1.2. Закреплённое соединение, реплики, транзакции

- `StorageReadSession` закрепляет один PDO на весь забор (`Storage/StorageReadSession.php:50-77`):
  - `Reads::Primary` — write PDO, `Reads::Default` — read PDO;
  - на клоне соединения стоит реконнектор, который бросает исключение: «a pinned authority read cannot
    reconnect during its fence» (`:73-77`);
  - реплики внутри проверки не переключаются — это уже так.
- **Внешняя транзакция приложения запрещена.** Проверка внутри неё бросает
  `invalid_configuration.authority_transaction` → `source_error` (`StorageReadSession.php:140-167`,
  `docs/concepts/decisions.md`, раздел «Checks inside database transactions»). Есть два признанных исключения:
  - `AuthorityTransaction` — корень, который открыл сам пакет (`mutate` / `withinAuthorityTransaction`). Панель
    заблокирована, чтения идут по write-PDO и видят собственные незакоммиченные записи, кэш не читается и не
    публикуется (`ReadAttempt.php:109`, `:185`, `:239`, `:285`; `Storage.php:85-111`, `:292-294`;
    `Storage/AuthorityTransaction.php`).
  - `AuthorityReadBaseline` — транзакция `RefreshDatabase` в тестах (`Testing/RefreshDatabaseBaseline.php`).
- **Протокол «блокировка сначала».** `withinAuthorityTransaction` берёт блокировку панели до работы хоста.
  Независимый revoke ждёт на ней, пока защищённая работа хоста не закоммитится
  (`tests/Engines/HostSnapshotRaceTest.php:47`). Это публичная гарантия: она держится на блокировке строки
  панели.
- **SQLite.** Laravel открывает транзакции `BEGIN DEFERRED`, если в конфиге нет `transaction_mode`
  (`vendor/laravel/framework/src/Illuminate/Database/SQLiteConnection.php:31`). Сейчас пакет на SQLite
  транзакций для чтения не открывает.

### 1.3. Что кэшируется

- **Только сырые вклады** (`Grant` / `RoleContribution`) — не решения и не эффективные права
  (`Authorization/Cache/PermissionSetCache.php:23`).
- **Ключ:** `storage, panel, incarnation, version, generation, fingerprint` + субъект, tenant, набор scope,
  источник, режим чтения, identity соединения (`:52-61`).
- **Два уровня:** request-мемо (scoped, сбрасывается на запрос / Octane-запрос, `AzGuardServiceProvider.php:110`)
  и общий store — только для `Stable` + `FencesReads` (`:64-91`, `:94-115`).
- **Срок.** При записи в кэш `validUntil = min(ttl, самый ранний expires_at)`, при чтении фильтр `activeAt($now)`.
  `$now` — один на операцию (`Authorizer.php:380`).
- **Мемо токена.** При `StateRefresh::Request` токен запоминается на запрос (`:137-156`). Попадание в кэш
  стоит 2 SQL (`storage_state` + `panel_state`), без повторной проверки токена после чтения: материализации не
  было, значит, `confirm()` источник пропускает (`ReadAttempt.php:268-270`).
- **Сейчас любая запись в панели инвалидирует кэш всех субъектов панели:** версия входит в каждый ключ.

### 1.4. Модель данных грантов

- **Таблицы.** `azg_role_grants` и `azg_permission_grants`: `panel, tenant_*, role|permission, subject_type,
  subject_id, context_*, origin, expires_at, actor_*, meta` (`StorageSchema.php:38-61`). `starts_at` нет.
  Каталог динамических прав — `azg_permissions` (на tenant).
- **Чтение для проверки.** `WHERE panel AND subject_type AND subject_id AND (tenant_key, context_key) IN пары`
  (`DatabaseSource.php:1002-1025`). Для `visibleTo` — все контексты субъекта в tenant, с бюджетом 10 000
  (`:1010-1018`, `:1053-1063`).
- **Групповых грантов, грантов «всем» и грантов на роль нет.** Каждая строка принадлежит одному субъекту.
  - Tenant-wide — это грант субъекта с глобальным контекстом.
  - Resource-wide — грант субъекта с контекстом.
  - Глобальные роли — грант субъекта в глобальном tenant.
  - Super-admin — роль в коде (`super_admin`), выдаётся тоже грантом субъекту.
  - Членство в tenant читается из таблицы хоста на каждой проверке, вне забора и без кэша (`MembershipRestriction`).
- **Что меняет решения сразу многих субъектов:**
  - изменение каталога: создание, правка, удаление динамического права; удаление ещё и отзывает гранты;
  - миграция ключа роли (`ChangePipeline` → `migrateRoleKey`);
  - prune истёкших;
  - `touch` и `reset`;
  - деплой кода — `fingerprint` и `generation` уже в ключе.
- **Прямой SQL в обход пакета не обнаруживается** ни сейчас, ни после изменений. Документировано: после ручной
  правки или restore нужен `azguard:state:reset`, который обновляет `incarnation` (`Storage.php:360-375`,
  `docs/advanced/operations.md:34`). При restore возвращается старая пара `incarnation` + `version`. Без reset
  возможен ABA в общем кэше — это требование остаётся и для новой схемы.

### 1.5. visibleTo, батчи, DecisionSet

- **`visibleTo`.** Выборка контекстов материализуется в PHP, и в SQL хоста подставляются литералы. Join таблиц
  хоста с таблицами грантов нет (`ReadAttempt.php:334`). `confirm()` вызывается до возврата builder
  (`Visibility.php:207`). Сам запрос хоста выполняется позже, вне забора, и снимок ему не нужен.
- **`DecisionSet::of`** требует одинаковый токен для одной пары storage/panel у всех решений набора
  (`Kernel/Decision/DecisionSet.php:33-47`, `@api`). Батч по нескольким субъектам повторяет набор, пока группы
  не совпадут по версии (`BatchEvaluation.php:48-80`). При панельной версии под записью это ещё один источник
  `consistency_error`.

### 1.6. Ошибки решения наружу

- `Effect` — `allow | deny | not_applicable`. Ошибки — это `deny` с причинами `source_error`,
  `consistency_error`, `policy_error` и т. д. (`Kernel/Decision/DecisionReason.php:23-32`). Все `@api`.
- **Gate:** `Response::deny(code: reason)`, статус берётся из решения, по умолчанию 403
  (`Laravel/Gate/GateBridge.php:104-111`).
- `allow` при ошибке и откат на устаревший кэш невозможны: уже так.

Вывод: причина — общая на панель версия, умноженная на длинное окно и повтор всей операции. Зависимость от
драйвера слабая: в замкнутом цикле и чтение, и запись замедляются вместе. Поэтому в бенче у всех драйверов
~20% / 44%.

### 3.1. Где P ошибается или не учитывает код

1. **Окно — это весь конвейер, а не только чтение.** P лечит «до/после» транзакцией, но сегодня забор
   закрывается после политик и ограничений. Даже без транзакции перенос `confirm()` сразу за последнее чтение
   источника и чтение токена непосредственно перед первым запросом грантов сокращают окно в ~5 раз
   (2.65 → ~0.5 мс). Это шаг с минимальным риском.
2. **Транзакцию нельзя держать открытой на коде хоста.** Чтения каталога (Prepare) и вкладов (Authority)
   разделены хуками `before`. Snapshot, открытый на общем PDO приложения на это время:
   - сделает запросы хуков и политик read-only — их запись упадёт;
   - покажет им старый снимок.

   Значит, snapshot должен открываться и закрываться внутри одного метода `DatabaseSource`. Для динамических
   каталогов: каталог и вклады читаются вместе, либо каталог сверяется по отдельной эпохе.
3. **Гидратация моделей — это код хоста.** `newFromBuilder()` вызывает событие `retrieved`, а свои модели
   грантов могут иметь касты и слушателей. Строки нужно выбрать в snapshot, закрыть его и только потом
   гидратировать.
4. **Транзакция пакета и тестовый baseline.** Внутри `AuthorityTransaction` (панель заблокирована) и
   `RefreshDatabase` новый `BEGIN` невозможен и не нужен. Остаётся текущий путь со сравнением токенов.
5. **«Убрать горячую строку».** Профиль записи бенча — 2–9 мс на грант. Проблема — отказы чтений, а не
   пропускная способность записи. Отказ от блокировки панели — переписывание валидации записи и публичной
   гарантии; в 1.0 этого не делать.
6. **`DecisionSet` (`@api`).** С токенами по субъекту набор по нескольким субъектам перестанет совпадать по
   токену. Это решение по контракту (раздел 6).
7. **MySQL / MariaDB.** `WITH CONSISTENT SNAPSHOT` даёт снимок только при `REPEATABLE READ`. Если у сессии
   `READ COMMITTED`, перед `START TRANSACTION` нужен `SET TRANSACTION ISOLATION LEVEL REPEATABLE READ`. P это
   отметил верно; добавим проверку в doctor.
8. **SQLite.** Без WAL читающая транзакция держит SHARED-блокировку, и писатели ждут `busy_timeout`. Snapshot
   допустим, но в doctor нужно предупреждение «рекомендуется WAL», а в документации — ограничение. В бенче WAL
   уже включён.

## 5. План для 1.0

Порядок выбран так, чтобы каждый шаг сам по себе уменьшал отказы и проверялся бенчем. Пакет ещё не
опубликован, поэтому изменение схемы сейчас бесплатно, а после 1.0 потребует миграции.

### Шаг 0. Измерения и красные тесты (S, ~0.5 дня)

- **Бенч, новые профили:**
  - `writes-disjoint` — писатели по пулу A, читатели по пулу B; цель — 0% отказов;
  - `hot-subject` — читатели одного субъекта, который пишут;
  - `open-loop` — писатель с фиксированной частотой 10 / 50 / 200 записей/с и доля отказов при каждой;
  - доля попаданий в кэш под записью (`array`, `redis`).

  Доля `consistency_error` идёт в результат как метрика с порогом (информационно).
- **Тесты движка с барьером** (`tests/Engines`, `AuthorityProcess`):
  - запись субъекта B между токенами проверки A → сейчас `ConsistencyError` в continuous-режиме, после
    шагов 2–3 — ответ с первой попытки;
  - запись во время политики → сейчас повтор, после шага 1 — без повтора.

### Шаг 1. Сузить окно забора (S, 1 день, без схемы)

- `DatabaseSource::read()` / `ReadAttempt`: модели, `GrantFields`, builder и ключи кэша готовить до чтения
  открывающего токена.
- Источник подтверждать сразу после его последнего чтения, а не в `AccessPipeline::complete()`. Политики,
  membership и ограничения выходят из окна. Публикация в кэш — там же.
- Повтор — локальный: перечитать только источник, до 3 раз, с коротким jitter. Prepare, хуки и политики не
  перезапускаются.
- **Файлы:** `Authorization/ReadAttempt.php`, `Authorization/Pipeline/AccessPipeline.php`,
  `Authorization/Pipeline/Stages/AuthorityStage.php`, `Sources/Database/DatabaseSource.php`, `Authorizer.php`
  (цикл повтора), `BatchEvaluation.php`.
- **Семантика:** решение отражает состояние на момент чтения. Отзыв, закоммиченный во время политики, ловит
  следующая проверка. Документация уже это обещает («A check that began before the revocation can still finish
  with the old set»).
- **Ожидание:** окно ~0.5 мс вместо 2.65. Отказы должны снизиться в разы, но не до нуля: версия всё ещё общая
  на панель. Оценку по пуассоновской модели зонд не подтвердил (реальные отказы выше), поэтому число даст
  профиль `open-loop`.

### Шаг 2. Snapshot-чтение для DatabaseSource (M, 2–3 дня)

- `StorageReadSession::snapshot(Closure)` на закреплённом PDO, только вне транзакции пакета и baseline:

  | СУБД | Начало | Конец |
  |---|---|---|
  | pgsql | `BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY` | `COMMIT` |
  | mysql / mariadb | `SET TRANSACTION ISOLATION LEVEL REPEATABLE READ` → `START TRANSACTION READ ONLY, WITH CONSISTENT SNAPSHOT` | `COMMIT` |
  | sqlite | `BEGIN DEFERRED` | `COMMIT` |

  Ошибка внутри → `ROLLBACK` в `finally` и проверка, что PDO вне транзакции. Соединение Laravel не трогается:
  без `transactionLevel` и без событий транзакций.
- **Внутри snapshot:** токен, каталог (если динамический) и строки вкладов. Гидратация моделей — после
  `COMMIT`. Сравнения «до/после» для БД-источника больше нет: токен точно описывает прочитанное. Внутри
  `AuthorityTransaction` и baseline остаётся путь шага 1.
- **Prepare + Authority для динамических панелей:** каталог и вклады читаются одним snapshot в момент, когда
  scope уже известны (`PrepareStage::complete` после структурной границы). Если сначала срабатывает хук
  `before`, лишнее чтение — допустимая цена.
- **Файлы:** `Storage/StorageReadSession.php`, `Sources/Database/DatabaseSource.php` (`read`, `readAssignments`,
  `readPermissions`, `readSelection`, `fenced`, `inspecting`), `Authorization/ReadAttempt.php`,
  `Pipeline/Stages/PrepareStage.php`, doctor-проверки (уровень изоляции MySQL, WAL на SQLite).
- **Ожидание:** `consistency_error` от БД-источника — 0 при любом темпе записи. Стоимость — +1–2 оператора
  (`BEGIN` / `COMMIT`) на промах; попадание в кэш snapshot не открывает.

### Шаг 3. Ревизии субъектов и эпоха панели (M, 2–3 дня, схема)

- **Схема:**
  - новая таблица `azg_subject_revisions(panel, subject_type, subject_id, revision bigint, updated_at)`,
    PK `(panel, subject_type, subject_id)`;
  - `azg_panel_state.epoch bigint default 0`;
  - `Storage::schema()['version']` → 2.

  Строки ревизий не удаляются: монотонность в пределах incarnation.
- **Запись:**
  - `StorageMutation` копит затронутых субъектов (`GrantWriter` и `ActionWriter` знают субъекта каждого
    изменения);
  - на корневом commit выполняется upsert `revision + 1` в отсортированном порядке, под той же блокировкой
    панели;
  - `epoch + 1` при touch, reset и изменении динамического каталога;
  - `version` по-прежнему растёт на каждой записи: это доказательство в `ChangeResult`, событиях и
    `DecisionSet`.
- **Чтение:** один запрос `panel_state LEFT JOIN subject_revisions` вместо `panel_state` — число SQL не растёт.
- **Кэш:** в ключе вместо `version` — `incarnation, epoch, subject_revision` (плюс `generation`,
  `fingerprint`). Мемо токена — на субъект.
- **Эффект:** запись субъекта B больше не сбрасывает кэш A. Под записью попадания сохраняются для всех, кроме
  пишущихся субъектов.
- **Файлы:** `Storage/Schema/StorageSchema.php`, `Storage/Storage.php`, `Storage/StorageMutation.php`,
  `Storage/PanelState.php`, `Sources/Database/{DatabaseSource,GrantWriter,ActionWriter,LockedReads}.php`,
  `Authorization/Cache/PermissionSetCache.php`, `Authorization/ReadAttempt.php`, `Kernel/Decision/StateToken.php`
  (аддитивно, если ревизия войдёт в токен — см. решение 3), doctor (таблица есть), `api-manifest.json`,
  миграции и stub установки.
- **Тесты:**
  - запись B не инвалидирует A (`array`, `redis`);
  - отзыв у A инвалидирует A;
  - `touch`, `reset`, создание и удаление динамического права инвалидируют всех;
  - массовый отзыв поднимает каждого;
  - upsert на sqlite / pgsql / mysql / mariadb (`tests/Engines`);
  - ABA после reset.

### Шаг 4. Батчи по нескольким субъектам (S, 1 день)

Вариант зависит от решения 3:

- **(а)** читать все группы батча одним snapshot — контракт `DecisionSet` не меняется;
- **(б)** сравнивать токены набора по `(storage, panel, incarnation, epoch)`, а ревизии — по субъекту.

Файлы: `BatchEvaluation.php`, `BatchInputs.php`, `DecisionSet.php`.

### Шаг 5. Ошибка как отдельный исход (S, 0.5 дня)

- Лог-метрика доли `consistency_error`.
- По решению владельца — статус 503 для `*_error` в Gate и middleware (`GateBridge::toGateResult`,

### Шаг 6. Документация и контракт SPI (S, 0.5 дня)

- `docs/concepts/decisions.md`: snapshot, момент решения, ошибки.
- `docs/advanced/performance.md` и `operations.md`: WAL для SQLite, изоляция MySQL, выделенное соединение,

## 6. Риски

| Риск | Мера |
|---|---|
| Snapshot на общем PDO приложения «протечёт» при исключении | `try/finally ROLLBACK`, assert `! inTransaction()` после; тест с исключением в середине |
| PgBouncer в режиме statement pooling | Многооператорная транзакция несовместима: документировать (transaction pooling совместим) |
| MySQL `READ COMMITTED` по умолчанию у хоста | `SET TRANSACTION` перед каждым snapshot; doctor-проверка |
| SQLite без WAL: читатель задерживает писателя | Окно — микросекунды; doctor-предупреждение, документация |
| Изменение семантики момента решения (шаг 1) | Уже задокументировано; тест на запись во время политики |
| Схема v2 до 1.0 | Пакет не публиковался; stub и миграции обновляются вместе |
| Регресс протокола «блокировка сначала» и reset ∥ grant | Блокировка панели при записи не меняется; существующие engine-тесты остаются зелёными |
| Рост таблицы ревизий | Одна строка на субъекта с грантами в панели; очищается вместе с reset при желании |

## 7. Решения владельца

1. **Момент решения (шаг 1).** Принять «решение на момент чтения» и не повторять операцию из-за записи во
   время политик. Рекомендуем: да.
2. **Snapshot на соединении по умолчанию (шаг 2)** или только на выделенном. Рекомендуем: на любом, когда
   транзакции нет.
3. **`DecisionSet` по нескольким субъектам:** (а) один snapshot на батч или (б) смягчить равенство токенов до
   эпохи панели. Рекомендуем (а), если не окажется сложным; иначе (б) до 1.0.
4. **Схема v2 с ревизиями субъектов до 1.0.** Рекомендуем: да, после 1.0 это миграция.
5. **Статус HTTP для `*_error`:** оставить 403 (сейчас) или 503. Плюс аддитивный `Decision::failed()`.
6. **Блокировка панели при записи:** оставить в 1.0 (рекомендуем) или переходить на блокировки по субъекту
   (отдельный проект после 1.0).
7. **Отложить квитанцию свежести для реплик (P7) на 1.x.** Рекомендуем: да.

зелёные.
