Аудит выполнен по ветке `main` на коммите [`7e7009c`](https://github.com/axiomasoft/azguard-private/commit/7e7009cc7c26e173cfa6bfec42365a311fc2adb0) в трёх независимых проходах: архитектура и модель расширения, adversarial-аудит корректности и безопасности, затем унификация AzGuard с Chatom. # Итерация 1: архитектура

## Сильная основа

В AzGuard правильно разделены несколько понятий:

- `PermissionCatalog` описывает известные разрешения.
- `GrantSource` предоставляет разрешения конкретного пользователя.
- `PermissionSet` представляет вычисленный набор.
- `PermissionMatcher` отвечает за wildcard grammar.
- `PermissionResolverInterface` вычисляет effective permissions.
- `PanelProvider` регистрирует permission enums и policy abilities.
- `PermissionLayer` позволяет companion-пакету добавлять ещё один слой разрешений.

Service provider уже связывает интерфейсы с заменяемыми реализациями, регистрирует scoped permission cache и собирает grant sources через container tags [AzGuardServiceProvider.php](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/core/src/AzGuardServiceProvider.php).

Это хорошая основа для long-lived package: центральный resolver не обязан знать все источники разрешений, а companion package может расширить вычисление без форка core.

## Три вида Role

Сейчас словом `Role` фактически называются три разных понятия:

1. PHP-класс, определяющий разрешения: `BaseRole` / `RoleInterface`.
2. Строка в таблице `roles`: `AzGuard\Models\Role`.
3. Назначение роли субъекту: строка в `model_has_roles` или `model_has_scopes`.

Это создаёт неоднозначность в contracts, документации и именах методов. Например, `RoleInterface` относится не к Eloquent-модели `Role`, а к code-first definition; `Role::getRoleLogic()` динамически создаёт этот definition-class [Role.php](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/core/src/Models/Role.php).

Предлагаемый словарь:

| Текущее | Предлагаемое | Семантика |
|---|---|---|
| `RoleInterface` | `RoleDefinition` | Code-first определение роли |
| `BaseRole` | `AbstractRoleDefinition` | Базовый класс определения |
| `Models\Role` | `RoleRecord` | Persistence representation |
| `model_has_roles` | `role_assignments` | Назначение роли субъекту |
| `ModelHasScope` | `ScopedRoleAssignment` | Назначение роли в scope |
| `RolePermission` | `RolePermissionGrant` | Связь роли и разрешения |

Не обязательно немедленно переименовывать публичные классы. Но glossary должен считать `RoleDefinition`, `RoleRecord` и `RoleAssignment` разными концепциями, даже если compatibility names сохраняются до major release.

## Перегрузка Panel

В AzGuard `Panel` — namespace разрешений и application surface, например `app`, `admin`, `api`. В Chatom `Panel` означает storage/isolation configuration: таблицы, модели, features, ID strategy и pipeline.

Это одна из главных несогласованностей двух пакетов. Один и тот же термин не должен обозначать authorization namespace в одном package и database partition в другом.

Рекомендуемая ecosystem-семантика:

| Термин | Единое значение |
|---|---|
| `Panel` | Пользовательская/application surface: `admin`, `app`, `api` |
| `Actor` | Идентичность, выполняющая действие |
| `Scope` | Ресурс или область, ограничивающая разрешение |
| `Space` | Изолированное пространство общения |
| `Partition` | Физическая конфигурация хранения |
| `Context` | Только request/runtime context; не persistence entity |

При таком соглашении AzGuard сохраняет `Panel`, а Chatom переименовывает собственный `Panel` в `ChatSpace`, `ChatPartition` или `ChatContextDefinition`. Это дешевле и семантически точнее, чем переименование AzGuard.

## Mutable Panel

`PanelProvider` создаёт mutable `Panel`, кэширует его внутри provider и затем использует этот же объект при регистрации policies и catalog builders [PanelProvider.php](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/core/src/Panels/PanelProvider.php).

Как и в Chatom, bootstrap DSL удобен, но runtime лучше выдавать immutable resolved definition:

```php
PanelDefinition::make()
    ->id('admin')
    ->permissionEnums([...])
    ->compile();
```

```php
final readonly class ResolvedAuthorizationPanel
{
    public function __construct(
        public PanelId $id,
        public PermissionCatalogDefinition $catalog,
        public PolicyMap $policies,
        public string $basePath,
        public string $namespace,
    ) {}
}
```

Компиляция должна проверять:

- непустой и валидный panel ID;
- отсутствие дублирующихся permission keys;
- существование enum и policy classes;
- согласованность `GateAbility` с catalog;
- отсутствие конфликтующих policy registrations;
- наличие default panel среди зарегистрированных;
- корректность custom catalog builders.

## Runtime context

`AzGuardManager` зарегистрирован singleton, хотя содержит mutable `currentPanel`. Для Octane и queue workers добавлены reset listeners, что показывает осознание lifecycle-риска [AzGuardServiceProvider.php](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/core/src/AzGuardServiceProvider.php#L81-L149) [reset listeners](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/core/src/AzGuardServiceProvider.php#L205-L230).

Но правильнее разделить:

```text
AzGuardManager                 singleton, immutable registry
CurrentAuthorizationContext    scoped, request/job-local state
```

`currentPanel` не должен жить в registry singleton. Это даст одинаковую модель с предлагаемым устранением mutable request-local state из контейнера Chatom.

Целевой API:

```php
interface AuthorizationContext
{
    public function panelId(): ?PanelId;
    public function runInPanel(PanelId $panel, Closure $callback): mixed;
}
```

`runInPanel()` должен восстанавливать предыдущую панель через `finally`, поддерживать вложенные вызовы и не оставлять состояние после исключения.

# Итерация 2: корректность

# Критические риски

## AZG-001: истечение grant и кэш

`DirectGrantSource` выбирает только активные grants через `active()`, но возвращает обычный `PermissionSet`, не содержащий ближайшее время истечения [DirectGrantSource.php](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/core/src/Registry/Sources/DirectGrantSource.php). Затем `PermissionCache` сохраняет весь effective set на полный configured TTL [PermissionCache.php](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/core/src/Registry/Resolver/PermissionCache.php).

Сценарий:

1. Direct grant истекает через 5 минут.
2. Permission set кэшируется на 1 час.
3. Через 5 минут строка в БД уже неактивна.
4. Resolver продолжает возвращать кэшированный permission ещё 55 минут.
5. Ежедневный prune не исправляет проблему вовремя.

Это потенциальный security defect: temporal permission живёт дольше заявленного срока.

### Исправление

Grant source должен возвращать не только keys:

```php
final readonly class GrantContribution
{
    public function __construct(
        public PermissionSet $permissions,
        public ?CarbonImmutable $validUntil,
    ) {}
}
```

Resolver вычисляет:

```text
effective TTL = min(
    configured cache TTL,
    nearest non-null validUntil - now
)
```

Альтернативы:

- не помещать наборы с временными grants в persistent cache;
- включать временной bucket в cache discriminator;
- хранить expiring grants отдельно от долговременного effective set.

### Обязательный тест

```text
Given grant expires at T+2s
And persistent cache TTL = 1h
When permission is resolved at T
Then permission is allowed
When clock advances to T+3s
Then permission is denied without prune command
```

Тот же тест нужен для `ContextRole`, поскольку context package также поддерживает `expires_at` и участвует в effective permission resolution [ContextRole.php](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/context/src/Models/ContextRole.php).

## AZG-002: destructive Filament sync

Filament relation manager сначала удаляет все permissions роли, затем собирает массив и выполняет bulk `RolePermission::insert()` [RolePermissionsRelationManager.php](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/filament/src/Resources/RoleResource/RelationManagers/RolePermissionsRelationManager.php#L175-L215).

Здесь сразу три проблемы:

- delete и insert не обёрнуты в явную транзакцию;
- ошибка между операциями оставляет роль без permissions;
- bulk `insert()` не запускает Eloquent `saving` event и обходит `RolePermissionValidator`.

Последнее особенно важно: модель заявляет opt-in validation на каждом save, но основной административный bulk path его не вызывает [RolePermission.php](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/core/src/Models/RolePermission.php).

### Исправление

Вынести мутацию из Filament в application service:

```php
interface SynchronizeRolePermissions
{
    public function execute(
        RoleId $role,
        RolePermissionSelection $selection,
    ): RolePermissionSyncResult;
}
```

Внутри:

1. Провалидировать весь desired set до удаления.
2. Открыть транзакцию.
3. Вычислить diff.
4. Удалить только отсутствующие строки.
5. Добавить только новые.
6. Записать audit event.
7. После commit инвалидировать holders.
8. Вернуть добавленные и удалённые keys.

Filament, CLI и будущий HTTP API должны использовать один service.

## AZG-003: config-swappable models не полностью swappable

`Config` объявляет заменяемые модели `role`, `scope`, `direct_grant` и `role_permission` [Config.php](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/core/src/Configuration/Config.php). Однако часть кода использует concrete classes напрямую:

- `HasRoles` содержит обращения к `Role`.
- `HasScopedRoles` создаёт и запрашивает `ModelHasScope`.
- `GrantBuilder` использует `DirectGrant::query()`.
- `HasDirectGrants` определяет relation через `DirectGrant::class`.
- Filament resources жёстко привязаны к `Role::class` и `DirectGrant::class`.
- Filament permission sync вызывает `RolePermission::insert()`.

Это означает, что extension seam работает только в части путей. Некоторые read operations уважают config, а write operations или UI — нет.

### Решение

Нужно выбрать один из вариантов.

**Вариант A — настоящая подмена моделей:**

- Ни одного `Role::query()` за пределами самой модели и default factory.
- Все relations используют `Config::*Model()`.
- Filament разрешает model через static method, а не static property.
- Contracts принимают базовый contract, а не concrete Eloquent class.
- Architecture test запрещает прямое использование default models.

**Вариант B — модели не заменяются:**

- Удалить config keys.
- Явно объявить models частью стабильного persistence contract.
- Расширять поведение через repositories, factories и observers.

Для AzGuard логичнее вариант A, поскольку заменяемые модели уже являются публичным обещанием.

### Architecture tests

```php
arch('configurable models are not referenced directly')
    ->expect([
        'AzGuard\Concerns',
        'AzGuard\Grants',
        'AzGuard\Commands',
        'AzGuard\Filament',
    ])
    ->not->toUse([
        Role::class,
        DirectGrant::class,
        ModelHasScope::class,
        RolePermission::class,
    ]);
```

Default model namespace можно разрешить только `Configuration`, factories и model-specific tests.

## AZG-004: fragmented cache invalidation

Cache invalidation выполняется одновременно несколькими способами:

- `DirectGrant` сбрасывает кэш через model events.
- `GrantBuilder` отправляет `GrantGiven`/`GrantRevoked`.
- Service provider слушает эти события и снова сбрасывает кэш.
- `HasRoles` отправляет `RoleAttached`/`RoleDetached` и дополнительно вызывает `flushPermissions()`.
- Listener на role events снова вызывает `flushPermissions()` [cache listeners](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/core/src/AzGuardServiceProvider.php#L304-L329) [HasRoles.php](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/core/src/Concerns/HasRoles.php) [DirectGrant.php](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/core/src/Models/DirectGrant.php).

Это способно увеличивать epoch дважды за одну логическую операцию. Корректность обычно не нарушается, но растёт число orphaned cache entries и становится трудно доказать, какой путь гарантирует invalidation.

### Целевая модель

У каждой мутации должен быть один authoritative invalidation path:

```text
Application command
  -> transaction
  -> database mutation
  -> records PermissionStateChanged
  -> after commit
  -> listener bumps epoch exactly once
```

Model observers можно оставить как safety net для прямого Eloquent использования, но тогда события application layer должны быть idempotent и объединяться по mutation ID. Ещё лучше — запретить прямые массовые mutations в documented API и направлять всё через services.

## AZG-005: изменение role permissions инвалидирует не всех

После Filament sync код проходит по `$role->users()` и вызывает `flushPermissions()` [RolePermissionsRelationManager.php](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/filament/src/Resources/RoleResource/RelationManagers/RolePermissionsRelationManager.php#L207-L214). Но `Role::users()` строится только для модели, указанной в `auth.providers.users.model` [Role.php](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/core/src/Models/Role.php).

При polymorphic role assignments это может не охватить:

- другой authenticatable model;
- административного и клиентского пользователя разных классов;
- scoped assignments;
- custom subject model.

### Лучшее решение

Не перечислять всех holders роли. Использовать versioning:

```text
role_permission_version:{roleId}
```

Cache key пользователя включает версии всех назначенных ему ролей. При изменении permissions достаточно увеличить version конкретной роли, не выполняя обход пользователей.

Более простой вариант — глобальная `catalog_epoch`, но она инвалидирует всех пользователей при изменении одной роли.

# Высокий приоритет

## AZG-101: mutable currentPanel

Mutable `currentPanel` внутри singleton manager требует специальных reset hooks для Octane и queue workers. Такие hooks уменьшают риск межзапросной утечки, но не решают полностью:

- вложенные переключения панели;
- исключение между set и restore;
- coroutine/fiber concurrency;
- long-running console processes;
- тесты, переиспользующие application;
- вызовы из sync job внутри request.

Нужно вынести текущую панель в scoped `AuthorizationContext`, а manager оставить immutable registry.

### Тесты

- После исключения предыдущая панель восстановлена.
- Nested `runInPanel(A) → runInPanel(B)` возвращает A после B.
- Два независимых scoped contexts не видят панели друг друга.
- Queue job не получает панель предыдущего job.
- Sync job не уничтожает панель текущего HTTP request.
- CLI command без панели работает fail-closed.

## AZG-102: strict panel validation непоследовательна

`PanelResolver::resolveDefault()` проверяет только явно переданную панель. Configured default возвращается без `guardUnregistered()`. `resolve()` и `resolveOrFail()` также не проверяют существование разрешённой панели [PanelResolver.php](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/core/src/Panels/PanelResolver.php).

Кроме того, даже strict mode пропускает неизвестную панель, если registry пока пуст. Это удобно для isolated tests, но в production способно скрыть неудачную регистрацию providers.

### Исправление

Разделить операции:

```php
PanelId::parse($raw);               // синтаксис
PanelRegistry::require($panelId);   // существование
PanelContext::currentOrFail();      // runtime context
```

При boot:

```text
strict_panels=true
default_panel configured
default_panel not registered
=> application boot failure
```

Для тестов можно предоставить explicit `UnregisteredPanelPolicy::Allow`.

## AZG-103: role identity

Таблица `roles` делает `name` глобально уникальным, но `class_name` остаётся nullable и не имеет unique constraint [core migration](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/core/database/migrations/2026_01_01_000000_create_az_guard_tables.php).

При этом scaffolding создаёт роль с default name `Admin` для каждой панели [MakeGuardPanelCommand.php](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/core/src/Commands/MakeGuardPanelCommand.php).

Нужно формально выбрать identity model.

### Вариант 1: роли глобальны

- `class_name` — основной уникальный identity.
- `name` — display/alias и необязательно уникален.
- Одна role definition может давать permissions разных panels.
- Поиск по строковому name считается неоднозначным и deprecated.
- `assignRole(RoleDefinition::class)` — основной API.

### Вариант 2: роли принадлежат панели

- В `roles` добавляется `panel_id`.
- Unique key: `(panel_id, name)`.
- `class_name` уникален либо глобально, либо внутри panel.
- Role permissions могут больше не дублировать `panel_id` либо должны проверять совпадение.

С учётом текущего code-first дизайна предпочтителен первый вариант: canonical identity = PHP class. Это соответствует обещанию refactor safety лучше, чем уникальное display-name.

### Обязательный тест

Создать две панели, обе с `AdminRole`, синхронизировать роли и проверить:

- не перезаписан ли `class_name`;
- не объединены ли случайно две разные роли;
- правильно ли разрешаются permissions;
- что делает `assignRole('admin')`;
- выдаёт ли doctor неоднозначность.

## AZG-104: silent invalid role logic

`Role::getRoleLogic()` возвращает `null`, если `class_name` отсутствует, класс удалён или не реализует `RoleInterface` [Role.php](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/core/src/Models/Role.php).

Fail-closed поведение безопасно, но operationally неотличимо от роли без code permissions. Ошибочная миграция namespace может тихо лишить пользователей доступа.

Нужно:

- регистрировать diagnostic event;
- показывать проблему в `guard:doctor`;
- добавить strict mode, где invalid `class_name` вызывает exception;
- разрешать aliases для переименованных role classes;
- включить stale role classes в deployment checks.

## AZG-105: CheckAccess допускает отсутствие атрибутов

`CheckAccess` извлекает `#[CheckPermission]`, проходит по найденным атрибутам и затем пропускает request. Если middleware подключён, но атрибут забыли добавить, список пуст и запрос разрешается [CheckAccess.php](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/core/src/Http/Middleware/CheckAccess.php).

Это может быть documented behavior, но с security middleware безопаснее fail-closed.

Варианты:

- middleware без `CheckPermission` возвращает configuration exception;
- route scanner проверяет это на boot;
- explicit `#[SkipGuardCheck]` разрешает отсутствие permissions;
- отдельный middleware `DiscoverPermissionAttributes` не обещает enforcement.

Рекомендуемый invariant:

```text
route has azguard.check
AND action has neither CheckPermission nor SkipGuardCheck
=> boot/doctor error
```

## AZG-106: permission grammar не проверяется централизованно

`PermissionKey::normalize()` преобразует enum или строку, но не проверяет:

- пустые сегменты;
- пробелы;
- leading/trailing separator;
- double separator;
- wildcard в середине;
- уже добавленный panel prefix;
- допустимый charset;
- максимальную длину [PermissionKey.php](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/core/src/Permissions/PermissionKey.php).

Дополнительно DB validation является opt-in и lenient по умолчанию. Это не полностью соответствует тезису «не magic strings», потому что Filament и direct grants всё ещё способны сохранять string keys.

### Целевой тип

```php
final readonly class PermissionName
{
    public static function fromEnum(UnitEnum $case): self;
    public static function parse(string $raw): self;

    public function scopeTo(PanelId $panel): ScopedPermission;
}
```

Для backward compatibility строки можно принимать на публичной границе, но сразу преобразовывать в validated value object.

## AZG-107: pure enums и backed enums

`PermissionKey::normalize()` возвращает `value` для `BackedEnum`, но `name` для обычного `UnitEnum`. `CheckAccess` добавляет panel scope только если permission является `BackedEnum` [PermissionKey.php](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/core/src/Permissions/PermissionKey.php) [CheckAccess.php](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/core/src/Http/Middleware/CheckAccess.php).

Нужно либо:

- официально поддерживать только `BackedEnum`;
- либо одинаково scope-ить оба типа;
- либо потребовать от permission enum реализации `PermissionDefinition`.

Текущая общая сигнатура `UnitEnum` обещает больше, чем некоторые runtime paths фактически обрабатывают.

## AZG-108: direct construction role definitions

`Role::getRoleLogic()` создаёт definition через `new $this->class_name`, минуя container [Role.php](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/core/src/Models/Role.php).

Если definitions должны оставаться полностью stateless, это следует зафиксировать contract. Если допускаются dependencies, нужен `RoleDefinitionFactory`:

```php
return app(RoleDefinitionFactory::class)->make($this->class_name);
```

Предпочтительно оставить definitions immutable и stateless, но не полагаться на неявное ограничение.

# Схема данных

## ContextRole назван неверно

`az_guard_context_roles` хранит:

- subject/model;
- context type и ID;
- panel ID;
- permission key;
- expiration.

В записи нет `role_id`; это direct contextual permission grant, а не роль [context migration](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/context/database/migrations/2026_01_01_000010_create_az_guard_context_roles_table.php).

Рекомендуемое переименование:

| Текущее | Предлагаемое |
|---|---|
| `ContextRole` | `ContextPermissionGrant` |
| `az_guard_context_roles` | `az_guard_context_permission_grants` |
| `ContextGrantBuilder` | оставить |
| `ContextPermissionLayer` | оставить |
| `guard:context-role:*` | `guard:context-grant:*` |

Это одно из наиболее полезных переименований: оно устраняет ошибочное представление о модели данных.

## ModelHasScope назван слишком абстрактно

`ModelHasScope` фактически представляет scoped role assignment:

```text
subject + scope entity + role + optional panel
```

Название не показывает, что внутри находится именно роль.

Лучше:

```text
ScopedRoleAssignment
az_guard_scoped_role_assignments
```

Поля:

```text
subject_type
subject_id
scope_type
scope_id
role_id
panel_id
```

`model` и `scope_entity` технически соответствуют Laravel morph naming, но хуже читаются на уровне SQL и домена.

## Subject вместо model

В таблицах одновременно используются morph-префиксы:

- `model`;
- `grantable`;
- `scope_entity`;
- `context`.

Для одной authorization ecosystem лучше:

| Семантика | Префикс |
|---|---|
| Тот, кому выдаётся доступ | `subject_*` |
| Ресурс ограничения | `scope_*` |
| Роль | `role_id` |
| Permission | `permission_key` |
| Application namespace | `panel_id` |

Так schema становится самодокументируемой:

```text
subject_type
subject_id
scope_type
scope_id
panel_id
permission_key
expires_at
```

## Morph types и PHPDoc

Schema поддерживает разные morph ID types через `MorphColumns`, но модели местами документируют IDs как `int`. Например, `DirectGrant::$grantable_id` и `ModelHasScope::$model_id` имеют int-oriented PHPDoc, хотя configuration допускает UUID/ULID [MorphColumns.php](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/core/src/Database/Schema/MorphColumns.php) [DirectGrant.php](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/core/src/Models/DirectGrant.php).

Нужно использовать:

```php
@property int|string $subject_id
```

Ещё лучше — generic PHPDoc или value object на service boundary.

## Context ID strategy

Context package хранит `context_id` как `string(64)` независимо от core morph strategy [context migration](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/context/database/migrations/2026_01_01_000010_create_az_guard_context_roles_table.php).

Это упрощает mixed UUID/int contexts, но создаёт отдельную стратегию ID, не совпадающую с core. Следует либо:

- использовать общий `SubjectIdentifierCodec`;
- иметь config `context_id_type`;
- документировать канонизацию integer IDs в строки;
- запретить значения длиннее 64;
- гарантировать одинаковое представление `42`, `"42"` и UUID casing.

## Null-aware uniqueness

Миграция `model_has_scopes` правильно замечает, что обычный SQL `UNIQUE` не дедуплицирует строки с `NULL`, и создаёт expression index через `COALESCE` [unique constraints migration](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/core/database/migrations/2026_01_01_000005_add_unique_constraints_to_model_has_roles_and_scopes.php).

Но sentinel values способны столкнуться с реальными значениями:

- `NULL panel_id` и пустой `panel_id`;
- `NULL role_id` и `0`;
- `NULL scope_entity_id` и `0`;
- `NULL UUID` и all-zero UUID;
- `NULL scope_entity_type` и пустая строка.

Следует добавить checks/application validation, запрещающие sentinel values. Иначе две семантически разные записи могут считаться одинаковыми.

## Raw SQL migration

Expression index строится raw SQL с подстановкой configurable table name [migration](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/core/database/migrations/2026_01_01_000005_add_unique_constraints_to_model_has_roles_and_scopes.php#L49-L79).

Риски:

- identifier не quoting-aware;
- schema-qualified names;
- reserved table names;
- различия MySQL/MariaDB;
- требования MySQL к functional indexes;
- PostgreSQL `DROP INDEX` и `search_path`;
- custom prefix с недопустимыми символами.

Table config является trusted input, поэтому это не классическая remote SQL injection. Но config необходимо валидировать как identifier и оборачивать через grammar.

## Dedupe migration

Для `model_has_roles` migration:

1. Загружает все distinct rows в память.
2. Удаляет содержимое таблицы.
3. Вставляет строки обратно чанками [migration](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/core/database/migrations/2026_01_01_000005_add_unique_constraints_to_model_has_roles_and_scopes.php#L115-L143).

На большой production-таблице это риск:

- высокий memory usage;
- длительная блокировка;
- потеря данных при частичном сбое;
- проблемы с auto-commit DDL;
- изменение порядка строк;
- тяжёлый rollback.

Предпочтительнее:

```sql
DELETE FROM model_has_roles a
USING model_has_roles b
WHERE a.row_identifier > b.row_identifier
  AND ...
```

Но текущая pivot table не имеет PK. Практичнее сначала добавить surrogate `id`, затем дедуплицировать row-wise и создать unique index.

## Table configurability

Core поддерживает configurable table names, но context package использует фиксированное `az_guard_context_roles`. Это нарушает единый extension contract.

Нужно либо:

- добавить context configuration с table/model map;
- либо объявить таблицы всех AzGuard packages фиксированными и постепенно убрать core overrides.

Для общей экосистемы лучше shared schema registry:

```php
AzGuardSchema::roles();
AzGuardSchema::roleAssignments();
AzGuardSchema::scopedAssignments();
AzGuardSchema::directPermissionGrants();
AzGuardSchema::contextPermissionGrants();
```

# Middleware и безопасность

## Morph map

Polymorphic типы по умолчанию способны хранить FQCN модели. Переименование `App\Models\User` тогда меняет persistence identity и противоречит общей идее refactor safety.

Рекомендуется:

- требовать Laravel morph map в strict mode;
- добавить doctor check;
- документировать aliases при переименовании;
- использовать стабильные типы `user`, `admin`, `service_account`;
- не принимать arbitrary morph class из пользовательского input.

## Dynamic class columns

`roles.class_name` и `model_has_scopes.scope_class` управляют созданием PHP-классов или применением query logic. Они исключены из обычного mass assignment, что является правильной защитой [Role.php](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/core/src/Models/Role.php) [ModelHasScope.php](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/core/src/Models/ModelHasScope.php).

Дополнительно нужны:

- interface validation;
- namespace allowlist;
- doctor validation;
- audit event при изменении;
- запрет arbitrary class name в generic API;
- migration aliases для переименованных классов.

## Global Gate hook

AzGuard регистрирует `Gate::before()` для всех Laravel abilities [AzGuardServiceProvider.php](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/core/src/AzGuardServiceProvider.php#L192-L203).

Нужно иметь contract tests, подтверждающие:

- неизвестная AzGuard способность возвращает `null`, а не `false`;
- обычные Laravel policies продолжают выполняться;
- super-admin не получает не-AzGuard ability случайно;
- panel-prefixed и unprefixed keys различаются;
- catalog conflict не перехватывает unrelated Gate ability.

## Bulk mutations

`DirectGrant` сам документирует, что query-builder bulk update/delete не запускает model events и поэтому не сбрасывает кэш [DirectGrant.php](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/core/src/Models/DirectGrant.php).

Поскольку Eloquent API публичен, одного комментария недостаточно. Нужны:

- repository/application commands как рекомендованный write API;
- mutation event или database trigger для особенно строгих deployments;
- `guard:cache-reset` после documented bulk operations;
- static rule, запрещающий bulk mutation внутри собственных packages;
- audit test на каждый официальный write path.

## Cache key encoding

Permission cache key собирается конкатенацией user ID, panel ID, epoch и discriminator через точки [PermissionCache.php](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/core/src/Registry/Resolver/PermissionCache.php).

Для UUID и стандартных panel IDs это практически работает, но произвольные string IDs способны создать неоднозначную композицию. Надёжнее:

```php
hash('xxh128', json_encode([
    'user' => (string) $userId,
    'panel' => $panelId,
    'context' => $discriminator,
]));
```

Читаемый prefix можно сохранить перед hash.

## Cache lock failure

При durable invalidation epoch увеличивается под cache lock. Если lock невозможно получить за timeout, exception может возникнуть уже после изменения grant или role [PermissionCache.php](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/core/src/Registry/Resolver/PermissionCache.php).

Это особенно опасно при revoke:

- разрешение удалено в БД;
- invalidation не завершилась;
- клиент получает ошибку;
- старый permission set остаётся доступен до TTL.

Нужно определить explicit policy:

- revoke при невозможности invalidate должен fail-closed;
- grant при невозможности invalidate может оставаться невидимым, но не должен повышать права из stale cache;
- invalidation event желательно записывать durable;
- metrics должны показывать lock timeout;
- retry должен быть идемпотентным.

# Итерация 3: API и экосистема

## Scaffolding

`make:guard-panel` одновременно создаёт panel provider, роль, permission enum, policy и optional abilities DTO, а затем редактирует `config/az-guard.php` регулярным выражением [MakeGuardPanelCommand.php](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/core/src/Commands/MakeGuardPanelCommand.php).

### Обнаруженные проблемы

- Panel ID строится через `Str::lower()`, но не проходит отдельную syntactic validation.
- Существующий каталог панели блокирует повторный вызов команды, поэтому добавление второго domain в уже существующую panel неудобно.
- Policy stub жёстко использует `App\Models\User`.
- Model вычисляется как `App\Models\{Domain}`; `Documents` даст `App\Models\Documents`, хотя Laravel-модель обычно `Document`.
- Конфиг редактируется regex-вставкой.
- Роль по умолчанию называется `Admin`, что создаёт риск global role-name collision между panels.
- Команда объединяет слишком много сценариев: создать panel и добавить domain.

### Предлагаемый CLI

```bash
php artisan azguard:make-panel Admin
php artisan azguard:make-domain Admin Documents --model=App\\Models\\Document
php artisan azguard:make-role Admin Editor
php artisan azguard:make-permission Admin Documents
php artisan azguard:make-policy Admin Documents --model=...
```

Для backward compatibility старые commands остаются aliases.

Config registration лучше выполнять через:

- отдельный registry file;
- package discovery;
- provider auto-discovery по manifest;
- либо структурный PHP parser, но не regex.

## Command namespace

Сейчас используются формы:

```text
make:guard-panel
guard:doctor
guard:sync-roles
guard:cache-reset
```

Для двухпакетной экосистемы стоит выбрать один namespace:

```text
azguard:doctor
azguard:roles:sync
azguard:cache:clear
azguard:make-panel
```

И для Chatom:

```text
chatom:doctor
chatom:schema:verify
chatom:outbox:status
```

Главное — не конкретная пунктуация, а одинаковая грамматика `package:resource:action`.

## Models и resources

Filament resources задают concrete models через static properties:

```php
protected static ?string $model = Role::class;
protected static ?string $model = DirectGrant::class;
```

Это не согласуется с configurable models [RoleResource.php](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/filament/src/Resources/RoleResource.php) [DirectGrantResource.php](https://github.com/axiomasoft/azguard-private/blob/7e7009cc7c26e173cfa6bfec42365a311fc2adb0/packages/filament/src/Resources/DirectGrantResource.php).

Исправление:

```php
public static function getModel(): string
{
    return Config::roleModel();
}
```

Relation managers должны работать через contracts/services, а не принимать только concrete `Role`.

## Public contracts

Некоторые public contracts и events импортируют concrete Eloquent `Role` или `DirectGrant`. Custom model-subclass формально совместим, но API остаётся связанным с конкретной persistence representation.

Целевой контракт:

```php
interface RoleRecord
{
    public function roleId(): int|string;
    public function roleDefinitionClass(): ?string;
    public function displayName(): string;
}
```

Не нужно превращать весь package в repository-heavy DDD. Достаточно, чтобы публичные events и services не обещали конкретный default model там, где config обещает его подмену.

## Mutation results

Write APIs должны возвращать semantic result, а не только model:

```php
final readonly class GrantPermissionResult
{
    public function __construct(
        public DirectGrant $grant,
        public bool $created,
        public bool $changed,
        public ?CarbonImmutable $validUntil,
    ) {}
}
```

```php
final readonly class SynchronizeRolePermissionsResult
{
    public function __construct(
        public array $added,
        public array $removed,
        public array $unchanged,
        public string $mutationId,
    ) {}
}
```

Это позволит:

- не отправлять повторные events;
- не увеличивать epoch при no-op;
- корректно аудитировать;
- формировать CLI JSON;
- тестировать идемпотентность.

## Events

Существующие события полезны, но следует унифицировать их envelope:

```php
interface AuthorizationMutation
{
    public function eventId(): string;
    public function occurredAt(): CarbonImmutable;
    public function actorId(): int|string|null;
    public function subjectId(): int|string;
    public function panelId(): string;
    public function correlationId(): ?string;
}
```

Нужны отдельные события:

- `RoleAssigned`;
- `RoleUnassigned`;
- `PermissionGranted`;
- `PermissionRevoked`;
- `RolePermissionsChanged`;
- `ScopedRoleAssigned`;
- `ScopedRoleRemoved`;
- `AuthorizationDecisionDenied`, опционально;
- `AuthorizationConfigurationInvalid`.

События mutation должны публиковаться after commit или через transactional outbox, если на них строится внешний аудит.

# Унификация с Chatom

## Общий архитектурный стандарт

Оба проекта должны принять одинаковые правила.

### Bootstrap definition

```text
Mutable DSL
  -> validate
  -> compile
  -> immutable resolved definition
  -> runtime registry
```

Применение:

- AzGuard: `PanelDefinition → ResolvedAuthorizationPanel`.
- Chatom: `ChatSpaceDefinition → ResolvedChatSpace`.

### Runtime state

Никакой mutable request-local state в singleton/application container:

- AzGuard `currentPanel` → scoped `AuthorizationContext`.
- Chatom `SendContext` → explicit pipeline envelope.

### Идентичность

Общий vocabulary:

```text
Actor      внешняя identity
Subject    тот, чьи разрешения вычисляются
Viewer     actor текущего представления
Scope      ресурс ограничения
Panel      application authorization surface
Space      chat environment
Partition  physical storage boundary
```

### Config keys

- Config strings преобразуются в enums/value objects во время boot.
- Unknown keys вызывают boot error в strict mode.
- Runtime не читает разрозненный `config()` внутри business logic.
- Doctor показывает effective compiled configuration.

### Extension seams

Каждый extension point должен иметь:

1. Contract.
2. Default implementation.
3. Config/container binding.
4. Validation.
5. Doctor check.
6. Contract tests.
7. Документированный lifecycle.
8. Architecture rule, запрещающий обход.

AzGuard частично соблюдает это для resolver и matcher, но не полностью для models. Chatom должен применить ту же схему к drivers, repositories, models и pipelines.

### Ошибки

Оба пакета должны иметь:

```php
interface PackageException
{
    public function errorCode(): string;
    public function context(): array;
}
```

Коды не должны вычисляться из PHP class names.

### Commands

Единая форма:

```text
azguard:doctor
azguard:schema:verify
azguard:roles:sync

chatom:doctor
chatom:schema:verify
chatom:counters:repair
```

Все диагностические команды должны поддерживать `--json`.

## Матрица расхождений

| Подход | AzGuard | Chatom | Что стандартизировать |
|---|---|---|---|
| Doctor | Уже есть | Рекомендован | Общий формат checks/result |
| API snapshots | Уже есть | Следует добавить | Единый BC gate |
| Mutation testing | Уже есть | Следует добавить | Package-level mutation budget |
| Mutable runtime state | `currentPanel` singleton | `SendContext` в container | Scoped context или explicit envelope |
| Configurable models | Заявлены, частично обходятся | Используются через panel repositories | Architecture test на отсутствие concrete bypass |
| Pipeline | Почти отсутствует | Расширяемый send pipeline | Общие stage/invariant conventions |
| Outbox | Не основной механизм | Реализован для webhooks | Использовать для security audit events при необходимости |
| Companion packages | Context/Filament | Forum/Poll/Voice | Одинаковые package boundaries |
| Naming | Role/Panel/Context перегружены | Panel/Member/Post перегружены | Общий glossary |
| Schema config | Core configurable, context hardcoded | Panel table maps | Общий schema registry |
| Strict boot validation | Частично | Недостаточно | Compile-time configuration checks |

# Тестовый план

## Temporal access

- Direct grant истекает раньше cache TTL.
- Context grant истекает раньше cache TTL.
- Несколько grants имеют разные expiration.
- Expired grant удаляется, но permission остаётся из роли.
- Clock находится ровно на `expires_at`.
- Clock skew между app и database.
- Persistent и array cache дают одинаковый результат.

## Cache invalidation

- Создание grant увеличивает epoch ровно один раз.
- Revoke увеличивает epoch ровно один раз.
- No-op `updateOrCreate` не увеличивает epoch.
- Role attach/detach не выполняет double invalidation.
- Role permission sync инвалидирует все subject model types.
- Bulk update либо запрещён, либо требует explicit invalidation.
- Lock timeout при revoke не оставляет активное stale permission.
- Context switch очищает только request cache, не durable cache.
- Catalog deployment не использует набор, вычисленный старым кодом.

## Custom models

Для каждой config model:

- relation возвращает custom model;
- read source использует custom model;
- write builder использует custom model;
- CLI использует custom model;
- Filament resource использует custom model;
- events принимают custom model;
- serialization не зависит от concrete class;
- doctor проверяет subclass/contract.

## Multi-panel

- Две panels с одинаковым названием роли.
- Одинаковый raw permission в двух panels.
- Default panel не зарегистрирована.
- Explicit panel неизвестна.
- Registry пуст в strict production mode.
- Nested panel contexts.
- Queue и Octane reuse.
- Scoped role `panel_id=null` и explicit panel.
- Удаление scoped role не затрагивает другие panels.

## Middleware

- Middleware без permission attribute.
- `SkipGuardCheck` как явное разрешение.
- Несуществующий route argument.
- Backed enum и pure enum.
- Invokable controller.
- Closure route.
- Обычная Laravel policy не перехватывается.
- Неизвестная ability возвращает `null`.
- Authenticated model не реализует ожидаемый AzGuard contract.
- Несколько `CheckPermission` attributes используют AND semantics — это должно быть явно зафиксировано.

## Миграции

- Fresh install и rollback на SQLite.
- Fresh install и rollback на PostgreSQL.
- Fresh install и rollback на MySQL.
- Отдельный прогон MariaDB, если она заявлена.
- Все morph ID strategies.
- Custom table names.
- Schema-qualified PostgreSQL table.
- Reserved-like table names.
- Pre-existing duplicates.
- Миллион role assignments либо реалистичный large fixture.
- Failure во время dedupe.
- Fresh schema совпадает с последовательно обновлённой schema.

## Filament

- Permission sync atomic.
- Validator вызывается для каждого нового key.
- Неизвестный permission rejected в strict mode.
- Custom Role model.
- Custom DirectGrant model.
- Несколько authenticatable models.
- Delete bulk action инвалидирует cache.
- Изменение grantable или panel инвалидирует старый и новый ключ.
- UI не позволяет редактировать class-backed role permissions.

## Architecture tests

- Core не зависит от Filament/context.
- Context зависит только от public core namespace.
- Filament не выполняет business mutations напрямую.
- Configurable models не используются как concrete classes.
- Commands вызывают application services.
- Middleware не делает прямые DB queries.
- Events immutable.
- Value objects readonly.
- Runtime context не singleton.
- `@internal` symbols не входят в public signatures.
- Public API snapshot не меняется без approval.

Changelog workflow запускается после появления version tag и затем пытается записать новый changelog в ветку.
