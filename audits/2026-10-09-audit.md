## 4. Процессы

- **CI (12 workflow).** Покрытие хорошее: матрица PHP×Laravel, БД-матрица, coverage, mutation, CodeQL
  (actions), zizmor, split, release с preflight. Исправлено: `npm install` → `npm ci` в docs; устаревшие

- **Composer-скрипты.** Удалены дубли `mutate:all`/`mutate:diff` (второй обещал несуществующий diff-режим) и
  `test:coverage` (без проверки драйвера, OOM). Добавлен `bench`.
- **Релиз (решено, `283b2974`, `04057743`).** Единственный источник заметок — курируемый CHANGELOG
  (`bin/release-notes.sh`). git-cliff, release-drafter и незапускавшийся commitlint удалены. Коммиты и заголовок
  PR проверяются `bin/check-commits.sh` (Conventional Commits, английский ASCII, ≤ 100 символов). CHANGELOG
  начат заново для первого релиза. Русские заголовки ранних коммитов этой ветки проверку не пройдут: ветку нужно
  вливать squash-merge с английским заголовком.
- **Makefile** — только docker up/down/logs/ps. Достаточно; дублировать composer-скрипты не нужно.
- **roadmap/** — заменён одним английским `ROADMAP.md` в корне (раздел 9, решение владельца).
- **`composer check` без драйвера покрытия теперь падает (`f18060e8`).** Пропуск — только явный
  `AZGUARD_ALLOW_NO_COVERAGE=1` с выводом NOT VERIFIED; SQLite-лейн тестов запускается с `--fail-on-skipped`.
- **Docs/Pages (`47ca133f`).** Pages настроен (workflow, https://axiomasoft.github.io/azguard-private/), но
  деплой с `main` падал с 2026-09-30: сборка ломалась на `docs/reference.md`, а на PR не запускалась. Теперь
  сборка идёт на PR, права `pages:write`/`id-token:write` только у deploy, actions обновлены. Деплой
  заработает после merge.

## 8. Предложения

1. ~~Мемо субъекта на запрос~~ — решено иначе: проверка использует переданную модель (раздел 9).
2. **Мемо `PanelSources` на запрос.** ~11% лёгкой проверки, без смены поведения (источники stateless по
   контракту). Низкий риск.
3. **Фасад видимости.** `AzGuard::panel('admin')->visibility()->visibleTo($admin->definition(), ...)` —

4. **Понятная ошибка видимости.** Источник без `FiltersQueries` даёт `source_error`, хотя это неподдерживаемая
   конфигурация. Нужен отдельный код и проверка doctor.
5. **Модель области в `on:` попадает в политику как `$resource`** — неочевидно. Задокументировано; **нужно
   обсудить** отдельный параметр.
6. **Doctor-проверки Filament.** Проверять trait-ы и guard-панель до первого запроса.
7. **`FolderSource` и автоматические роли с видимостью.** Не поддержано — ошибка настройки. Описать или
   поддержать.
8. **Stub политики** генерирует `true` для `RequiresGrant` — верно, но без подсказки о вето.
9. **`azguard:filament:generate`** создаёт CRUD-enum для read-only `RoleResource`. Лишние права.
10. **Иерархия исключений.** Много узких классов. Оценить объединение по кодам перед фиксацией API 1.0.
11. **147 МБ артефактов плана в публичном репо** (логи, локальные пути, источник утечки ключа). Код, тесты и
    документация от `plans/` больше не зависят (`9dfc40d1`), каталог можно удалить одним коммитом вместе с

13. ~~PHPStan level 9~~ — сделано. **Level max** (124 ошибки) — типизированные обёртки над `wheres` Query

## 9. Второй раунд: решения владельца

- **Субъект без N+1 (`624ba4b7`, `b9db21c7`).** Проверка использует переданную вызывающим модель субъекта
  (как Gate и `SessionGuard::user()` в Laravel); по голому `SubjectRef` строка читается, как раньше. Модель
  принимается, только если это сохранённый экземпляр того же класса и ключа. Тёплая проверка 0.67 → 0.42 мс,
  SQL 1 → 0; 100 записей с политикой — 5 SQL вместо 105.
- **Отвязка от `plans/` (`9dfc40d1`).** Код, тесты, скрипты и документация не ссылаются на план; регрессии
  сверяются с тестами без поля «Owning item». Проверено во временном worktree без `plans/` (раздел 11).
- **Релиз и коммиты (`283b2974`, `04057743`).** См. раздел 4.
- **Строгие гейты (`f18060e8`).** См. раздел 4.
- **Логотип и Pages (`8a4d8169`, `47ca133f`).** См. разделы 4 и 6.
- **PHPStan level 9 (`9f583a18`).** См. раздел 7.
- **Roadmap — оценка (файлы не менялись).**
  - Оба файла ссылаются на идентификаторы плана (PLAN1.D2, PLAN2.D27) и написаны по-русски; после удаления
    `plans/` ссылки станут мёртвыми.
  - Неактуально: «общий axioma-support / Chatom» (вне пакета), «feature-first перенос namespaces» (после 1.0 —
    только churn публичного API), «резкий рост PHPStan» (level 9 сделан).
  - Актуально как отложенное: immutable-компиляция Panel DSL, transactional outbox для аудита, обязательная
    morph-map (threat model), SBOM/подпись релизов, фильтр выдач Filament по своим полям.
  - «Удаление level / class-as-identity»: `level` остался только отображаемым полем `#[Role]` — решение для 2.0.
  - Предложение: один английский `ROADMAP.md` без ссылок на план, плюс новые пункты из раздела 11
    (версия состояния не на всю панель, `abilities()` без полного прохода на каждое право).
  - **Сделано:** `roadmap/` удалён, `ROADMAP.md` (английский, без ссылок на план) содержит только актуальные
    пункты: immutable-компиляция DSL, outbox аудита, обязательная morph-map, SBOM/подпись, фильтр выдач Filament,
    квитанция свежести для реплик и блокировки записи по субъекту. `abilities()` ускорен отдельно (`a77c2c94`).

## 10. Нагрузочный стенд `bench/`

По образцу `axiomasoft/chatom` `bench/` (`b43a4dd5`, `72448f3b`, `d531525f`, `d0539e59`, `e1d92ee3`, `9f5af3df`, `ac2835e2`).
Форк-воркеры обращаются к одной базе; уровни smoke/mini/ci/ref (до 1 млн постов); 6 профилей: параллельные
проверки, большие наборы ролей и прав, `visibleTo` на объёме, холодный и тёплый кэш, выдачи и отзывы под
нагрузкой чтения, tenant-проверки. У этапов есть проверки корректности; ошибка движка считается ошибкой, а не
быстрым отказом. Из chatom взяты идеи (каталог профилей, уровни, защита от небезопасной базы, перцентили,
правило 3→5 повторов при CV p95 > 10%, схема результата, `compare.php`); не взяты k6/HTTP, профили хостов,
парные коммиты, сборщик pg_stat. Smoke-уровень входит в тест-сьют.

Найдено стендом:

- **`permissionSet()` тяжёлого субъекта — 2.17 с** (каждый шаблон × каждое право каталога с повторной
  валидацией, ~1.2 млн сравнений). Точные шаблоны теперь — поиск по хешу: **18 мс** (`f956510c`, тест на

- **Соединение, закрытое `DB::disconnect()`** (перед fork, между запросами Octane), давало `source_error` на
  каждой проверке. Хранилище теперь переподключается, как это сделал бы запрос (`1f5aae1e`, тест).
- **Чтения под записью отклоняются.** Версия состояния общая на панель: любая выдача в панели заставляет
  параллельное чтение повторяться, после 3 повторов — отказ `consistency_error`. Это безопасно (fail closed),
  но при одном писателе отклоняется ~20% параллельных проверок, при двух — ~44%, на всех драйверах.
  **Нужно обсудить:** версия на субъекта/tenant или чтение снимка в одной транзакции.
- **`abilities()` — ~4 мс на право** для тяжёлого субъекта (200 мс на 50 прав): полный проход по 220 вкладам на
  каждое право. **Нужно обсудить:** индекс вкладов по точному праву, как в `permissionSet()`.

## 13. Обсуждение архитектуры с владельцем

Обсуждали с владельцем: функционала много, не всем он нужен. Цель — **правильное разделение по
ответственности** (цель, кто пользуется, причины изменений, направление зависимостей), чтобы любая будущая
перестройка была переносом файлов без смены публичного API и без изменения данных. Правила владельца:
**1.0 не выходит с нестабильным API**; **схема БД замораживается сейчас** — владелец начинает пользоваться
текущей версией. Подробно —
**[`audits/2026-10-09-architecture-modularization.md`](2026-10-09-architecture-modularization.md)**.

Коротко:

- **Критерии (раздел 2).** Ядро — если без этого решение или запись неверны, если это общий язык/SPI или если это
  нужно большинству и ничего не стоит без использования. Модуль внутри пакета — включается явно, имеет свои
  артефакты (DSL, таблицы, команды) и вне AzGuard смысла не имеет. Отдельный пакет — только самодостаточная
  интеграция с другим продуктом для его пользователей.
- **Раскладка (раздел 3).** Один пакет `axiomasoft/azguard`: ядро в `src/` (решение, хранение и запись грантов,
  изоляция тенанта в `AzGuard\Tenancy`, все источники, `visibleTo`, батч, события, диагностика, справочники,
  тестовый набор) и модули в `modules/<name>/src` со своими корнями: `AzGuard\Scopes` (области назначения),
  `AzGuard\Audit` (журнал изменений), `AzGuard\DevTools` (генераторы). Отдельный пакет — только
  `azguard-filament`. Модули включаются плагином на панели (`ScopesPlugin`, `AuditPlugin`) или только в консоли
  (`DevToolsServiceProvider`).
- **Взаимодействие (раздел 4).** Модули не знают друг друга; с ядром — через SPI, события и точки конвейера;
  пакет к модулю — только своим мостом. Новый SPI один: `AssignmentScopeEvaluator`, без модуля — только
  глобальная область.
- **Найдено в коде:** аудит — плагин только по названию (таблица, запись и чистка в ядре); ядро и Filament
  импортируют классы областей (`ChangeValidator`, `RoleCompiler`, `GateBridge`, `EnterPanel`, редакторы
  Filament); движок 26 раз проверяет `instanceof DatabaseSource`/`FolderSource`; `Contracts` зависит от 14 зон;
  138 из 246 публичных типов без маркера.
- **Схема БД (раздел 6)** уже почти совпадает с границами: колонки `tenant_*` и `context_*` — часть ключа гранта и
  остаются в таблицах ядра (отдельная таблица тенантности ослабила бы изоляцию); переезжает только владелец
  `azg_audit_log` (в миграцию модуля, без изменения колонок). До заморозки — S1–S7, 3–3,5 дня; после 1.0 —
  только аддитивно, модули меняют только свои таблицы.
- **Что стабилизировать до 1.0 (раздел 5), 25 пунктов.** P0 — разметка и бюджет API, контракты без реализаций,
  способности SPI вместо `instanceof`, финальные namespace и каталоги модулей, SPI и DSL областей, тенант в
  идентичности (ADR), фасад и тестовый набор, регистрация doctor-проверок. P1 — исключения, `GateMode`,
  `StateToken`, `Decision`, словарь причин, неявная панель, ручки согласованности, методы на модели хоста, DSL,
  API Filament. P2 — заморозка схемы, конфиг, события, команды, JSON `doctor`, префиксы `azguard/` и `azg_`.
  Оценка 42–60 рабочих дней (минимальный вариант — 38–53). Есть критерий выпуска «1.0 со стабильным API» и
  арх-тесты, которые его держат.
- **Порядок:** схема → стабилизация в текущем пакете (API ломать можно) → 1.0 → дальше без смены API и данных.

## 14. Три пункта после ревью (решено)

1. **Точный ключ в Filament (`61c8cf49`).** `AzGuard\Support\ModelKey` стал публичным (`@api`, в манифесте API):
   ядро и Filament ищут субъекты, тенанты и контексты только по точному ключу. Дубликат хелпера в Filament удалён,
   граница пакетов не нарушена (Filament использует только публичное ядро). `GrantEditor::lookup()` для `a/b`,
   `02`, `2abc` не делает ни одного запроса и не находит строку (`RoleGrantResourceTest`), на PostgreSQL ошибка
   и сорванная транзакция больше невозможны.
2. **Пакетное чтение `DecisionSet` (`ae27bbea`).** Ревизии и гранты набора читаются фиксированным числом выражений
   (9 SQL на 500 субъектов вместо 1 506). Снимок набора из 500 субъектов без кэша: 167 → 23 мс (SQLite),
   0.5–0.8 с → 27–31 мс (серверы); время набора ~1.34 с, остаток — вычисление в PHP. Таблица —
   `bench/README.md`, «DecisionSet batching».
3. **Полный последовательный прогон на серверных БД.** Было 92 failed / 577 errors (435 `too many clients`).
   Причины: закреплённый PDO не освобождался после сессии чтения (`c03f1635`), соединения перезагруженного
   приложения не закрывались (`1df62381`), схема серверной БД оставалась от прошлого теста (`d5a8c6bb`), тесты
   только для SQLite не были выделены (`42d3b1f7`, `e9bb0ee5`, `aad41106`), гонка чтения id воркера в тестах
   engines (`18a83eaa`). Теперь на PostgreSQL 16 и MySQL 8.4 зелёный весь сьют: pgsql 4808 / 4808 (после `18a83eaa`), mysql 4808 / 4808.

покрытие строк 93.9% (порог 85), docs:language, docs:php, сборка VitePress — зелёные.
