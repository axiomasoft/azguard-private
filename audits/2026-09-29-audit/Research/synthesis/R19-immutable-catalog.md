# R19 — Immutable panels и versioned catalog

**Статус:** предварительный Perplexity synthesis, сохранён из этой сессии. Вопрос сформулирован на уровне области, без точных фрагментов текущего кода. Советы о локальном AzGuard использовать только после сверки с [репозиторием](../repository-inventory.json) и [первичными источниками](../primary-sources.md). Пересечения с другими темами смотрите в [карте исследования](../README.md).

## Исходный вопрос

Laravel code-first permission catalog and panel registration architecture: mutable fluent panel changes after registry insertion, duplicate registration, freeze at boot, builder-to-immutable definition vs defensive copy/minimal freeze. Hot reload, worker restart, deploy generation/catalog fingerprint for changed code roles and merge policy. Extension registration order and conflict detection. Avoid interfaces solely mirroring each class.

## Документированные факты

В Laravel service provider register() предназначен для связывания сервисов с контейнером; регистрация функциональности, зависящей от других сервисов, должна выполняться в boot(). boot() вызывается после регистрации остальных провайдеров. В Laravel 13 пользовательские провайдеры перечисляются в bootstrap/providers.php. — официальная документация, просмотрена 2026-09-29.
Laravel-контейнер различает singleton — один экземпляр на контейнер — и scoped — один экземпляр на lifecycle запроса или задания; scoped-экземпляры сбрасываются при переходе к следующему lifecycle в Octane/queue worker. Сам по себе singleton не делает объект неизменяемым и не задаёт правила дублирования записей. — просмотрена 2026-09-29.
Octane загружает приложение в память при старте worker; провайдеры не выполняются заново для каждого запроса. Изменения кода не подхватываются автоматически, а после деплоя документация рекомендует php artisan octane:reload. — официальная документация, просмотрена 2026-09-29. Это источник версии 12.x; не следует трактовать его как проверку поведения каждой поддерживаемой версии или каждого runtime.

## Архитектурная оценка

Панель лучше рассматривать как builder до регистрации и как неизменяемую definition после неё. Если registry сохраняет ссылку на mutable fluent-объект, последующие вызовы могут незаметно менять уже опубликованное определение; поведение зависит от того, когда читатель получает снимок. Это риск смешения фаз конфигурации, а не утверждение о дефекте конкретного кода.
Предпочтительный вариант для долгоживущего каталога — преобразовать builder в отдельное immutable-представление при вставке в registry: нормализовать поля, скопировать вложенные коллекции и закрыть дальнейшие изменения. Defensive copy проще по миграции, но нужна глубокая копия: поверхностное клонирование не защищает от мутаций вложенных массивов или объектов. Минимальная заморозка с запретом fluent-вызовов после регистрации может быть достаточной, если все хранимые значения сами по себе immutable и это проверяется.
Freeze логично выполнять после завершения регистрации расширений и до первой публикации каталога читателям. В Laravel boot-провайдеры — естественная точка координации, поскольку запускаются после регистрации провайдеров, но порядок между несколькими сторонними расширениями сам по себе не становится детерминированным контрактом библиотеки: его следует явно определить в собственном API.
Для повторной регистрации я бы предпочёл ошибку на duplicate key, а не молчаливое «последний победил»: явная ошибка выявляет конфликт пакетов и случайный двойной вызов провайдера. Если override нужен как расширяемость, пусть он будет отдельной явной операцией с проверяемым происхождением/приоритетом. Одинаковый повтор одного определения можно считать идемпотентным только при точном совпадении нормализованного содержимого; одинаковый ключ с отличающимся содержимым — конфликт. Это проектная рекомендация, не правило Laravel.

## Hot reload и fingerprints

При Octane обновление кода — это прежде всего смена поколения worker, а не сигнал пересобрать runtime-каталог внутри старого процесса: документация подтверждает однократный boot и необходимость reload после deploy. Для обычного PHP-FPM/короткоживущего процесса модель может быть иной — это зависит от среды запуска.
Рекомендация для последующего дизайна: вычислять детерминированный catalog fingerprint из канонического набора определений и версии/идентификатора сборки. Использовать его как generation-компонент для кэшированных производных результатов, увязав с уже имеющимися cache generation и revision fence. Тогда изменение code-first ролей/разрешений не будет ошибочно выглядеть как прежний каталог после обновления кода. Fingerprint не заменяет DB revision: один описывает версию кода/каталога, другой — изменения состояния БД. При rolling deploy следует определить политику совместимости старых и новых worker и не смешивать кэш-ключи между поколениями.

## Нерешённые вопросы аудита

Официальные источники Laravel не устанавливают правила для registry разрешений: семантику duplicate, merge, приоритетов расширений, канонизации fingerprint или согласования его с DB revision. Также не проверены фактическая глубина копирования, публичные точки мутации, порядок регистрации трёх пакетов и способ инвалидации кеша.
Практический критерий против лишней абстракции: не создавать интерфейс на каждый класс ради зеркального API. Вводить контракт там, где есть реальная граница замены, внешняя интеграция или потребность тестового потребителя; builder, immutable definition и registry могут оставаться конкретными типами, если библиотека не обещает пользователям полиморфную замену этих ролей.
