# R14 — Composer isolation и dependency matrix

**Статус:** предварительный Perplexity synthesis, сохранён из этой сессии. Вопрос сформулирован на уровне области, без точных фрагментов текущего кода. Советы о локальном AzGuard использовать только после сверки с [репозиторием](../repository-inventory.json) и [первичными источниками](../primary-sources.md). Пересечения с другими темами смотрите в [карте исследования](../README.md).

## Исходный вопрос

Laravel PHP package monorepo CI with path repositories can hide undeclared dependencies. Core-only, core+context, core+Filament and all-installed consumer fixtures; published archive/package discovery tests, prefer-lowest/stable, Laravel 11/12/13 Testbench mapping, Filament 5 PHP/Laravel compatibility constraints and Pest 4 runtime minimum. Verify current constraints from official composer manifests; avoid fabricated support matrix.

## Ответ Perplexity

## Вывод

Факт: локальные Composer path repositories удобны для монорепозитория, но не доказывают, что каждый пакет объявляет все зависимости, нужные потребителю. Composer устанавливает такой пакет из локального каталога; если возможно, он подключает его симлинком. Архитектурный вывод: тесты, которые запускаются только в общей root-среде с path repositories, могут пройти благодаря другим пакетам или dev-зависимостям, уже установленным рядом. Поэтому CI стоит проверять пакеты в отдельных потребительских проектах с разными наборами установленных пакетов, а публикацию — отдельно от локальной разработки.
Ниже — исследовательская рекомендация для описанного устройства, не утверждение о текущей реализации репозитория. Я не проверял и не предполагаю доступ к приватному репозиторию.

## Что подтверждают источники

- Composer документирует path repositories как способ подключать локальные каталоги, в том числе в монорепозиториях. Симлинк позволяет потребителю видеть рабочее дерево пакета напрямую; конфигурация репозиториев относится к root-проекту, а не наследуется от зависимостей. Это делает локальную сборку отличающейся от независимой установки опубликованного пакета.
- Документация Laravel указывает, что Laravel 13 требует PHP 8.3 минимум; таблица поддержки также приводит PHP-диапазоны Laravel 11, 12 и 13. В документации Testbench Core версия 9 соответствует Laravel 11, 10 — Laravel 12, 11 — Laravel 13. Это соответствие указывает на подходящие линии зависимостей, но не гарантирует, что конкретные версии Testbench совместимы с выбранными PHPUnit/Pest и PHP в матрице CI.
- Официальная установка Pest на дату исследования указывает PHP 8.4+ для запуска. Следовательно, библиотека, декларирующая PHP 8.3+, не может считать тестовый процесс на Pest 4 доказательством запуска CI на PHP 8.3. Поддержку PHP 8.3 пакетом и минимальную версию PHP для тестового инструментария следует явно разделить.
- Официальная документация Filament 5 указывает требования «PHP 8.2+» и «Laravel v11.28+». Эти общие требования не подтверждают поддержку каждой комбинации Laravel 11/12/13: фактический вердикт для выбранного релиза должен следовать из его Composer-манифеста и разрешения зависимостей, а не из обобщённой матрицы.

## Матрица версий и артефакты

Практичная схема — запускать Laravel-версии через соответствующие линии Testbench: 11 → Testbench 9, 12 → 10, 13 → 11. Однако точные ограничения Laravel, PHP и зависимостей нужно проверять по манифестам конкретных версий Testbench и всех трёх пакетов; имеющиеся источники не дают полной подтверждённой матрицы.
Для prefer-lowest и prefer-stable нужны отдельные Composer-разрешения: первое проверяет нижние границы объявленных ограничений, второе — стабильность выбора при настройке проекта. Архитектурный вывод: низшие допустимые версии следует проверять хотя бы на core-only и на интеграциях с наибольшей поверхностью зависимостей; иначе полный набор может маскировать дефект минимальной установки.
Архивная проверка должна собирать каждый пакет отдельно и устанавливать его в свежий consumer без path repositories. Включите проверку Composer metadata/package discovery и запуск теста загрузки провайдера/интеграции там, где она применима. Это обнаруживает ошибки упаковки, автозагрузки и регистрации, которые симлинк в монорепозитории способен скрыть.
