# R28 — Порты хранения и persistence-модели

**Статус:** предварительный Perplexity synthesis, сохранён из этой сессии. Вопрос сформулирован на уровне области, без точных фрагментов текущего кода. Советы о локальном AzGuard использовать только после сверки с [репозиторием](../repository-inventory.json) и [первичными источниками](../primary-sources.md). Пересечения с другими темами смотрите в [карте исследования](../README.md).

## Исходный вопрос

Ideal storage abstraction with Eloquent default for an authorization library whose owner permits rewriting everything: define minimal read/write transaction/revision ports that can coherently support alternate storage, customized tables/models and Filament read projections. Same-connection atomicity capability versus unsupported cross-store dual writes, snapshot token from providers, external grant sources and identity codecs. Avoid a generic CRUD repository for each table. Is an independent kernel/contracts package beneficial for this goal? Compare meaningful boundary choices.

## Ответ Perplexity

Дата среза: 2026-09-29. Ниже — проектные рекомендации для окончательного дизайна Opus5.5, а не описание существующей реализации. У меня нет доступа к приватному коду AzGuard; учитываю только заданные требования. Центральный вывод: строить ядро вокруг семантики проверки и атомарного изменения авторизационных данных, а Eloquent оставить заменяемым адаптером по умолчанию — не превращать всю библиотеку в универсальный ORM-порт.

## Факты

- Laravel разделяет авторизацию на gates и policies: первые подходят для проверок общего действия, вторые группируют логику вокруг ресурса или модели. Это полезная точка интеграции AzGuard, но не обязательная внутренняя модель хранения библиотеки.
- Eloquent связывает модель с таблицей и допускает явные имена таблиц и отдельные соединения. Значит, адаптер хранения может поддерживать пользовательские модели, таблицы и подключения без изменения доменного API.
- Laravel предоставляет транзакции на подключении; документация описывает их как атомарную операцию, которая откатывается при исключении. Операции на разных подключениях не становятся от этого единой транзакцией.
- Filament допускает пользовательский источник данных, включая данные, возвращаемые функцией records(). Следовательно, UI-проекция не обязана быть тем же интерфейсом, что и запись авторизационных правил.

## Предложение по границам

Минимальную границу ядра я бы задал не набором CRUD-репозиториев, а тремя узкими возможностями:
- AuthorizationReader: читает согласованный набор субъектов, ролей, разрешений и связей для вычисления решения.
- AuthorizationWriter: применяет именованные изменения — например, назначить роль, отозвать разрешение, заменить набор грантов — с явной семантикой идемпотентности.
- AuthorizationUnitOfWork: выполняет группу изменений в транзакции и сообщает, гарантирует ли адаптер атомарность на выбранном хранилище.
Для каждой успешной записи нужен Revision или SnapshotToken: монотонная версия, хеш/непрозрачный токен либо версия области авторизации. Провайдер контекста должен отдавать токен вместе со снимком, чтобы кэш и диагностика могли отличать актуальное решение от вычисленного по устаревшим данным. Контракт не должен обещать глобально согласованный снимок, если адаптер его не обеспечивает.
Не вводить RoleRepository, PermissionRepository, GrantRepository с симметричными find/create/update/delete только ради абстракции. Они закрепят текущую реляционную схему и протащат детали хранения в ядро. Лучше описывать операции языком домена и читать именно тот граф данных, который нужен оценщику. Для Filament предоставить отдельный read-порт/адаптер либо рекомендованный Eloquent query-путь; таблицы, поиск и пагинация — не обязанности доменного writer.
Внешние источники грантов оформлять как read-only GrantSource с явным приоритетом/объединением и происхождением результата. Их нельзя включать в транзакцию локальной БД. Если внешний источник изменился, токен должен отражать его версию или оставаться явно ограниченным локальной revision. Идентичности нормализовать через IdentityCodec: преобразовать Laravel-модель или другой principal в стабильный ключ вида type + id, без предположения, что все субъекты — Eloquent-модели или целочисленные ID.

## Транзакции и замены хранилища

Eloquent-адаптер по умолчанию должен владеть таблицами, миграциями и оптимизированными запросами, но позволять переопределить модели, таблицы и connection. Критичный инвариант — все записи одной логической операции и чтения, необходимые для её проверки, используют один transaction boundary. Адаптер обязан сообщать capability вроде atomicity: same_store; ядро не должно изображать межсистемную атомарность.
Для альтернативного хранилища адаптер реализует те же доменные операции и сообщает ограничения: транзакционность, согласованность чтения, revision и поддерживаемые фильтры. При разных сторах нельзя обещать dual write как атомарный. Практические варианты — назначить один store источником истины, вынести изменения в outbox/очередь с eventual consistency либо запретить такую конфигурацию для операций, требующих немедленного согласования. Это должно быть видимо в API/конфигурации, а не скрыто внутри фасада.

## Пакеты и решения

Отдельный kernel/contracts package полезен условно. Он оправдан, если есть реальная цель: несколько независимых адаптеров, интеграции вне Laravel или отдельное версионирование контрактов. Тогда ядро — PHP-only, без Eloquent/Illuminate-зависимостей; Laravel-пакет содержит provider, фасады, middleware, миграции и Eloquent adapter. Но преждевременное разделение добавит совместимость версий, релизы и риск дублированных контрактов. Для одного Laravel-пакета с одним официальным адаптером разумнее начать с чётких namespace-границ внутри пакета и выделять Composer-пакет при появлении второго независимого потребителя.

## Нерешённые вопросы

- Нужно ли поддерживать несколько независимых write-store, или «альтернативное хранилище» означает ровно один адаптер на установку?
- Требуются ли синхронные внешние гранты при каждом решении, или допустимы кэш и ограниченная свежесть?
- Какова семантика конфликтов между локальными и внешними grants: объединение, запрет приоритетнее, либо источник с приоритетом?
- Нужна ли строгая сериализуемость изменений, или достаточно атомарности одной операции и eventual consistency для проекций?
- Должен ли Filament быть официальной интеграцией, или библиотека ограничивается документированным query/read-интерфейсом?
Для финального дизайна стоит зафиксировать эти ответы до выбора точных сигнатур интерфейсов: именно они определяют, где проходит граница kernel, а где начинается Laravel-адаптер.
