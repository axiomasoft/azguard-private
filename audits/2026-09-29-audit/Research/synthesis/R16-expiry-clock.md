# R16 — Expiry, часы и temporal consistency

**Статус:** предварительный Perplexity synthesis, сохранён из этой сессии. Вопрос сформулирован на уровне области, без точных фрагментов текущего кода. Советы о локальном AzGuard использовать только после сверки с [репозиторием](../repository-inventory.json) и [первичными источниками](../primary-sources.md). Пересечения с другими темами смотрите в [карте исследования](../README.md).

## Исходный вопрос

Authorization grant absolute expires_at and cached nearest validity deadline: TTL is not authorization deadline, now>=deadline semantics, UTC microseconds, clocks across DB/PHP/cache nodes, long requests, renewable grants, earliest expiry under union/intersection/context merge. Effective set versus decision cache. Deterministic tests and clock skew contract; minimum design for Laravel Carbon.

## Ответ Perplexity

## Краткий вывод

Абсолютный expires_at должен оставаться источником истины для авторизации; ближайший срок действия, записанный в кэш, — только повод повторно проверить вычисленное решение. TTL записи сам по себе не запрещает доступ: решение должно отказать, если в момент проверки now >= deadline, а долгий запрос требует отдельно определить, считается ли авторизация снимком на начало запроса или проверяется повторно перед защищённым действием.

## Документированные факты

PostgreSQL. timestamptz хранит момент времени внутри в UTC, хотя при выводе преобразует его в часовую зону сессии. Точность типов времени — до микросекунды; PostgreSQL допускает заданную точность от 0 до 6 знаков. Поэтому для грантов уместно документировать единый UTC-инстант и явно проверить фактическую точность столбца и round-trip через используемый PHP-драйвер.
PostgreSQL различает transaction_timestamp() — время начала транзакции — и clock_timestamp() — фактическое время вызова, меняющееся даже внутри одного SQL-оператора. Если проверка истечения должна отражать момент выполнения запроса, использование CURRENT_TIMESTAMP внутри долгой транзакции может не соответствовать этому ожиданию.
Laravel и Carbon. Laravel 12 принимает в Cache::put() число секунд либо DateTime как момент истечения, а отсутствие срока хранит запись бессрочно. Документация также описывает Cache::flexible() как механизм, который может возвращать устаревшее значение в заданном stale-интервале. Для кэша решений об авторизации такое поведение нельзя трактовать как разрешение выдавать доступ после дедлайна гранта.
Carbon позволяет фиксировать тестовое now через setTestNow() и очищать его; начиная с Carbon 2.56, этот вызов не меняет часовую зону now(). Это удобно для детерминированных unit-тестов, но не имитирует самостоятельно часы БД, кэш-сервера или других PHP-узлов.

## Архитектурная оценка

Инвариант истечения. Сравнивать абсолютные инстанты, а не округлённые секунды или TTL: valid ⇔ now < expires_at; на точной границе now == expires_at грант уже недействителен. TTL можно вычислить как консервативную подсказку для повторного чтения, например max(0, deadline - now), но даже положительный TTL не заменяет сравнение дедлайна при использовании кэшированного решения.
Объединение источников. Для разрешения по объединению грантов эффективный deadline обычно равен максимуму сроков тех грантов, каждый из которых независимо достаточен для разрешения: более раннее истечение одного гранта не должно отнимать доступ, пока остаётся другой действующий путь. Для пересечения требований эффективный deadline — минимум сроков необходимых грантов: истечение любого обязательного условия снимает разрешение. Это вывод из логики AND/OR, а не свойство Laravel. При слиянии контекстов вычислять дедлайн нужно по фактическому набору грантов, удовлетворяющему контекстному условию; нельзя без спецификации трактовать «earliest expiry» как минимум по всем кандидатам. Без формальной семантики merge это остаётся открытым вопросом.
Кэшируемый объект. Эффективный набор разрешений и кеш решений — разные модели. Набор можно хранить вместе с ближайшим дедлайном и перед выдачей фильтровать по текущему времени. Кеш решения должен дополнительно привязываться к субъекту, ресурсу, действующему контексту, ревизии и правилам объединения; при достижении deadline — пересчитываться, не обслуживаться как stale. Имеющиеся revision fence и generation envelopes полезны против устаревших ревизий, но из предоставленного описания нельзя установить, как они взаимодействуют с истечением гранта.

## Минимальный контракт

- Нормализовать expires_at в UTC и сохранять микросекунды в БД, сериализации кэша и сравнении; явно определить точность для драйверов, которые дают меньшую точность.
- Инжектировать источник времени в библиотечный слой, а не вызывать системное now() в нескольких местах; Laravel-адаптер может использовать Illuminate\Support\Carbon, но API границы лучше выражать как DateTimeImmutable/DateTimeInterface.
- Указать, что считается часами истины. Практичный минимум — синхронизация узлов и заданный допустимый skew; для строгого контракта сравнивать с временем авторитетного источника (например, БД) либо применять запас безопасности не меньше максимального skew. Один Carbon::setTestNow() этого контракта не обеспечивает.
- Для длительных запросов определить точку проверки: при входе, перед каждой чувствительной операцией или оба раза. Проверка только в middleware не гарантирует, что грант не истёк до позднего побочного эффекта.
- Для renewable grants считать новую выдачу новым абсолютным дедлайном; не «продлевая» кэшированный deadline автоматически, а повторно вычислять решение при смене гранта/ревизии.

## Тесты и нерешённое

Зафиксировать тесты непосредственно до границы, ровно на ней и после неё, включая микросекунды; долгий запрос, renewal, clock skew ±Δ, разные часовые зоны отображения, точность БД round-trip, смену ревизии и матрицу union/intersection/context merge. В тестах использовать фиксируемые часы и явный fake для DB/cache clocks.
Официальные материалы подтверждают поведение PostgreSQL, Laravel Cache и Carbon; они не задают контракт часов между узлами, семантику вашей модели merge, политику renewal или гарантию проверки внутри долгого запроса. Их необходимо определить в публичном контракте библиотеки и проверить по трём Composer-пакетам; репозиторий здесь не исследовался, и доступ к нему не предполагается.
