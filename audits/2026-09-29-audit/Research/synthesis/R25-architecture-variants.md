**Статус:** предварительный Perplexity synthesis, сохранён из этой сессии. Вопрос сформулирован на уровне области, без точных фрагментов текущего кода. Советы о локальном AzGuard использовать только после сверки с [репозиторием](../repository-inventory.json) и [первичными источниками](../primary-sources.md). Пересечения с другими темами смотрите в [карте исследования](../README.md).

## Исходный вопрос

Owner explicitly permits replacing any existing code, namespace, structure and API; prioritize flexibility, configurability, clean public API and understandable names. For AzGuard, embedded PHP8.3+/Laravel RBAC + contextual authorization + Filament5, compare three coherent target architectures: modular Laravel-native package, framework-independent authorization kernel with Laravel/Eloquent adapters, and policy/relationship engine. Include dependency direction, public versus SPI surface, configurations, tradeoffs, rationale and failure cases. Do not make backward compatibility a veto or design a detailed implementation plan. Which target best balances these priorities?

## Ответ Perplexity

Рекомендация: выбрать framework-independent authorization kernel с Laravel/Eloquent-адаптерами, но оставить его внутренней архитектурой одного Laravel-пакета, а не превращать проект в набор независимо публикуемых пакетов. Это лучше всего сочетает гибкость и чистые границы с простым Laravel API и практичной интеграцией с Filament 5.
Исследование опирается на публичную документацию. У меня нет доступа к приватному коду AzGuard; существующую реализацию и её структуру не считаю ограничениями.

## Проверенные факты

- Laravel описывает два штатных механизма авторизации: gates для именованных действий и policies для логики, организованной вокруг моделей или ресурсов. Policies разрешаются контейнером Laravel. (). Для библиотечного пакета Laravel предоставляет автообнаружение service provider через Composer и загрузку конфигурации через provider. ().
- Filament 5 автоматически применяет Laravel model policies к стандартным операциям ресурсов, но не гарантирует авторизацию пользовательских страниц, действий и иной прикладной логики. Для bulk-операций возможны отдельные проверки на каждую запись; документация также предупреждает, что не всякий UI-компонент автоматически вызывает policy. , , .
- PHP 8.3 добавляет, среди прочего, типизированные константы классов и глубокое клонирование readonly-свойств; это возможности языка, а не обязательные основания строить API на атрибутах или enum-ах. .

## Предложение по дизайну

Выбрать вариант 2 как архитектуру продукта, а вариант 1 — как опыт установки и использования: один Composer-пакет с автообнаружением Laravel provider, одной основной точкой конфигурации и интеграциями, включаемыми явно. Не публиковать отдельные пакеты для каждого внутреннего модуля, пока нет независимой потребности в версиях и релизах.
Семантику решений держать в ядре: субъект, действие, ресурс и явно передаваемый контекст; результат должен различать разрешение и отказ, а при необходимости содержать стабильную причину. Роли и RBAC — один из источников решений, а не вся модель авторизации. Отдельно предусмотреть контекстные ограничения и отношения, но не делать из них обязательный собственный язык политик до доказанной потребности.
Laravel-адаптер должен связывать контракты с контейнером, Eloquent и штатными gates/policies; Filament-адаптер — повторно использовать те же решения для стандартных и пользовательских действий. Важный инвариант: скрытие кнопки не заменяет серверную проверку, а разрешение отдельной записи не доказывает безопасность запроса, возвращающего коллекцию.
Конфигурация должна называть бизнес-смысл и поведение: модель субъекта, хранение, способ назначения ролей, контекст, кэширование и интеграции. Не выставлять наружу классы ядра, внутренние enum-ы, SQL-детали и «универсальные» хуки без гарантированного контракта. Публичная поверхность — только то, что пользователю библиотеки нужно для штатной интеграции; SPI — только расширения с документированной семантикой и тестируемыми инвариантами.

## Нерешённые вопросы

До фиксации дизайна нужно определить: обязательны ли multi-tenant границы и как они участвуют в запросах; нужен ли запрет по умолчанию; каковы правила приоритета явных разрешений и отказов; какие контексты должны быть доступны в policy; как обновления прав отражаются на кэше и долгоживущих сессиях; требуется ли фильтрация Eloquent-запросов по разрешённым записям; какие операции Filament 5 нужно покрыть помимо стандартных CRUD. Это продуктовые решения, не выводы из документации.
Итог: ядро с направленными наружу адаптерами — лучший баланс при условии, что ядро остаётся небольшим, а Laravel-facing API выглядит естественно. Полностью policy/relationship-центричный движок оправдан только если выражение отношений и фильтрация наборов данных — центральная, заранее подтверждённая задача продукта.
