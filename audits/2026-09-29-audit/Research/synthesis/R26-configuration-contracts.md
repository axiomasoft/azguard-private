# R26 — Конфигурируемость без противоречивых режимов

**Статус:** предварительный Perplexity synthesis, сохранён из этой сессии. Вопрос сформулирован на уровне области, без точных фрагментов текущего кода. Советы о локальном AzGuard использовать только после сверки с [репозиторием](../repository-inventory.json) и [первичными источниками](../primary-sources.md). Пересечения с другими темами смотрите в [карте исследования](../README.md).

## Исходный вопрос

Ideal configuration architecture for a freely redesigned Laravel authorization library: validated immutable settings, profile presets, per-panel overrides, policy injection versus boolean feature flags, config:cache serialization, environment deployment, extension provider registry and deterministic conflict detection. What should be configurable (storage, models, subject mapping, sources, membership, superadmin scope, grammar) and what must remain an invariant? Include impossible combinations, schema versioning and capability diagnostics. Owner permits all structural changes.

## Ответ Perplexity

Вывод: конфигурацию AzGuard лучше проектировать как публичный декларативный вход, который при загрузке приложения преобразуется в валидированный неизменяемый снимок настроек. Профили и переопределения для панелей должны собираться до создания сервисов; расширения — подключаться через явный реестр с детерминированным разрешением конфликтов. Это предложение для полной переработки, а не описание или аудит недоступной мне приватной реализации AzGuard.

## Проверенные факты

- Laravel поддерживает публикацию конфигурации пакета и слияние её значений через service provider; пакет может регистрировать provider автоматически через Composer package discovery. Для config:cache конфигурационные файлы должны избегать замыканий, поскольку Laravel не может сериализовать их корректно. официальная документация Laravel: Package Development
- При кэшировании Laravel собирает конфигурацию в единый файл. После этого .env при запросах и командах Artisan не загружается; env() следует вызывать только внутри файлов конфигурации. официальная документация Laravel: Configuration
- Laravel описывает Gate как подход к отдельным действиям, а Policy — как группировку авторизационной логики вокруг модели или ресурса. Policies разрешаются через service container, что позволяет внедрять зависимости. официальная документация Laravel: Authorization
- В PHP readonly защищает свойство от повторного присваивания после инициализации. Это языковой механизм, но сам по себе он не гарантирует глубокую неизменяемость вложенных объектов. официальная документация PHP: Properties

## Предлагаемая архитектура

- Конфигурация приложения — только данные. Публичный PHP-конфиг содержит строки классов, скаляры, массивы и идентификаторы профилей, но не экземпляры сервисов, замыкания, ресурсы или объекты, чья сериализация зависит от окружения. Не читайте .env из runtime-классов: Laravel требует ограничить env() конфигурационными файлами, особенно при config:cache.
- Сборка в неизменяемый снимок. На старте ConfigCompiler принимает сырые массивы, применяет defaults, профили и overrides, проверяет типы и совместимость, затем строит AzGuardSettings и производные value objects. Ошибки должны завершать boot с точным путём, например panels.admin.storage.connection, а не превращаться в молчаливое fallback-поведение. Сервисы получают готовый снимок через контейнер; не читают произвольные ключи config() по ходу проверки доступа.
- Профили и панели с явной семантикой. Профиль — именованный полный набор базовых решений, например database или teams; panel override — частичное переопределение разрешённых настроек. Задайте один порядок слияния: defaults → профиль → глобальная конфигурация → panel override. Запретите менять идентичность общей схемы панели-специфичным способом, если storage и модель данных физически общие; разрешайте такое разделение только при явном раздельном backend/schema. Это предложение: официальные источники Laravel не предписывают такую модель.
- Политики — классы, флаги — только для режимов. Для предметного поведения используйте внедряемые контракты: SubjectResolver, PermissionSource, MembershipResolver, SuperadminRule, PermissionNameGrammar. Это согласуется с Laravel-способом группировать правила в Policies и разрешать классы через контейнер. Булевы флаги уместны для простых возможностей (audit_enabled, cache_enabled), но не как подмена расширяемой логики флагами вроде use_custom_membership; иначе комбинации флагов образуют неявный API и усложняют валидацию.
- Реестр расширений — явный и стабильный. Провайдеры объявляют уникальный ключ, версию контракта, поддерживаемые возможности и приоритет. Одинаковый ключ без явной политики override — ошибка; одинаковый приоритет для взаимоисключающих реализаций — тоже ошибка, а не случайный выбор по порядку регистрации. Не полагайтесь на порядок Composer discovery как на приоритетную семантику: документация подтверждает discovery provider, но не задаёт для AzGuard правила разрешения конфликтов.

## Настраиваемое и инварианты

Настраиваемыми сделайте: storage-драйвер, таблицы/соединение и миграции; классы моделей и их ключи; отображение subject и auth guard; источники ролей/прав; правила членства и tenant-принадлежности; область действия superadmin; грамматику имён разрешений; профили, panel overrides, кэш и диагностику возможностей.
Инвариантами оставьте: deny по умолчанию; отсутствие повышения привилегий из-за ошибки конфигурации или backend; однозначную идентичность subject/tenant; проверку авторизации на сервере; отсутствие скрытого межпанельного доступа; одинаковую семантику результата при любых допустимых backend. Конфигурируемость не должна позволять отключить эти гарантии.

## Невозможные комбинации и диагностика

Валидатор должен отклонять, например, membership=tenant без tenant-resolver; superadmin_scope=tenant без способа определить tenant; выбранный storage без нужных таблиц/миграционной поддержки; panel override, указывающий на несовместимую модель; несколько источников с одинаковым приоритетом и неоговорённой стратегией объединения; невалидную грамматику, допускающую неоднозначный разбор permission names.
Добавьте schema_version для формата конфигурации и capability diagnostics — команду Artisan, которая показывает активный профиль, эффективные настройки панели, обнаруженные драйверы, миграционный статус и отсутствующие возможности. При неизвестной major-версии схемы boot должен завершаться ошибкой; миграции конфигурации между версиями должны быть явным преобразованием, а не угадыванием. Формат схемы, семантика capability и политика миграции — авторские предложения, не требования Laravel.

## Открытые вопросы

До финального дизайна Opus5.5 нужно решить: означает ли «panel» только UI-контекст или границу безопасности; могут ли панели иметь независимые хранилища; как объединять несколько permission sources — union, приоритет или veto; разрешён ли superadmin в обход обычных Policies; какие Laravel/PHP версии поддерживать и нужен ли runtime reload конфигурации. Без ответов безопасный базовый выбор — один неизменяемый снимок на процесс и отказ при неоднозначной конфигурации.
