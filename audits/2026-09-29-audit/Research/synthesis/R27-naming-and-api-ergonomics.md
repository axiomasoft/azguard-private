## Исходный вопрос

Design a clear naming/glossary and small ergonomic public API for freely redesigned PHP/Laravel authorization library: Subject/Actor/Principal, Permission/Ability/Action, Grant/Assignment, Panel/Namespace/AuthGuard/Tenant/Context/Resource scope, RoleDefinition versus persisted Role, Decision, Catalog. Avoid name collisions with Laravel Gate/Guard and ambiguous ContextRole when it stores direct grants. Compare explicit immutable query API and fluent convenience API, readonly value objects, grant command vs side-effect builder, return types and named-argument contract. Give several illustrative calls, not implementation.

## Факты из первичных источников

Laravel описывает авторизацию через Gate и Policy: Gate — проверка, часто для действий без конкретной модели; Policy — группировка правил вокруг модели или ресурса. Laravel также использует Guard в отдельном контексте аутентификации: он определяет способ аутентификации запроса. Поэтому AzGuard не стоит называть собственный объект авторизации Gate или Guard: эти слова уже имеют конкретные значения в экосистеме, а Guard к тому же легко спутать с аутентификационным механизмом Laravel.
В PHP readonly-классы доступны с версии 8.2; они делают свойства класса readonly и запрещают динамические свойства. Именованные аргументы поддерживаются начиная с PHP 8.0. Они делают вызовы самодокументируемыми, но имена параметров становятся частью практического контракта API: несовпадение имени при переопределении может привести к ошибке при вызове именованным аргументом.

## Предлагаемый глоссарий

Используйте один основной термин на понятие; альтернативы — только в документации, а не как взаимозаменяемые классы и методы.
Tenant следует использовать только для изоляции арендатора, а AuthGuard — только когда действительно имеется в виду Laravel guard аутентификации. Не вводите универсальный Context, если в нём смешиваются subject, tenant, panel и resource: передавайте эти измерения отдельными именованными параметрами или объединяйте в строго типизированный объект-запрос. Название ContextRole особенно неудачно, если сущность хранит прямые grants: оно обещает роль, но описывает иной предмет.

## API: явная проверка и удобный вызов

Публичное ядро лучше строить вокруг явного неизменяемого запроса и предсказуемого результата. Fluent API допустим как тонкая ergonomics-обёртка, только если он остаётся неизменяемым и не скрывает, откуда взялся subject и какая область действует.
```
$decision = $authorizer->decide( subject: $user, permission: 'posts.update', resource: $post, tenant: $tenant, ); if ($decision->isAllowed()) { // ... }
```
Удобная сокращённая проверка может возвращать bool, если название честно указывает на потерю деталей:
```
$authorizer->allows( subject: $user, permission: 'posts.update', resource: $post, );
```
Fluent-форма уместна для построения запроса, если каждый шаг возвращает новый объект и терминальный метод ясно обозначает вычисление:
```
$decision = $authorizer ->for($user) ->inTenant($tenant) ->on($post) ->decide('posts.update');
```
Не делайте fluent-объект изменяемым «текущим контекстом» на singleton-сервисе: это создаёт риск протекания состояния между запросами и усложняет отладку. Для диагностики предпочтителен Decision; для обычного условного ветвления — bool; для отказа с Laravel-исключением — отдельный явный метод вроде authorize(...). Laravel сам различает простой boolean-путь и подробный Response/inspect, что подтверждает полезность такого разделения.

## Значения, команды и контракт API

Используйте readonly value objects для Permission, Grant, Decision и запроса проверки там, где объект представляет уже определённое значение, а не изменяемую запись хранилища. Их поля должны иметь чёткую семантику; неизменяемость не должна превращать Eloquent-модель или агрегат с жизненным циклом в value object.
Запись права оформляйте как команду с явным побочным эффектом: например, grant(...) : GrantRecord или grant(...) : void, с выбором по тому, нужен ли вызывающему созданный идентификатор/запись. Не используйте builder, который выглядит как описание, но незаметно пишет в БД при вызове to(...), for(...) или деструкторе. Если нужен builder, пусть он сначала строит неизменяемую команду, а сохранение происходит только при явном execute().
Именованные параметры — часть публичной ergonomics, но и долговременный контракт: закрепите и документируйте стабильные имена (subject, permission, resource, tenant, panel), не переименовывайте их без причины и проверяйте совместимость интерфейсов и реализаций. Неизвестно, какой минимальный PHP поддерживает будущий AzGuard; поэтому readonly-классы требуют явного решения о минимуме PHP 8.2, а при более старой версии можно применять readonly-свойства или обычные value objects с закрытой мутацией.

## Открытые вопросы

До фиксации дизайна нужно решить: является ли Panel собственным измерением или только конфигурацией приложения; как складываются grants, роли и вычисляемые правила; поддерживаются ли guest subjects; что именно считается resource scope и как задаётся tenant; должна ли Decision содержать стабильный код причины отказа; какой PHP/Laravel-диапазон обязателен; и возвращает ли команда grant запись, идентификатор или только подтверждение. Эти решения — не факты о текущей реализации, а вопросы финального проектирования.
