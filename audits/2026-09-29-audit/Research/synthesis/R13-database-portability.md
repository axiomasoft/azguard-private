# R13 — PostgreSQL/MySQL/SQLite: portable identity

**Статус:** предварительный Perplexity synthesis, сохранён из этой сессии. Вопрос сформулирован на уровне области, без точных фрагментов текущего кода. Советы о локальном AzGuard использовать только после сверки с [репозиторием](../repository-inventory.json) и [первичными источниками](../primary-sources.md). Пересечения с другими темами смотрите в [карте исследования](../README.md).

## Исходный вопрос

Database identity portability authorization tables: PostgreSQL NULLS NOT DISTINCT unique indexes, SQLite expression indexes, MySQL functional/generated columns, MariaDB distinctions, collation case sensitivity, bigint/UUID/ULID/morph alias, custom connections, DDL implicit commits. Limit claims to exact tested versions. How to test permission uniqueness and upgrade collisions without normalizing table names solely for aesthetics?

## Ответ Perplexity

На 2026-09-29. Короткий вывод: не следует рассчитывать, что один и тот же UNIQUE-индекс на таблице разрешений даст одинаковую семантику во всех СУБД. Сначала нужно явно определить, какие строки считаются одной выдачей разрешения — включая NULL, регистр, тип и контекст субъекта — и проверять это на точных версиях серверов и схемах, которые библиотека заявляет как поддерживаемые. Ниже — документированные факты, затем архитектурные выводы и план тестирования; это не аудит частного репозитория.

## Что подтверждают источники

- PostgreSQL 18. Обычный уникальный индекс считает NULL отличным от других NULL, поэтому допускает несколько строк с одинаковыми остальными ключевыми полями и NULL в nullable-поле. NULLS NOT DISTINCT меняет поведение: такие значения NULL считаются равными. Для составного индекса нарушение возникает только при совпадении всех ключевых значений. (проверено 2026-09-29). Значит, замена обычного индекса на NULLS NOT DISTINCT — это смена правила идентичности, а не косметическое улучшение.
- SQLite. Выражения допустимы в CREATE INDEX, включая уникальные индексы; выражение должно быть детерминированным и обращаться только к столбцам индексируемой таблицы. Планировщик распознаёт выражение только когда запрос использует то же выражение, практически в той же записи. Индексы выражений поддерживаются начиная с SQLite 3.9.0; более старые версии не смогут использовать такую базу. (страница проверена 2026-09-29; минимальная версия прямо указана в документации). В отдельной документации SQLite обычный уникальный индекс допускает повторные NULL. .
- MySQL 8.4. Функциональные части индекса могут быть уникальными и реализуются как скрытые виртуальные generated columns; действуют ограничения generated columns. Уникальные индексы допускают несколько NULL. Семантика строк зависит от collation: в руководстве приведён пример, где сравнение с utf8mb4_0900_ai_ci нечувствительно к регистру, а utf8mb4_bin — чувствительно. . Документация MySQL также указывает, что DDL неявно завершает активную транзакцию; атомарный DDL не означает возможность откатить его вместе с транзакцией приложения. .
- MariaDB. Нельзя автоматически считать её эквивалентом MySQL. Документация описывает индексируемые VIRTUAL/PERSISTENT generated columns; MariaDB 11.8 отдельно отмечает поддержку оптимизатором распознавания выражения индексируемого виртуального столбца. , . Уникальные индексы допускают несколько NULL. . Эти источники не доказывают поддержку MariaDB каждой формы функционального индекса MySQL 8.4: её нужно проверять отдельно на точной версии MariaDB.

## Архитектурный вывод

Сначала сформулируйте ключ идентичности как правило домена, например: (permission, subject_type, subject_id, context) — с явным ответом, означает ли context = NULL «глобально», и может ли такая запись существовать в единственном экземпляре. Если NULL означает отдельное значение, обычный уникальный индекс, вероятно, не обеспечивает требуемую уникальность в PostgreSQL, MySQL, SQLite и MariaDB. Если требуется ровно одна такая строка, движок-специфичный индекс, выражение либо дополнительный явный маркер могут помочь, но это решения для проверки, не переносимая гарантия.
Не отождествляйте идентификаторы без проверки типов: BIGINT, UUID и ULID могут иметь разные представления, ограничения длины, сортировку и поведение при приведениях. Для polymorphic-ссылки subject_type тоже входит в идентичность: стабильный alias и полное имя класса — разные строки; collation, игнорирующая регистр, может их схлопнуть. Пользовательские DB connections влияют на то, где фактически выполняются миграции и тесты. Документация Laravel 13 предусматривает задание соединения для миграции и явный выбор соединения для Schema-операций. (страница проверена 2026-09-29).

## План проверок и открытые вопросы

- Зафиксировать матрицу с точными версиями СУБД, драйверов PDO, Laravel и схемой колонок. Документация сама по себе не подтверждает совместимость конкретного SQL с поддерживаемыми версиями библиотеки.
- На каждой СУБД создавать минимальную реальную таблицу разрешений и проверять: точный дубль; дубли с NULL по каждому nullable-полю; различие только в регистре/Unicode-нормализации alias и context; граничные значения bigint; UUID/ULID; одинаковый subject_id при разных subject_type; конкурирующие вставки.
- Тестировать не только вставки: проверить, что API чтения разрешений использует ту же семантику равенства и что предполагаемый индекс применяется, особенно для SQLite — выражение в запросе должно совпадать с выражением индекса.
- Для обновления со старой схемы сначала запускать read-only диагностику будущих конфликтов по целевому правилу равенства, включая collation и обработку NULL; сообщать строки и ключи конфликта, не исправлять и не удалять их автоматически. Затем проверять построение индекса на копии данных и отказ миграции при конфликте. Учитывать, что DDL может коммитить транзакцию отдельно.
- Не переименовывать таблицы ради единообразия. Обосновывать изменение имени только реальным дефектом или доказанной совместимостью; отдельно тестировать миграции как с существующими именами таблиц, так и с альтернативным префиксом/пользовательской схемой, если это поддерживается.
Неразрешённые вопросы для аудита: точный состав ключа и смысл NULL; collation и допустимая канонизация строк; перечень заявленных версий MariaDB/MySQL/SQLite/PostgreSQL; поведение существующих данных при переходе на выбранное правило; поддержка кастомных соединений во всех трёх пакетах; и требуется ли переносимость физического DDL или только одинаковая наблюдаемая семантика API.
