# R01 — Public API / SPI и границы Laravel-пакетов

**Статус:** предварительный Perplexity synthesis, сохранён из этой сессии. Вопрос сформулирован на уровне области, без точных фрагментов текущего кода. Советы о локальном AzGuard использовать только после сверки с [репозиторием](../repository-inventory.json) и [первичными источниками](../primary-sources.md). Пересечения с другими темами смотрите в [карте исследования](../README.md).

## Исходный вопрос

Design a pragmatic public API/SPI/internal policy for a PHP 8.3 Laravel 11/12/13 RBAC monorepo with core, optional context and Filament 5 packages. Compare same-release friend modules vs independently versioned extensions; PHPStan @api/@internal limitations, Deptrac and Roave BC. Are @spi/@experimental standard supported annotations or project conventions? Model customization versus internal Eloquent models. Give alternatives, migration risks and minimal useful contracts; avoid a wholesale DDD rewrite.

## Ответ Perplexity

Для такого монорепозитория разумнее разделить публичный API для пользователей, ограниченный SPI для расширений и внутреннюю реализацию — и закрепить границы контрактами и проверками, а не одной только документацией. Для трёх тесно связанных пакетов я бы по умолчанию выбрал синхронный выпуск; независимо версионировать стоит только те расширения, которым действительно нужна отдельная совместимость и самостоятельный жизненный цикл.

## Факты из официальных источников

Laravel. На дату исследования Laravel 13 требует PHP 8.3+, Laravel 12 поддерживает PHP 8.2–8.5, Laravel 11 — 8.2–8.4; официальная таблица также указывает даты окончания поддержки. Laravel рекомендует задавать ограничения зависимостей с учётом мажорных версий, поскольку они могут содержать несовместимые изменения. Поэтому поддержку Laravel 11/12/13 следует выразить и проверять в Composer-матрице каждого применимого пакета, а не выводить из факта, что PHP 8.3 удовлетворяет требованиям. — версия 13.x, дата проверки 2026-09-29; — версия 12.x, дата проверки 2026-09-29.
PHPStan и аннотации. PHPStan 2.1.13+ поддерживает @internal при включённом Bleeding Edge: он может сообщать об использовании помеченных символов вне верхнего namespace пакета. Это статическая проверка, а не ограничение PHP во время выполнения и не защита от потребителей, не запускающих анализатор. Документация PHPStan описывает @internal, но не задаёт аналогичный стандартный механизм для @api, @spi или @experimental. Их разумно трактовать как проектные соглашения, пока вы явно не выбрали инструмент и не настроили его поведение. — текущая документация; .
Архитектурные проверки и BC. Deptrac позволяет определить слои, разрешённые зависимости и проверять нарушения в CI. Roave BackwardCompatibilityCheck сравнивает API между версиями; автоматический выбор предыдущего релиза опирается на SemVer-теги и требует, чтобы CI получал теги. Это полезные проверки, но сами по себе они не определяют, какие символы вы считаете контрактом. — текущая документация; — README проекта, дата проверки 2026-09-29.
Filament 5. Официальная документация указывает PHP 8.2+, Laravel 11.28+ и Livewire 4+. Ресурсы работают с Eloquent-моделями, но есть и пути настройки модели или использования таблиц с данными из внешнего источника. , , — ветка документации 5.x, дата проверки 2026-09-29.

## Архитектурная рекомендация

Для core, context и Filament-пакета предпочтителен общий release train, особенно если context и UI зависят от внутренних деталей core. Практически это не требует монолитного Composer-пакета: оставьте три пакета, но координируйте версии, changelog и совместимую матрицу. Так ниже риск комбинации «новый core + старый адаптер», а BC-проверки проще интерпретировать.
Независимые версии оправданы, если пакеты имеют самостоятельных потребителей, редко требуют согласованных изменений и способны поддерживать диапазон версий core. Цена — больше комбинаций для CI, строгие ограничения Composer и необходимость описывать совместимость релизов. Если context и Filament пока являются официальными сопровождаемыми адаптерами, синхронные мажорные версии с допустимым диапазоном core обычно проще. Это вывод из описанной структуры, не установленный факт о репозитории.
Практичная граница: публичный контракт — небольшие интерфейсы и value objects для проверки разрешения, идентичности субъекта/ресурса, контекста и результата; SPI — точки подключения для resolver/adapter, отмеченные собственным соглашением и снабжённые контрактными тестами; Eloquent-модели, кеш-конверты, fencing и детали инвалидации — внутренние, если нет конкретной потребности пользователя их расширять. Существующие revision fence, generation и expiry envelopes следует считать инвариантами реализации: расширение не должно обходить или самостоятельно воспроизводить их.

## Модели и риски

Не открывайте наследование внутренних Eloquent-моделей как основной способ кастомизации без точного требования. Это связывает потребителя со схемой, отношениями, конструкторами и деталями Laravel. Предпочтительнее конфигурируемый класс модели только если реально нужны дополнительные поля/отношения; безопаснее — интерфейс/адаптер или фабрика, принимающая модели Eloquent и возвращающая минимальный контракт. Для Filament держать ресурс в отдельном пакете снижает загрязнение ядра зависимостью на UI. Риск модели-плагина — несовпадение схемы и ожиданий запросов; риск интерфейса — чрезмерно абстрактный контракт, который замедлит простую настройку.
@api, @spi, @experimental можно документировать, но считать работающими только при наличии проверок и политики снятия/изменения. Минимально полезная защита: PHPStan для границ @internal, Deptrac для зависимостей между core/context/Filament, Roave для опубликованных API и тесты совместимости пакетов в CI. Roave может выявить BC-изменение символа, но не докажет корректность кеш-инвариантов или семантики авторизации.

## Что пока неизвестно

Я не получал и не проверял частный репозиторий. Неизвестны текущие namespaces и Composer-ограничения, реальные точки расширения, набор экспортируемых моделей, версия PHPStan и наличие тегов релизов; поэтому нельзя утверждать, что описанные механизмы уже соблюдаются. Следующий этап аудита должен сопоставить публичные символы и фактические межпакетные зависимости с этими критериями, не начиная с перестройки в DDD.
