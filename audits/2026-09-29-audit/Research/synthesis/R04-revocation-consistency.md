# R04 — Отзыв прав и консистентность кэша

**Статус:** предварительный Perplexity synthesis, сохранён из этой сессии. Вопрос сформулирован на уровне области, без точных фрагментов текущего кода. Советы о локальном AzGuard использовать только после сверки с [репозиторием](../repository-inventory.json) и [первичными источниками](../primary-sources.md). Пересечения с другими темами смотрите в [карте исследования](../README.md).

## Исходный вопрос

Security-critical authorization cache: committed database revision updated atomically with grant mutations; Redis payload key includes revision; revision read from write connection each check; transaction bypass cache. Analyze revoke races, snapshot isolation, in-flight checks, replica lag, Redis outage and fail-closed semantics. Compare global vs per-subject/panel revision, contention. What guarantee is realistic? Do NOT claim linearizability merely from a revision key.

## Ответ Perplexity

Коротко: ревизия в ключе Redis — эффективный механизм отделения старых кеш-записей от новых, но сама по себе не даёт линейризуемой авторизации. При чтении актуальной ревизии с primary БД и атомарном увеличении ревизии вместе с изменениями прав можно обещать более узкую гарантию: проверки, начавшиеся после подтверждённого commit отзыва и читающие актуальное состояние primary, не должны принимать решение по кешу прежней ревизии. Уже выполняющиеся проверки могут завершиться по старому состоянию.
Ниже — исследовательская оценка по заданному описанию системы, не аудит репозитория. Версии источников: Laravel 12.x, PostgreSQL 18, MySQL 8.4; ссылки ведут на официальную документацию.

## Документированные факты

- Laravel поддерживает раздельные read/write-соединения. Опция sticky направляет последующие чтения на write-соединение после записи в рамках текущего request cycle; это ограниченная гарантия чтения после собственной записи, а не общий протокол свежести для всех запросов. Транзакции Laravel объединяют операции и откатываются при исключении из closure. — официальная документация; при публикации страницы дата версии явно не указана.
- PostgreSQL READ COMMITTED получает снимок на начало каждого statement; REPEATABLE READ использует снимок, установленный первым запросом транзакции, и не видит чужие commit, сделанные позже. — официальная документация, версия 18.
- MySQL InnoDB по умолчанию работает в REPEATABLE READ; обычные consistent reads внутри транзакции используют снимок, установленный первым чтением. Это тоже может сохранить старый взгляд на ревизию и grants до конца транзакции. — официальная документация, версия 8.4.

## Гонки отзыва и снимки

Пусть проверка A прочитала ревизию r и нашла кешированный allow; затем отзыв прав коммитит новую ревизию r+1. Проверка, которая после этого прочитает r+1 с primary, построит другой ключ и не должна использовать payload для r. Однако A уже могла прочитать r; между чтением ревизии и возвратом ответа отзыв может завершиться. Ключ ревизии не отзывает уже выданное решение и не останавливает запрос, который продолжает работу со старой ревизией.
Архитектурный вывод: реалистична гарантия «после commit отзыва новые проверки, начавшиеся после commit и выполнившие чтение ревизии с primary, не используют кеш старой ревизии» — при условии, что все пути изменения grant атомарно обновляют ревизию в той же транзакции. Это не эквивалентно «ни один запрос не сможет действовать с разрешением после commit». Для такой более сильной семантики потребовалась бы координация с выполняемыми операциями, а не только versioned cache key.
Есть важная граница: обход кеша внутри транзакции полезен, но сам по себе не гарантирует, что обход читает актуальный снимок. Например, транзакция, начавшаяся до commit отзыва при REPEATABLE READ, может прочитать старые grants и ревизию из одного и того же старого снимка. Результат внутренне согласован, но уже не актуален относительно момента проверки. Как именно это ведёт себя в конкретной СУБД и конфигурации, нужно подтвердить тестами на поддерживаемой матрице.

## Реплики, отказ Redis и гранулярность

Чтение revision с read replica подрывает stated guarantee: lagging replica может вернуть старое r, после чего приложение легально найдёт старый ключ и разрешит доступ. Для проверки отзыва revision нужно читать с write connection/primary независимо от sticky; опция Laravel sticky не заменяет это требование.
При недоступности Redis безопасная политика для критической авторизации — не превращать ошибку cache в allow. Можно попытаться вычислить решение непосредственно из primary БД; если и достоверное чтение БД недоступно, fail closed означает отказ/ошибку, а не разрешение. Это выбор продукта: он ухудшает доступность при сбоях, зато не маскирует отказ инфраструктуры потенциально устаревшим разрешением.
Глобальная revision проста и инвалидирует всё, но каждый grant mutation пишет одну горячую строку: конкурирующие изменения сериализуются на ней. Revision на subject/panel уменьшает конкуренцию и объём логической инвалидации, но корректность зависит от полноты области: изменение глобальной роли, наследуемого permission или контекста должно инвалидировать каждую затронутую область. Это вывод из модели ключей, а не гарантия Laravel или БД.

## Нерешённые вопросы и вывод

Неизвестны СУБД/изоляция в production, конкретная граница транзакции и источник revision при всех путях записи, использование read replicas, семантика «проверка началась», а также перечень глобальных и наследуемых grants. Эти детали нельзя подтвердить без конфигурации и тестов.
Реалистичное обещание: отсутствие использования старого кеш-ключа при новой проверке, если она читает committed revision с primary после commit отзыва; плюс обход кеша внутри транзакций и отказ в разрешении при невозможности проверить актуальные данные. Не обещать линейризуемость, мгновенную остановку in-flight запросов или защиту от чтения из устаревшего snapshot.
