# R20 — Порядок источников и restriction layers

**Статус:** предварительный Perplexity synthesis, сохранён из этой сессии. Вопрос сформулирован на уровне области, без точных фрагментов текущего кода. Советы о локальном AzGuard использовать только после сверки с [репозиторием](../repository-inventory.json) и [первичными источниками](../primary-sources.md). Пересечения с другими темами смотрите в [карте исследования](../README.md).

## Исходный вопрос

Authorization extension SPI for grant sources and restricting permission layers: union of allows, global wildcard superadmin early return bypasses tenant restrictions, context only vs global plus context; deny-overrides versus additive grants. Single layer binding collision with multiple plugins, deterministic ordering and topology checks. Data-dependent external sources with stable cache discriminators and volatility contracts. Minimal alternatives to a generic pipeline framework.

## Документированные факты

- Laravel Gate::before запускается перед обычной проверкой; его ненулевой результат становится результатом проверки. Поэтому глобальный true — не просто дополнительный grant, а короткое замыкание, способное обойти последующие проверки, включая tenant-ограничения, если библиотека помещает их позже в вычисление. Laravel документирует такое поведение как способ выдать пользователю все abilities.
- В Laravel policies можно получать дополнительные аргументы и возвращать Response с причиной отказа; это позволяет представить контекстные решения и диагностируемые отказы, но не определяет семантику объединения независимых источников.
- Composer рекомендует PSR-4, объединяет mappings при install/update, а provide предназначен, в частности, для интерфейсных виртуальных пакетов. Это может поддержать распределение SPI-контракта и адаптеров по трём пакетам, но само по себе не регистрирует плагины и не задаёт порядок их исполнения.
- PSR-16 формулирует TTL как время, по истечении которого элемент считается устаревшим. Это не является гарантией, что внешнее изменение прав будет немедленно отражено до истечения TTL.

## Архитектурный вывод

Для расширения лучше разделить источник grants и ограничивающий слой как разные роли SPI. Источник должен сообщать, что он знает про конкретную проверку; слой — может ли запрос вообще пройти неизменяемые границы вроде tenant, контекста и состояния объекта. Объединение «любой источник разрешил → allow» безопасно только после обязательных ограничений. Иначе глобальный wildcard или plugin grant станет аналогом раннего Gate::before(true) и обойдёт tenant fence.
Рекомендуемая логическая модель: сначала обязательные ограничения, затем deny-override, затем объединение allow-grants. Для каждого источника различать abstain, allow, deny: отсутствие решения не должно трактоваться как deny, а «не найдено» — как разрешение. Явный deny от любого доверенного источника должен блокировать additive allow, если продукт явно не выбирает модель «только additive». При этом superadmin лучше моделировать как отдельную привилегию, которая всё равно проходит tenant/context restrictions, а не как *-grant с ранним возвратом.
Для области действия стоит зафиксировать один контракт: проверяются глобальный слой плюс слой активного контекста; либо только слой контекста, если глобальные grants сознательно исключены. Не оставлять это выбором порядка плагинов. В частности, «глобальное allow» не должно расширять полномочия через tenant, если tenant restriction объявлен обязательным инвариантом.
Конфликт единственной binding точки для нескольких плагинов — риск потери регистрации или неявной зависимости от порядка boot. Минимум: registry собирает все реализации, проверяет уникальные стабильные ID, сортирует по явному приоритету с tie-break по ID и валидирует ссылки зависимостей/конфликты до первого запроса. Ошибочная топология должна завершать bootstrap с понятной ошибкой, а не менять доступ молча. Порядок не должен влиять на итог при выбранной семантике; тест на перестановку регистрации проверит это свойство.
Внешний, data-dependent источник может кэшироваться безопасно лишь при явном контракте: стабильный discriminator входит в cache key (например, provider ID + версия политики/снимка + релевантный субъект и контекст); источник декларирует волатильность или максимальный срок свежести; а invalidation/revision fence и expiry envelope ограничивают устаревание. Источник без устойчивого discriminator или понятной границы свежести следует по умолчанию считать некэшируемым. Это вывод из заявленной схемы и общей семантики TTL, не гарантия PSR-16.

## Минимальная альтернатива pipeline

Не вводить универсальные этапы, middleware-подобные преобразования и динамический граф. Достаточны два небольших интерфейса (restriction и grant source), неизменяемый request object, трёхсоставной результат abstain/allow/deny, registry с детерминированным порядком и стартовыми topology checks. Позже можно добавить capabilities метаданных источника для cacheability/volatility, не превращая SPI в generic workflow framework.

## Нерешённые вопросы

Нужно отдельно решить: deny-overrides применяется к любому plugin или только к доверенным; допускается ли tenant-scoped superadmin; как именно определяется глобальный scope относительно контекста; какое поведение при недоступности удалённого источника — fail closed, ошибка или ограниченный stale-cache. Источники не отвечают на эти продуктовые решения. Перед фиксацией контракта также потребуется сверить реальные binding points и пакетные зависимости в репозитории, которых здесь не проверяли.
