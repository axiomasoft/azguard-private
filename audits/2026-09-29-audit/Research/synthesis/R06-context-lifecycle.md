# R06 — Контекст, scoped DI, Octane и fibers

**Статус:** предварительный Perplexity synthesis, сохранён из этой сессии. Вопрос сформулирован на уровне области, без точных фрагментов текущего кода. Советы о локальном AzGuard использовать только после сверки с [репозиторием](../repository-inventory.json) и [первичными источниками](../primary-sources.md). Пересечения с другими темами смотрите в [карте исследования](../README.md).

## Исходный вопрос

Laravel scoped service bindings vs Octane/Swoole concurrent fibers/coroutines, queue workers and synchronous nested jobs. Authorization context run(context, callback) restores with finally; nested scopes and coroutine-local state. Distinguish lifecycle isolation from concurrent isolation. Explicit immutable authorization input versus ambient current panel/context, risks and realistic supported runtime contract.

## Ответ Perplexity

Короткий вывод. Laravel scoped решает сброс экземпляров между жизненными циклами запроса или задания, но сам по себе не гарантирует изоляцию двух одновременно выполняющихся контекстов внутри одного жизненного цикла. Для библиотеки авторизации безопаснее считать контекст явным входом операции; ambient-контекст оставить удобством для ограниченного, документированного режима исполнения, а не обещать универсальную поддержку корутин.

## Документированные факты

- В официальной документации Laravel 11 и 13 scoped описан как экземпляр, переиспользуемый в пределах одного request/job lifecycle и сбрасываемый при новом lifecycle, включая обработку запроса Octane-worker’ом или задания queue-worker’ом. Это контракт по жизненному циклу, не контракт по конкурентному исполнению внутри него. · Документация актуальна на дату исследования — 2026-09-29; это движущиеся URL документации, а не закреплённые архивные снимки.
- Octane оставляет приложение в памяти и повторно использует его между запросами. Laravel предупреждает о глобальном состоянии и о риске устаревших зависимостей, захваченных долгоживущими объектами. Документация отдельно описывает Octane::concurrently() для Swoole: задачи выполняются task workers в отдельных процессах от входящего запроса. Это не основание считать произвольное состояние родительского запроса автоматически доступным или синхронизированным в дочернем процессе.
- Queue worker — долгоживущий процесс, обрабатывающий задания. dispatchSync выполняет задание сразу в текущем процессе; поэтому вложенный синхронный job не является новым изолированным процессом. Laravel описывает scoped lifecycle для job, но документация не обещает, что синхронный вложенный job создаст независимую область авторизационного состояния поверх вызывающего кода. ·

## Архитектурная оценка

Предоставленный контекст говорит, что библиотека уже имеет run(context, callback) с восстановлением через finally, вложенные scopes, публичный PermissionLayer, discriminator контекста, revision fence и кэш-оболочки с generation/expiry. Это описание пользователя; репозиторий не исследовался, и выводы ниже не являются утверждениями о его реализации.
try/finally — необходимый инвариант для исключений и обычного вложенного вызова: внутренний scope должен восстановить предыдущий контекст, а внешний — исходное отсутствие контекста. Но это lifecycle safety, не concurrency safety. Если ambient state хранится в одном поле scoped-объекта, статическом свойстве или обычном stack на объекте, две корутины в одном worker могут чередовать выполнение: A устанавливает контекст A, уступает управление; B устанавливает B и завершается; A возобновляется и читает B или уже восстановленное значение. Корректный finally не устраняет такое пересечение.
Нужен ли coroutine-local storage, зависит от фактического runtime и пути исполнения. Для обычного синхронного PHP и вложенных вызовов stack может быть достаточен. При кооперативных корутинах требуется локальное состояние на coroutine/fiber либо отказ от ambient API в корутинном пути. Нельзя выводить наличие нужного механизма только из «Swoole»: Octane документирует отдельные task-процессы, но не формулирует универсальную гарантию изоляции для произвольных PHP Fiber/корутин и объектов контейнера.

## Рекомендуемый контракт

- PermissionLayer принимает неизменяемый authorization input явно; ключевые проверки не должны неявно зависеть от «текущей панели/контекста».
- run(context, callback) допустим как scoped convenience для синхронного, неразделяемого исполнения; вложенность поддерживается по стеку, восстановление — при исключении.
- Не передавать ambient-контекст через очередь автоматически. Для асинхронного job передавать сериализуемые идентификаторы/значения контекста явно и повторно валидировать их при выполнении.
- Пока coroutine-local реализация и тесты не подтверждены, документировать, что параллельные корутины с разными authorization contexts в одном PHP worker не поддерживаются. Для Swoole task workers трактовать выполнение как отдельную границу процесса и требовать явного входа.
- Отдельно проверить сценарии: вложенный run, исключение во внутреннем callback, dispatchSync под активным scope, два чередующихся coroutine/fiber и повторное использование Octane/queue worker.

## Неурегулированные вопросы

Официальные документы не определяют для этой библиотеки поведение контекста в произвольном coroutine scheduler, не устанавливают перенос ambient state в Swoole task process и не уточняют, создаёт ли конкретная версия Laravel при синхронной вложенной диспетчеризации отдельную область scope. Это требует проверки поддерживаемых версий Laravel 11/12/13, конкретных адаптеров runtime и интеграционных тестов; до этого безопасный публичный контракт — lifecycle isolation без обещания concurrent isolation.
