# R15 — Mutation score и property-based testing

**Статус:** предварительный Perplexity synthesis, сохранён из этой сессии. Вопрос сформулирован на уровне области, без точных фрагментов текущего кода. Советы о локальном AzGuard использовать только после сверки с [репозиторием](../repository-inventory.json) и [первичными источниками](../primary-sources.md). Пересечения с другими темами смотрите в [карте исследования](../README.md).

## Исходный вопрос

Pest 4 native mutation testing ignoreMutations whitelist/exclusions interpretation, denominator, changed-file scope, surviving and uncovered mutants, flaky concurrency tests. Add property/metamorphic tests for wildcard grammar, merge strategies, expiry and revision race state machine. Distinguish line/type/mutation coverage from security proof. Verify official APIs; alternatives without new runtime dependencies.

## Ответ Perplexity

## Краткий вывод

Для этой библиотеки Pest 4 подходит как способ проверять, замечают ли тесты конкретные семантические изменения в коде, но его mutation score нельзя трактовать как меру безопасности или доказательство корректности авторизации. В официальной документации подтверждены строковый @pest-mutate-ignore, исключение классов и ограничение области через covers()/mutates(); публичного API ignoreMutations() или whitelist-списка мутантов в проверенных официальных материалах я не нашёл. Это не доказывает, что такого API нет в конкретном установленном релизе: его нужно сверить с зафиксированной версией Pest/plugin и исходным кодом пакета.

## Факты из официальной документации

Документация Pest описывает @pest-mutate-ignore как способ пропустить генерацию мутаций для строки. Для неисполняемого кода, который Pest всё равно помечает UNCOVERED, директива может размещаться в PHPDoc перед свойством. CLI --ignore исключает класс или namespace; --class задаёт целевые классы. covers() и mutates() одинаково ограничивают mutation testing, но covers() дополнительно меняет отчёт code coverage. --everything обходит ограничение covers(); --covered-only ограничивает генерацию строками, покрытыми тестами.
Официальное описание различает пойманные (tested) и не пойманные (untested) мутации. Также оно отдельно сообщает о UNCOVERED для строк, не исполняемых тестами. Поэтому не следует считать все эти категории взаимозаменяемыми. В рассмотренных документах не определены достаточно точно детали знаменателя score при исключениях, в частности — точная формула с учётом uncovered, игнорируемых строк и нулевого числа мутаций. Документация подтверждает существование --min и отдельного --ignore-min-score-on-zero-mutations, но этого недостаточно, чтобы без проверки версии утверждать детали подсчёта в вашем запуске.
Документация перечисляет область через классы и декларации тестов, но не подтверждает, что Pest по умолчанию ограничивает mutation testing файлами, изменёнными в Git. Не проектируйте CI-политику вокруг такой гипотезы: используйте явный --class/mutates() либо проверяйте фактическое поведение закреплённой версии.

## Архитектурная интерпретация для whitelist

Для трёх Composer-пакетов whitelist разумно понимать как управляемый перечень обоснованных исключений, а не как критерий успешного тестирования. Если встроенный API не предоставляет список конкретных мутантов, поддерживаемый вариант — локальная @pest-mutate-ignore для действительно эквивалентных или бессмысленных строк и узкий --ignore для сознательно исключённых классов. Вести whitelist отдельно можно в документации/CI-конфигурации, но это будет вашей политикой, а не гарантией Pest.
При аудите фиксируйте полный набор целей и версий, запускайте отдельные результаты по пакетам и проверяйте, что исключения не скрывают условные ветви авторизации. В частности, не исключайте широкие области, содержащие публичный PermissionLayer, discriminator контекста, revision fence или логику expiry: именно там цена незамеченного выживающего мутанта может быть высокой.

## Предлагаемые свойства тестов

- Wildcard grammar: генеративно проверять допустимые и недопустимые шаблоны, границы сегментов, совпадения и непересечения. Метаморфное свойство: добавление несвязанного permission не должно менять решение для исходного запроса; шаблон не должен совпадать с дополнительным сегментом, если грамматика этого не разрешает.
- Merge strategies: для одинаковых входов результат детерминирован; порядок слияния проверять отдельно — коммутативность/ассоциативность утверждать только для стратегий, где это часть контракта. Добавление пустого набора должно быть нейтральным, если так определено поведение.
- Expiry envelopes: до срока результат действителен, после истечения — недействителен; проверять граничный момент, часовые значения и некорректный envelope, используя контролируемые часы, а не sleep().
- Revision race state machine: моделировать чтение ревизии, получение значения из cache, смену ревизии и повторную проверку. Инвариант: результат, вычисленный для устаревшей ревизии, не должен выдаваться как действующий. Проверять перестановки событий и повторные попытки, не полагаясь на тайминг потоков.
Это рекомендации для будущего дизайна тестов, а не утверждения о существующей реализации.

## Покрытие, безопасность и неизвестное

Line coverage показывает выполнение строк; type coverage — соблюдение выбранных проверок типов; mutation testing — обнаружение выбранных изменений. Ни один из этих показателей не доказывает отсутствие обхода авторизации, корректность всех сочетаний ролей/контекста или безопасность конкурентного сценария.
Флаки-тесты особенно опасны при параллельном mutation testing: случайный сбой может ошибочно выглядеть как «убитый» мутант. Сначала добейтесь повторяемости race-тестов с управляемыми часами, барьерами/синхронизацией и изолированным состоянием; сравните последовательный и --parallel прогоны, а нестабильные тесты не используйте как основание для score-gate. Документация Pest рекомендует параллельный режим ради скорости, но не обещает, что он безопасен для тестов с общим состоянием.
Не разрешено официальными источниками, проверенными здесь: точное поведение ignoreMutations() в вашей целевой версии, формула знаменателя с исключениями и автоматическая Git changed-file область. Перед решением нужно сверить исходный код и тесты именно установленного Pest/plugin; это исследование не предполагает доступа к вашему приватному репозиторию.
