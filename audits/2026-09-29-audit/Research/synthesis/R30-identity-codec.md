# R30 — Typed identity и инъективная сериализация

**Статус:** предварительный Perplexity synthesis, сохранён из этой сессии. Вопрос сформулирован на уровне области, без точных фрагментов текущего кода. Советы о локальном AzGuard использовать только после сверки с [репозиторием](../repository-inventory.json) и [первичными источниками](../primary-sources.md). Пересечения с другими темами смотрите в [карте исследования](../README.md).

## Исходный вопрос

Authorization cache discriminator collision: (contextType='workspace:a', contextId=7) and (contextType='workspace', contextId='a:7') both stringify to ctx:workspace:a:7; hashing that string cannot fix it. Propose ideal typed SubjectId/ContextRef/PanelId/PermissionKey identity codec, tuple serialization before hashing, namespace/version separation, int7 versus string'7', model DB normalization, UUID/ULID/morph aliases, multi-database identity and strategy/catalog generation. What canonicalization is a product choice? State concrete properties for tests; no copied code required.

## Ответ Perplexity

Дата исследования: 2026-09-29. Ниже — предложение для чистого редизайна AzGuard, а не описание существующего кода: у меня нет доступа к приватному репозиторию или реализации. Исходный пример уже доказывает важное: конкатенация полей с разделителями не является однозначным кодированием, поэтому хеширование результата не устраняет коллизию.

## Проверенные факты

- Кортежи (contextType='workspace:a', contextId=7) и (contextType='workspace', contextId='a:7') превращаются в одну строку ctx:workspace:a:7. Хеш-функция детерминированно выдаст для одинакового входа одинаковый выход: она не может восстановить границы полей, потерянные при сериализации.
- PSR-16 требует поддержки ключей длиной до 64 символов из A-Z, a-z, цифр, _ и .; ряд символов, включая :, зарезервирован. Следовательно, ключи кэша следует формировать с учётом минимально совместимого набора символов, а не полагаться на произвольные разделители.[Источник: ]
- Eloquent по умолчанию сохраняет полное имя класса для morph type, но позволяет использовать morph map и aliases. В миграциях Laravel тип morph-ID зависит от типа ключа модели: integer, UUID или ULID.[Источник: ] [Источник: ]
- RFC 8785 задаёт канонизацию JSON, но числа ограничены представлением IEEE 754; для больших целых рекомендуется строковое представление. Это делает RFC полезным ориентиром для детерминированного формата, но не готовым кодеком всех PHP-идентификаторов без дополнительного типового контракта.[Источник: ]

## Предложение: typed identity

Ввести отдельные неизменяемые value objects: SubjectId, ContextRef, PanelId, PermissionKey. Пусть кодек единолично преобразует их в каноническое представление для сравнения и кэширования. Компоненты должны быть типизированы: например, ContextRef включает тип контекста и идентификатор; при необходимости — пространство приложения/тенанта и database connection identity. PermissionKey должен задавать отдельные поля вроде домена, ресурса и действия, если продуктовая модель AzGuard их различает, а не скрыто кодировать их в строке.
Порядок обработки: сначала построить типизированный кортеж, затем сериализовать его однозначно, затем хешировать сериализацию для компактного ключа. Например, логическая структура кортежа могла бы содержать версию кодека, тип сущности, поля идентичности и их типы. Для байтовой кодировки можно выбрать length-prefix или другой формат с однозначным декодированием; конкретный формат — продуктовый выбор. Важно, чтобы хеш входных данных считался от всего кортежа, а не от прежней неоднозначной строки.
Идентификаторы должны сохранять различие int(7) и string('7'), если адаптер явно не нормализовал их в один доменный тип. Аналогично, int(7) и string('7') — разные значения по умолчанию в предложении; объединять их можно только осознанным правилом canonicalization. Если целые могут выходить за безопасный диапазон IEEE 754, кодек не должен пропускать их через float или JSON-number путь, теряя точность.

## Предложение: границы идентичности

Eloquent-адаптер должен получать модельную идентичность из явных метаданных: устойчивого типа модели или alias, значения primary key и, где это влияет на уникальность, connection/database scope. Не полагаться только на PHP FQCN: morph map позволяет отвязать хранимый morph type от имени класса. Но сам alias — тоже конфигурационный идентификатор: смена его значения или назначения должна рассматриваться как изменение схемы идентичности и кэша. UUID и ULID следует хранить как строковые типизированные значения, не смешивая их с числовыми ключами; Laravel документирует оба типа ключей и соответствующие morph-колонки.[Источник: ] [Источник: ]
Для кэш-ключа предлагается независимый namespace AzGuard и версия формата, например логические компоненты library namespace, codec version, strategy/catalog generation, затем хеш сериализованного tuple. Реальная строка должна соответствовать переносимому набору символов PSR-16. strategy/catalog generation нужен, чтобы изменение политики авторизации или каталога разрешений не позволяло выдавать устаревшее решение из прежней конфигурации. Это не заменяет инвалидацию при изменении данных: политика, зависимости и срок жизни кэша требуют отдельного решения.

## Проверяемые свойства

- Указанные два контекста дают разные канонические байтовые представления и разные ключи.
- Перестановка полей или изменение любого значения идентичности меняет каноническую запись; одинаковый кортеж всегда даёт одинаковую запись.
- int(7) и string('7') различаются до явно настроенной нормализации; UUID/ULID и числовой ID не смешиваются.
- Разные типы субъектов с одним ID не совпадают; одноимённые модели в разных database scopes различаются, если scope объявлен частью идентичности.
- Изменение версии кодека, morph alias mapping или поколения стратегии изменяет namespace/version-компонент ключа.
- Сгенерированные ключи проходят PSR-16 ограничения минимальной переносимости и не превышают выбранную реализацией длину.
- Кодек не теряет точность на предельных целых, не зависит от порядка свойств объектов и отвергает недопустимые идентификаторы вместо молчаливого приведения.

## Нерешённые продуктовые вопросы

Выбор canonicalization нельзя вывести из Laravel или PSR. Нужно утвердить: считаются ли 7 и '7' одной идентичностью; нормализуются ли регистр, Unicode и формат UUID; включаются ли connection, tenant и database в идентичность; какой источник истины для morph aliases и как версионировать их изменения; какие поля входят в PermissionKey; что именно меняет strategy/catalog generation и как инвалидируются записи при обновлении политик. До этих решений разумный безопасный дефолт — не объединять потенциально разные значения и требовать явной нормализации на границе адаптера.
