# AzGuard 1.0 — целевая архитектура (проработка Opus)

Дата: **2026-09-29**. Основание: [исходный аудит](../../2026-09-29-audit.md) (Perplexity) и
[исследовательский пакет Codex](../README.md). Код прочитан на `50fe4af` (прикладной код = `253cbf4`).
Инженерные правила согласованы с проработкой Vaulter (`vaulter/audits/2026-09-29-stable-audit/opus/`, `a572121`).

Это **целевая архитектура** для перевода в исполняемый план: понятия, имена, API, схема данных, смысл решений,
порядок работ и критерии готовности. Оспорить решение можно через [вопросы владельцу](15-owner-questions.md).

**Начните с [00-overview.md](00-overview.md).** Там простыми словами описано, как устроен AzGuard: панели как

## Главное — коротко

1. **Панель — конструктор прав** для части приложения: кабинет, кабинет продавца, админка, API, модуль. В панель
   подключают нужные механики: права всем, роли из кода, автоматические роли, Laravel Policy и Gate, роли и права в
   БД (как в Spatie), связи сущностей, свои источники. Механики сочетаются и меняются без изменения кода проверок.
2. **Проверки — как в Spatie:** `$user->hasPermissionTo('orders.view', on: $order)`, `$user->assignRole('editor',
   on: $project)`. Панель по умолчанию не указывают; другая — `$user->inPanel('admin')` или `admin:orders.view`.
3. **Одно правило выбора панели** для всех входов: явная → панель маршрута → по умолчанию → понятная ошибка. Сейчас
   правил четыре, и часть проверок отвечает не про ту панель.
4. **Права бывают у любой модели:** пользователь, проект, команда. У одной модели несколько панелей; все её права
   собираются в один набор, разделённый по панелям.
5. **Суперадмин** — субъект, которому в панели разрешено всё; правило задаётся на панели (или сразу для всех).
6. **Кто может редактировать права — решает приложение.** AzGuard не моделирует администраторов. Он даёт **схему
   панели**, по которой Filament и любой свой интерфейс строят редакторы.
7. **Хуки** — вмешаться без правки AzGuard: переопределить решение, запретить, дополнить или отменить изменение,
   отреагировать. Подтверждения и правило «не больше своего» — рецепты на хуках.
8. **Надёжность:** ошибка на любом шаге = отказ; изменение — одна транзакция с новой версией прав панели; события
   после сохранения; кэш не отдаёт отозванное право; повторная проверка — 0 запросов.
9. **Хранилища и свои поля:** общие таблицы по умолчанию или свои на панель; свои модели с полями (колонки или
   `meta`), поля проверяются и попадают в формы.
10. **Без совместимости с 0.3:** пакет строится сразу правильно; найденные дефекты становятся регрессионными тестами.
    Пакет `axiomasoft/azguard`, выпуски `1.0.0-beta` → `1.0.0`.

## Что изменилось по проходам

- **Второй проход** (по первому отзыву): панели вернулись как главное понятие (отказ от Realm), появились плагины,
  пайплайны, хранилища и свои поля, модули, контракт интеграций; предметные слова AzGuard отделены от Vaulter.
- **Третий проход** (по ответам на вопросы):
  - панель стала **конструктором механик**; политики и роли-классы вернулись как основа продукта (D52–D53);
  - трейт модели снова **проверяет и меняет** права, с именами методов Spatie; панель по умолчанию; права у любой
    модели (D10–D11);
  - **схема панели** для интерфейсов и **хуки** (D54–D55);
  - убраны делегирование, мета-права, `administeredBy`, подтверждения и глобальный суперадмин из ядра (D19, D23);
  - убраны патч 0.3, миграция данных, нормализатор старого конфига (D01);
  - имена пакетов — `axiomasoft/*`; идея моста Vaulter описана для отдельной задачи Vaulter (10 §9).

Находки N01–N24 и probes не изменились: это факты о текущем коде.

## Отличия от предыдущих аудитов

- **От аудита Perplexity:** не размечаю 150 классов тегами (граница API — namespace + манифест); контексты
  становятся частью ядра, а не отдельным plugin-API; префикс `azg_` беру, но главное — меняю саму схему назначений;
  исправляю факты, которые Codex уже опроверг.
- **От Codex:** принимаю рамку «смысл раньше раскладки» и почти все C-находки, довожу их до решений и имён. Выбираю
  вариант B внутри одного дистрибутива, без отдельного порта хранилища в 1.0. C01 довожу до межзапросной утечки (P07).

## Границы проработки

- Прочитаны все исходники трёх пакетов, миграции, конфиги, стабы, выборочно тесты и документация; мост Vaulter и
  решения Vaulter — для согласования.
- **Запускались:** существующий набор тестов (871 зелёный, SQLite) и 19 probes (все воспроизводят дефекты), см.
  [evidence](evidence/README.md). PHPStan и Rector не запускались (их загрузка закрыта политикой egress окружения).
- **Не запускались:** PostgreSQL/MySQL, реплики, Redis, Octane, конкурентные сценарии, Filament-UI в браузере. Для
  них есть сценарии в [14](14-verification.md).
- Код пакетов и Vaulter **не менялся**; probes лежат в `evidence/`, а не в `tests/`.

## Как превратить в план

1. Создать план по протоколу проекта (`plans/ACTIVE.md`). Фазы и пункты взять из [13-workstreams.md](13-workstreams.md)
   без перенумерации.
2. В `Execution Rules` перенести правила [13 §0](13-workstreams.md#0-правила-исполнения-переносятся-в-execution-rules-плана),
   в `Decision Log` — ссылки на D01–D55 (не копировать тексты).
3. Probes — регрессионные требования: каждый переписывается на новый API с обратным ожиданием в своём пункте.
4. Пункты с маршрутизацией opus не отдавать младшим моделям без спецификации в `findings/`.
5. Идею моста и заметки для Vaulter ([10 §9–§10](10-integrations.md#9-идея-моста-vaulter--azguard)) передать
   отдельной задачей в план Vaulter (пункт P8.6).
