# AzGuard 1.0 — целевая архитектура (проработка Opus)

Дата: **2026-09-29**. Основание: [исходный аудит](../../2026-09-29-audit.md) (Perplexity) и
[исследовательский пакет Codex](../README.md). Код прочитан на `50fe4af` (прикладной код = `253cbf4`).
Инженерные правила согласованы с проработкой Vaulter (`vaulter/audits/2026-09-29-stable-audit/opus/`, `a572121`).

Это **целевая архитектура** для перевода в исполняемый план: понятия, имена, API, схема данных, смысл решений,
порядок работ и критерии готовности. Решения можно оспорить через [вопросы владельцу](15-owner-questions.md).

## Главное — коротко

1. **Сначала безопасность (T0-патч 0.3.N).** Сейчас роль со звёздочкой в одной панели даёт права суперадмина во всех
   (N01). Админка позволяет записать в роль произвольный класс и выдать себе любые права (N02). Gate игнорирует
   настроенную логику проверки (N03). «Изоляция» по контексту открыта в очередях и ломается на двух назначениях
   (N04). Разные контексты могут совпасть в кэше (P07). Всё воспроизведено probes.
2. **Панели остаются сердцем AzGuard.** В одном приложении несколько независимых панелей: админка, сайт, API,
   модули. У каждой свои субъекты, права, роли, контексты, настройки, хранилище, модели и плагины.
3. **Ключ права знает свою панель** (`admin.orders.refund`). Угадывание панели по четырём разным правилам исчезает;
   вместе с ним уходит поломка моста Vaulter (N05, N09).
4. **Плагины.** Всё, что не ядро, подключается к панели плагином, включая встроенные возможности (роли, прямые права,
   контексты, суперадмин, аудит). Встроенные плагины пишутся тем же способом, что и сторонние. Это доказывает, что
   разъёмов достаточно.
5. **Два пайплайна с понятными правилами.** Проверка: подготовка → суперадмин → сбор прав → ограничения →
   наблюдение. Правила добавить могут только источники, ограничения могут только запретить, а ошибка означает отказ.
   Изменение: полномочия → проверка → перехват (например, подтверждение) → запись → журнал → уведомления.
6. **Хранилища и свои поля.** Панель хранит данные в общих таблицах или в своих. Модели можно расширить своими
   полями, эти поля проверяются при выдаче и могут участвовать в решении.
7. **Модули** дополняют чужую панель (`configurePanel` + `keyPrefix`) или регистрируют свою.
8. **Изменения прав — только через менеджер доступа панели** с указанием, кто действует. Нельзя выдать больше, чем
   есть у тебя. Запись, новая версия состояния и журнал — в одной транзакции. События — после commit.
9. **Честная консистентность**: чтения с primary, версия состояния на панель, дословная гарантия отзыва; повторная
   проверка — 0 запросов.
10. **Интеграции.** Vaulter и будущие пакеты опираются на небольшой стабильный контракт. Мост к пакету пишет сам
    пакет. С Vaulter общие инженерные правила (конфиг, команды, события, ошибки, тесты), но предметные слова свои.
    Путь релизов: 0.3.N → 0.4.0 → 0.9.0 → 1.0.0.

## Что изменилось во втором проходе

Первый проход был сделан по образцу Vaulter слишком буквально и слишком «машинным» языком. По замечаниям владельца:

- **Панели сохранены и усилены.** Отказ от переименования в Realm. Панель — самостоятельная единица со своими
  настройками (провайдер → плагины → конфиг), хранилищем, моделями и плагинами ([D06](02-decisions.md#d06),
  [D45](02-decisions.md#d45), [D46](02-decisions.md#d46)).
- **Добавлены плагины, пайплайны, свои модели и поля, модули, контракт интеграций**
  ([D47](02-decisions.md#d47)–[D51](02-decisions.md#d51)), а также управление панелью из другой панели
  (`administeredBy`, [D23](02-decisions.md#d23)).
- **Терминология AzGuard — своя.** Сохранены привычные имена (Panel, GrantSource, DirectGrant); переименовано только
  то, что вводило в заблуждение. С Vaulter общие только инженерные правила, предметные слова разные: Profile ≠ Panel,
  NodeGrant ≠ DirectGrant ([D43](02-decisions.md#d43)).
- **Мост к Vaulter — работа Vaulter.** Файл 10 переписан как общий контракт для любых пакетов; замечания по текущему
  мосту оформлены как заметки для Vaulter ([10 §10](10-integrations.md#10-заметки-для-vaulter-по-текущему-мосту)).
- **Язык.** Добавлен обзор [00](00-overview.md), у каждого решения есть строка «Кратко», таблицы объясняют «зачем».

Находки N01–N24, probes и T0-патч не изменились: это факты о текущем коде.

## Отличия от предыдущих аудитов

- **От аудита Perplexity:** не размечаю 150 классов тегами (граница API — namespace + манифест); контексты
  становятся встроенным плагином ядра, а не отдельным plugin-API; не ввожу два типа строк прав; префикс `azg_`
  беру, но главное — меняю саму схему назначений; исправляю факты, которые Codex уже опроверг.
- **От Codex:** принимаю рамку «смысл раньше раскладки» и почти все C-находки, но довожу до решений и имён. Выбираю
  вариант B **внутри одного дистрибутива**, без отдельного порта хранилища в 1.0. C01 довожу до межзапросной утечки
  (P07). Нахожу N01–N04, которые меняют порядок работ (T0-патч до канона).

## Границы проработки

- Прочитаны все исходники трёх пакетов, миграции, конфиги, стабы, выборочно тесты и документация; мост Vaulter и
  решения Vaulter — для согласования.
- **Запускались:** существующий набор тестов (871 зелёный, SQLite) и 19 probes (все воспроизводят дефекты), см.
  [evidence](evidence/README.md). Зависимости ставились из git без rector/phpstan/larastan (загрузка zip с GitHub
  закрыта политикой egress окружения). На тесты и probes это не влияет; PHPStan и Rector не запускались.
- **Не запускались:** PostgreSQL/MySQL, реплики, Redis, Octane, конкурентные сценарии, Filament-UI в браузере. Для
  них есть сценарии в [14](14-verification.md).
- Код пакетов и Vaulter **не менялся**; probes лежат в `evidence/`, а не в `tests/`.
- Связь с mAInd из контейнера не проверена (`maind` не установлен), см. [Q17](15-owner-questions.md).

## Как превратить в план

1. Создать план по протоколу проекта (`plans/ACTIVE.md`). Фазы и пункты взять из [13-workstreams.md](13-workstreams.md)
   без перенумерации; первым идёт F1 (T0-патч 0.3.N).
2. В `Execution Rules` перенести правила [13 §0](13-workstreams.md#0-правила-исполнения-переносятся-в-execution-rules-плана),
   в `Decision Log` — ссылки на D01–D51 (не копировать тексты).
3. Каждый пункт начинается с инверсии своего probe в регрессионный тест.
4. Пункты с маршрутизацией opus не отдавать младшим моделям без спецификации в `findings/`.
5. Заметки по мосту для Vaulter ([10 §10](10-integrations.md#10-заметки-для-vaulter-по-текущему-мосту)) передать
   отдельной задачей в план Vaulter (пункт P9.6).
