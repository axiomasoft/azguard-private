# 02 — Журнал решений

Каждое решение — **позиция для плана**, а не вариант. Оспорить решение можно через
[15-owner-questions.md](15-owner-questions.md); без ответа действует то, что записано здесь. У каждого решения есть
строка **«Кратко»** — смысл без технических деталей. Ниже неё — спецификация для исполнителя. Обзор всей картины
простыми словами — [00-overview.md](00-overview.md).

Ссылки `Nxx` — находки о текущем коде из [01-review.md](01-review.md), `Cxx` — находки Codex, `Pxx` — probes из
[evidence](evidence/README.md). Probes остаются тестами: новая архитектура должна делать эти дефекты невозможными.

**Третий проход (по ответам владельца).** Панель — **конструктор**. Он собирает права субъекта из разных механик:
правила в коде, роли-классы, Laravel Policy и Gate, база данных (как в Spatie), связи сущностей, свои источники.
Механики сочетаются в одной панели и меняются без изменения кода проверок (D52–D55). Трейт модели снова умеет и
проверять, и менять права, с простым синтаксисом как в Spatie. Есть панель по умолчанию, поэтому указывать панель
приходится редко (D05, D10, D11). Суперадмин — просто субъект, которому в панели разрешено всё (D19). Кто может
редактировать права, решает приложение, а не AzGuard (D23). Совместимость с 0.3 не нужна: пакет строится сразу
правильно (D01).

<a id="d01"></a>
### D01 — Новая версия с чистого листа, без совместимости с 0.3

**Кратко:** пакет ещё не в работе, поэтому делаем сразу правильно: без переходных слоёв, без старых ключей конфига и
без переноса данных.

**Решение.**

- Код переписывается по этому досье. Старые классы, ключи конфига, таблицы и команды удаляются, а не
  переименовываются через алиасы.
- Нет патча 0.3.x, нет команды обновления данных, нет нормализатора старого конфига.
- Находки N01–N24 не патчатся в старом коде. Каждая превращается в требование к новому коду и в регрессионный тест
  (probe с обратным ожиданием, [13](13-workstreams.md)).
- Выпуски: `1.0.0-beta.N`, пока идёт сборка и dogfooding, затем `1.0.0`, когда зелёные гейты совместимости
  ([12 §5](12-operations-and-release.md#5-гейты-совместимости)). После 1.0 — SemVer.

**Отвергнуто.** Выпуск 0.4 с upgrade-миграцией и нормализатором: он нужен только при живых пользователях 0.3.

<a id="d02"></a>
### D02 — Архитектура: ядро понятий, панели-конструкторы, механики прав

**Кратко:** в центре — маленькое ядро понятий. Вокруг него — панели, которые собирают права из подключаемых механик.
Laravel и Filament — внешние слои, которые только переводят.

**Решение.** Зоны кода (подробно — [04](04-packages-and-layout.md)):

| Зона | Простыми словами | Правило |
|---|---|---|
| **Kernel** | словарь и арифметика прав: ключ, шаблон, субъект, контекст, решение | чистый PHP, без Laravel |
| **Panels** | описание панели, настройки, реестр, выбор панели | панель неизменна после загрузки |
| **Sources** | механики, из которых панель собирает права: код, БД, связи, свои | каждая механика — отдельный модуль |
| **Policies** | вызов Laravel Policy и Gate как механики решения | только вызывает, не регистрирует политики в Gate |
| **Authorization** | пайплайн проверки, кэш, пакетная проверка, объяснение, видимость | только читает |
| **Changes** | пайплайн изменения прав (роли, назначения, прямые права в БД) | единственный путь записи |
| **Schema** | описание панели для интерфейсов: какие права, роли, поля и как их заполнять | только читает |
| **Storage** | таблицы, модели, хранилища панелей, версия состояния | единственное место работы с БД |
| **Plugins** | контракт плагина; встроенные механики и аудит — тоже плагины | ядро не знает конкретных плагинов |
| **Laravel** | фасад, трейт, Gate, middleware, команды | только переводит Laravel ↔ ядро |
| **Filament** (отдельный пакет) | редакторы ролей и прав по схеме панели | только публичный API |

Хранилище в 1.0 — Eloquent. Внешние системы прав подключаются как **источник прав** (D52), а не как замена хранилища.

**Отвергнуто.** Внешний policy engine (Cedar/OpenFGA): нет потребителя графов отношений. Отдельный пакет
`azguard-kernel`: границу держит arch-тест.

<a id="d03"></a>
### D03 — Пакеты: `axiomasoft/azguard` и `axiomasoft/azguard-filament`

**Кратко:** два пакета. Контексты (доступ «внутри сущности») — часть ядра. Интеграции с другими пакетами живут в
этих пакетах.

**Решение.**

1. `axiomasoft/azguard` (namespace `AzGuard\`) — ядро, все встроенные механики, Laravel-слой, тестовый набор.
   Бывший `azguard-context` вливается в ядро: доступ к конкретной сущности — базовая возможность, а не дополнение
   (сейчас context-пакет использует пять внутренних классов ядра, то есть отдельным он не является).
2. `axiomasoft/azguard-filament` (`AzGuard\Filament\`) — требует `axiomasoft/azguard: self.version`.
3. Публичный репозиторий — `github.com/axiomasoft/azguard`; `homepage`/`support` в `composer.json` указывают туда.
4. Релизы lockstep: один тег монорепо → одинаковая версия split-пакетов.
5. Пакеты-интеграции (мост Vaulter и будущие) — вне монорепо AzGuard, опираются только на `@api`/`@spi` (D51).

<a id="d04"></a>
### D04 — Словарь: панель остаётся панелью

**Кратко:** слово «панель» сохраняется. «Guard» не подходит: в Laravel guard — это способ входа пользователя, а у
одного guard'а бывает несколько панелей.

**Решение.** Полный словарь — [03](03-glossary-and-renames.md).

Почему не Guard. Панель ссылается на auth guard Laravel (`subjects(User::class, guard: 'web')`). При этом на одном
guard'е `web` живут сразу «личный кабинет» и «кабинет продавца». Если назвать панель Guard, получится
`->guard('web')` внутри guard'а `cabinet` и путаница с `config/auth.php`. У Spatie роли разделены именно по auth
guard'ам (`guard_name`), поэтому разделить кабинет и кабинет продавца там нельзя. Если владелец всё же выберет
Guard, это механическая замена имён ([Q1](15-owner-questions.md)).

| Понятие | Термин | Почему |
|---|---|---|
| Пространство прав со своими настройками и механиками | **Panel** | язык продукта; как панели Filament |
| Что можно разрешить | **Permission** | без изменений |
| Набор прав | **Role** | из кода или из БД (D14) |
| Выдача роли субъекту | **Role assignment** | вместо технических `model_has_roles`/`ModelHasScope` |
| Право, выданное напрямую | **Direct permission** | как в Spatie; «ContextRole» не было ролью |
| У кого права | **Subject** | пользователь или любая сущность (D11) |
| Где действует право | **Context** | конкретная сущность: проект, магазин, страница |
| Механика, дающая права | **Grant source** | код, БД, связи, свои (D52) |
| Правило-метод, решающее право | **Policy** | Laravel Policy с привязкой к праву (D53) |
| Описание панели для интерфейсов | **Schema** | D54 |
| Правило «только запретить» | **Restriction** | D20 |
| Точки вмешательства | **Hooks** | D55 |

<a id="d05"></a>
### D05 — Имена прав и одно правило выбора панели

**Кратко:** внутри панели право называется коротко (`orders.view`), полное имя — `admin:orders.view`. Панель
выбирается одним правилом для всех способов проверки: явно указанная → панель текущего маршрута → панель по
умолчанию для этой модели. Если панель определить нельзя, это ошибка, а не тихий отказ.

**Решение.**

- **Локальное имя** права — сегменты через точку, **минимум два** (`orders.view`, `cabinet.pages.billing`). Одиночные
  слова (`view`, `update`) остаются Laravel-политикам моделей, AzGuard их не перехватывает.
- **Полное имя** — `panel:local` (`admin:orders.view`). Разделитель `:` однозначен: сегмент `admin` в локальном имени
  никогда не спутается с панелью `admin`. Тот же вид у ролей: `admin:manager`.
- **Enum-права** хранят локальную часть. Enum, подключённый к одной панели, знает её сам. Подключённый к нескольким —
  требует явной панели, иначе `AmbiguousPanelException`.
- **Правило выбора панели** (одно, в `Panels\PanelResolver`, используется всеми входами: трейт, фасад, Gate,
  middleware, Blade, CLI):
  1. явно: enum с одной панелью, полное имя `admin:…`, `->inPanel('admin')`, аргумент `panel:`;
  2. текущая панель запроса (middleware `azguard.panel`, Filament-панель), если субъект ей принадлежит;
  3. панель по умолчанию для модели субъекта (D11);
  4. иначе `PanelNotResolvedException` с подсказкой.
- `explain()` показывает, по какому шагу выбрана панель.

**Почему.** Сейчас в коде четыре разных правила выбора панели, и часть проверок отвечает не про ту панель (N01, N05,
N09, P01c, P09). Одно правило с понятным порядком убирает этот класс ошибок. При этом синтаксис остаётся коротким:
в обычном коде панель не указывают.

<a id="d06"></a>
### D06 — Панель: провайдер, сборка, реестр

**Кратко:** панель описывается в своём провайдере, как в Filament. После загрузки приложения её нельзя незаметно
поменять; две панели с одним id — ошибка.

**Решение.**

- `PanelProvider::panel(PanelBuilder $panel): PanelBuilder`; результат сборки — `final readonly Panel`.
- id панели: `^[a-z0-9][a-z0-9-]{0,63}$`.
- `PanelRegistry`: повторный id → `DuplicatePanelException`; `replace()` — явная замена до заморозки;
  `configurePanel(id, fn)` — дополнение чужой панели (модули, D50); `configurePanels(fn)` — одна настройка для всех
  панелей (например, общее правило суперадмина). После `booted` реестр заморожен (`RegistryFrozenException`).
- Что задаётся на панели — D45; механики — D52–D53; хуки — D55; плагины — D47.

<a id="d07"></a>
### D07 — Единый кодек идентичности: субъект, контекст, роль

**Кратко:** «кто» и «где» кодируются одинаково везде — в БД, кэше и событиях. Два разных контекста никогда не
превратятся в одну строку.

**Решение.**

- `SubjectRef(type, id)`, `ContextRef(type, id)` — readonly-значения. `type` — morph alias без `:`
  (`^[A-Za-z0-9_.\\-]{1,128}$`); `id` — строка: число → десятичная строка, строка — без преобразований, ≤ 64 байт.
  `7` и `'7'` — одна идентичность.
- `ContextRef::key()` = `"{type}:{id}"` — однозначно, потому что в `type` нет `:`. Отсутствие контекста — ключ
  `global`.
- `RoleKey`, `PermissionKey` — `"{panel}:{local}"`.
- `IdentityCodec` — единственное место кодирования; digest для кэша — sha256 от JSON-массива компонентов.

Закрывает P07 (право одного контекста выдавалось в другом из-за совпадения строк).

<a id="d08"></a>
### D08 — Типы ключей хоста: `ids.host_keys`

**Кратко:** колонки с id пользователей и сущностей по умолчанию строковые — подходят и для чисел, и для UUID/ULID.
Тип можно выбрать явно.

**Решение.** `azguard.ids.host_keys`: `string` (по умолчанию, `varchar(64)`) | `bigint` | `uuid` | `ulid` — те же
значения, что у Vaulter (общее правило экосистемы, D43). Отдельное хранилище панели может задать свой тип.
Применяется к `subject_id`, `context_id`, `actor_id`.

<a id="d09"></a>
### D09 — Публичный API: модель, панель, фасад

**Кратко:** чаще всего работают с моделью (`$user->hasPermissionTo('orders.view')`), как в Spatie. Для другой
панели — `$user->inPanel('admin')`. Для всего про панель целиком — `AzGuard::panel('admin')`.

**Решение.** Нормативно — [05-php-api.md](05-php-api.md).

```php
// 1. Модель (трейт HasAzGuard) — панель по умолчанию или текущая
$user->hasPermissionTo('orders.view');
$user->hasPermissionTo(CabinetPermission::OrdersView, on: $order);
$user->assignRole('editor', on: $project);
$user->inPanel('admin')->hasRole('manager');
$user->isSuperAdmin();

// 2. Панель целиком
$admin = AzGuard::panel('admin');
$admin->roles()->create('support', label: 'Поддержка', permissions: [OrderPermission::View]);
$admin->schema();                               // описание для интерфейсов (D54)
$admin->decideMany($requests);                  // пакетно, один снимок данных
$admin->explain($request);

// 3. Laravel как обычно
Gate::allows('orders.view');                    // правило выбора панели D05
@can('admin:orders.refund')
```

- `AzGuardManager` — корень фасада без состояния.
- `PanelAccess` (`AzGuard::panel()`, `@api`): `for($subject)`, `roles()`, `schema()`, `decide()`, `decideMany()`,
  `explain()`, `catalog()`, `visibility()`, `state()`, `definition()`.
- Удаляются `AzGuardManagerInterface`, `GrantBuilder`, `ContextGrantBuilder`(+factory),
  `AzGuard::forUser()->on()->grant()`.

<a id="d10"></a>
### D10 — Трейт `HasAzGuard` на любой модели: проверки и изменения

**Кратко:** модель умеет всё, что нужно в повседневном коде: проверить право и роль, выдать и забрать. Синтаксис
как в Spatie, плюс панели и сущности.

**Решение.** `AzGuard\Concerns\HasAzGuard` + контракт `AzGuardSubject`.

| Группа | Методы |
|---|---|
| Права | `hasPermissionTo()`, `hasAnyPermission()`, `hasAllPermissions()`, `getAllPermissions()`, `getPermissionNames()` |
| Роли | `hasRole()`, `hasAnyRole()`, `hasAllRoles()`, `getRoleNames()` |
| Суперадмин | `isSuperAdmin()` |
| Изменения | `assignRole()`, `removeRole()`, `syncRoles()`, `givePermissionTo()`, `revokePermissionTo()`, `syncPermissions()` |
| Панели | `inPanel(string $id): SubjectAccess`, `azguard(): SubjectPanels` (все панели субъекта сразу) |

- Имена методов — как в Spatie Permission: разработчик, знающий Spatie, пишет код сразу.
- У всех методов есть необязательный `on:` — сущность (контекст или ресурс, D16). У изменений — `expiresAt:` и
  `fields:` (свои поля назначения, D46).
- Изменения идут через пайплайн изменений (D49): проверка, запись одной транзакцией, новая версия состояния, события.
- Методы изменения работают для механик, которые хранят данные в БД. Для правил из кода и политик менять нечего:
  `assignRole()` для автоматической роли (D14) → `RoleNotAssignableException`.
- Трейт подходит любой модели, не только пользователю (D11).

**Отвергнуто.** Трейт «только для чтения» (второй проход): владелец хочет управлять правами из сущности.

<a id="d11"></a>
### D11 — Субъекты: любая модель; панель по умолчанию

**Кратко:** права могут быть у пользователя, у проекта, у команды — у любой модели с трейтом. У одной модели
бывает несколько панелей; одна из них — «по умолчанию», чтобы не указывать её в каждой проверке.

**Решение.**

- `PanelBuilder::subjects(User::class, guard: 'web')` — какие модели бывают субъектами панели и из какого auth
  guard'а брать текущего субъекта (для middleware и UI). Моделей может быть несколько.
- `->default()` — панель по умолчанию для своих моделей. Если модель входит в одну панель, эта панель и есть панель
  по умолчанию. Две панели с `default()` для одной модели → ошибка при загрузке.
- Модель может переопределить выбор: `azguardDefaultPanel(): ?string` (например, продавцу — кабинет продавца).
- Все панели субъекта собираются в один набор, разделённый по панелям: `$user->azguard()->permissions()` →
  `['cabinet' => …, 'seller' => …]`. Каждая панель собирается лениво при первом обращении и кэшируется.
- `SubjectDirectory` (`@spi`) — поиск субъектов для UI/CLI; по умолчанию — через модели панели.
- Зашитая модель `User` и ключ `'id'` удаляются (N15).

<a id="d12"></a>
### D12 — Граница API: namespace + машинный манифест

**Кратко:** по расположению класса видно, можно ли от него зависеть; тест не даст незаметно поменять публичный
контракт.

**Решение.** `Contracts\*` — `@api` (вызывать) или `@spi` (реализовывать); `Kernel\*`, `Panels\PanelBuilder`/`Panel`/
`PanelProvider`, `Schema\*`, `Events\*`, `Exceptions\*`, `Facades\AzGuard`, `Concerns\HasAzGuard`, `Roles\CodeRole`,
`Testing\*`, базовые модели (чтение и наследование) — `@api`; остальное — internal по расположению.
`api-manifest.json` в каждом пакете сравнивается в CI.

<a id="d13"></a>
### D13 — Данные в БД: роли, назначения, прямые права

**Кратко:** в БД хранится только то, что меняется во время работы: роли, созданные в админке, назначения ролей и
прямые права. Всё с контекстом (где действует), сроком и тем, кто выдал.

**Решение.** Таблицы — [08](08-data-model-and-migration.md):

| Таблица | Строка означает |
|---|---|
| `{p}roles` | роль, созданная во время работы (в админке, командой, кодом через API) |
| `{p}role_permissions` | права этой роли |
| `{p}role_assignments` | субъект держит роль (из кода или из БД) в контексте до даты |
| `{p}direct_permissions` | субъекту выдано право или шаблон в контексте до даты |
| `{p}panel_state` | версия состояния прав панели (для кэшей) |

- Назначения ссылаются на роль по ключу (`panel`, `role`), а не по id строки: роли из кода не нужно копировать в БД,
  команда синхронизации не нужна.
- В идентичности нет NULL (`context_key = 'global'`), поэтому обычные уникальные индексы работают на всех СУБД.
  `NullSafeUniqueIndex` и `AssignmentDeduplicator` (~1100 строк) не нужны.
- У каждой строки — `meta` (JSON, nullable) для своих полей без миграций (D46).

<a id="d14"></a>
### D14 — Роли: где определены × как назначаются

**Кратко:** роль можно описать в коде (права не меняются из админки) или создать в БД (права редактируются).
Назначить роль можно вручную (запись в БД) или автоматически по правилу в коде (например, «продавец — каждый, у кого
есть магазин»).

**Решение.**

| | Назначается вручную (БД) | Назначается автоматически (правило) |
|---|---|---|
| **Роль в коде** (`CodeRole`) | «Менеджер»: права в коде, кому — решает админ | «Покупатель»: всем с моделью `Customer`; «Продавец»: всем с `is_seller` |
| **Роль в БД** | «Поддержка», созданная в Filament | — (правило живёт в коде) |

- Роль в коде — класс `CodeRole` (`key()`, `label()`, `permissions()`, `formerKeys()`). Автоматическая роль реализует
  `AssignedAutomatically::appliesTo(Model $subject, ?ContextRef $context): bool`; по умолчанию она недоступна для
  ручного назначения (`assignable(): bool` можно переопределить).
- Роль в БД создаётся через `AzGuard::panel($id)->roles()` или Filament; ключ не может совпасть с ключом роли из кода.
- Ключ роли — `^[a-z0-9][a-z0-9-]{0,63}$`, полное имя `panel:key`. PHP-класс — не идентичность: переименование класса
  ничего не ломает (N12). Смена ключа роли из кода — `formerKeys()` + команда `azguard:roles:rename-key`.
- `rank`/`level` удаляются: иерархия ролей не нужна для проверки.

<a id="d15"></a>
### D15 — Контексты: политика на панели

**Кратко:** каждая панель сама решает, как права работают внутри сущностей: «глобальные права действуют везде и
дополняются правами в сущности», «внутри сущности — только её права», «без сущности нельзя» или «сущностей нет».

**Решение.**

```php
$panel->contexts(ContextPolicy::inherit(Project::class, Store::class));   // глобальные ∪ права в сущности
$panel->contexts(ContextPolicy::isolated(Project::class));                // в сущности — только её права
$panel->contexts(ContextPolicy::required(Store::class));                  // без сущности — отказ
$panel->contexts(ContextPolicy::none());                                   // по умолчанию
$panel->contexts(ContextPolicy::inherit(Store::class)->requireMembership(StoreMembership::class));
```

- Таблица смысла — [09 §3](09-authorization-semantics.md#3-политика-контекстов-панели).
- Тип, не объявленный панелью, → ошибка при записи и `Deny(ContextNotAccepted)` при проверке.
- Членство (Q11): «глобальная роль действует внутри магазина только для его сотрудников» — необязательное ограничение
  на панели. Реализация членства — любая: связь модели, свой класс `ContextMembership`, запрос.

---

<a id="d16"></a>
### D16 — Контекст и ресурс в проверке

**Кратко:** сущность передают прямо в проверку: `on: $project`. Если это заказ, а не проект, AzGuard сам узнаёт у
заказа, в каком он магазине. В фоновых задачах контекст передают явно.

**Решение.**

- `on:` принимает модель или `ContextRef`. Модель типа, объявленного панелью как контекст, → контекст. Любая другая
  модель → **ресурс**: передаётся в политики и ограничения, а контекст берётся из ресурса
  (`ContextAware::azguardContext()`, например `$order->store`), иначе из текущего контекста запроса.
- Текущий контекст запроса (`CurrentContext`, scoped) ставит middleware панели через её резолверы (например, из
  параметра маршрута `{store}`).
- `AzGuard::withinContext($context, fn)` — для кода без HTTP; ставит внутри `try`, восстанавливает в `finally` (C02).
- Jobs передают `ContextRef` явно; текущий контекст в очередь не переносится.

<a id="d17"></a>
### D17 — Смысл решения

**Кратко:** ответ «можно ли» получается одним и тем же путём при любом способе проверки. Ошибка на любом шаге
означает «нельзя».

**Решение.** Порядок шагов — D48, нормативный алгоритм — [09](09-authorization-semantics.md). Итог — `Decision`:
`Allow`/`Deny`/`NotApplicable` + причина + версия состояния. Явных запрещающих выдач нет (Q12): запрет делается
ограничением (D20) или хуком (D55).

<a id="d18"></a>
### D18 — Грамматика имён и шаблонов

**Кратко:** права пишутся маленькими буквами через точку. Звёздочки — только при выдаче, не в каталоге. «Всё в
панели» — это суперадмин, а не звёздочка.

**Решение.** Сегмент `^[a-z0-9][a-z0-9_-]*$`; локальное имя — ≥ 2 сегментов, ≤ 255 символов; полное — `panel:local`.
Шаблоны — только в выдаче (роль в БД, прямое право): `orders.*` — один сегмент, `orders.**` — всё глубже. Голые `*` и
`**` запрещены: «всё» даёт суперадмин (D19). Сменяемый `PermissionMatcher` удаляется: грамматика — часть данных.

---

<a id="d19"></a>
### D19 — Суперадмин

**Кратко:** суперадмин — обычный субъект, для которого в панели любая проверка возвращает «да». Сколько их — не
важно. Проверить можно методом `isSuperAdmin()`.

**Решение.**

- Правило задаётся на панели: `->superAdmin(role: 'superadmin')` (по умолчанию: держатель роли `superadmin` этой
  панели) или `->superAdmin(when: IsRootUser::class)` / замыкание в провайдере, или `->superAdmin(false)`. Если роли
  `superadmin` на панели нет, AzGuard добавляет роль из кода `SuperAdminRole`; назначить её можно, если на панели
  есть механика БД.
- Правило для всех панелей сразу — `defaults.super_admin` в конфиге или `AzGuard::configurePanels()`. Отдельного
  «глобального суперадмина» нет (Q10).
- Суперадмин проходит всё в своей панели, включая ограничения. Это первый встроенный before-хук (D55).
- Суперадмин — только через правило панели. Звёздочка в правах роли или прямом праве запрещена (N01, N13, P01, P14).
- `isSuperAdmin()` на модели (панель по D05) и `->inPanel('admin')->isSuperAdmin()`.

<a id="d20"></a>
### D20 — Ограничения: правила, которые умеют только запрещать

**Кратко:** ограничение — это «нельзя, даже если право есть»: пользователь заблокирован, не сотрудник этого
магазина, нерабочее время. Разрешить ограничение не может, поэтому его безопасно подключать откуда угодно.

**Решение.** `Restriction` (`@spi`): `key()`, `appliesTo(AccessRequest): bool`, `check(AccessRequest, EvaluationContext):
RestrictionResult` (`pass` | `deny(reason)`). Регистрация — `$panel->restrict(...)` и плагины; порядок = порядок
регистрации. Исключение внутри ограничения → отказ. `PermissionLayer` удаляется (C06).

<a id="d21"></a>
### D21 — Сознательно отложено (после 1.0, без поломок)

Наследование прав между панелями; иерархия контекстов (проект внутри workspace); явные запрещающие выдачи; граф
отношений; порт записи для чужого хранилища; outbox событий; готовый плагин подтверждения изменений вторым
человеком (в 1.0 — рецепт на хуке `changing`, D55).

<a id="d22"></a>
### D22 — Единственный путь записи

**Кратко:** выдать или забрать права можно через модель, через панель или через Filament — но внутри это всегда один
и тот же путь. Поэтому всегда обновляется кэш, всегда отправляются события.

**Решение.** Трейт, `AzGuard::panel()->roles()`, `->for($s)`, команды и Filament вызывают пайплайн изменений (D49).
Запись — в `Storage::mutate()` хранилища панели: транзакция → строки → +1 версия состояния панели → журнал (если
включён) → commit → события. Базовые модели можно читать и наследовать; их `save()`/`delete()` в обход API →
`UnsupportedDirectWriteException` в local/testing и предупреждение в production (Q14). Закрывает C04 (удаление роли
без сброса кэша) и N11 (события не со всех входов).

---

<a id="d23"></a>
### D23 — Кто может менять права — решает приложение

**Кратко:** AzGuard не знает, кто в приложении «администратор». Для него есть суперадмин и обычные субъекты.
Страницу «Роли» в админке защищает обычное право этой админки, как любую другую страницу.

**Решение.**

- В ядре нет политики делегирования, мета-прав, рангов и «кто кем управляет». Пайплайн изменений проверяет только
  корректность данных (D49).
- Интерфейсы редактирования защищают себя обычными правами своей панели. Например, Filament-ресурс ролей требует
  право `admin:azguard-roles.update`, как любой другой ресурс.
- Если приложению нужно правило «нельзя выдать то, чего нет у тебя», это хук `changing` (рецепт в
  [06 §4](06-extension-points.md#4-хуки-изменений)).
- «Кто выдал» записывается, если известен: текущий пользователь, явно `AzGuard::actingAs($user)` или system в
  консоли. Без актора изменение тоже проходит.

**Почему.** Во втором проходе я смоделировал администрирование внутри AzGuard. Это лишнее: у разных приложений
разное понимание «админа», а у панели может вообще не быть редактирования (например, у панели с правами только из
политик).

---

<a id="d24"></a>
### D24 — Версия состояния на панель и честная консистентность

**Кратко:** у каждой панели свой счётчик изменений: изменения в админке не сбрасывают кэш кабинета. После отзыва
права новая проверка его уже не увидит. Повторная проверка в том же запросе не ходит в БД.

**Решение.**

- `{p}panel_state` — строка на панель; +1 только внутри `mutate()` этой панели. `StateToken` = `{panel, version,
  generation, fingerprint}` — публичное значение для кэшей интеграций (D51).
- Q5: версия и встроенные источники читают **с primary** (`reads = primary`, по умолчанию; можно поменять на панели).
  Это одна дешёвая выборка на запрос, а отзыв права не зависнет из-за задержки реплики (C03).
- `state_refresh = request` (по умолчанию): версия читается раз на request/job; `check` — на каждую проверку.
  Дословная гарантия отзыва — [09 §8](09-authorization-semantics.md#8-кэш-и-консистентность).
- Кэш обходится только при незакоммиченном изменении AzGuard в этом процессе (P10b).

---

<a id="d25"></a>
### D25 — Кэш наборов прав

**Кратко:** кэшируется только «что у субъекта есть» из механик, которые это позволяют. Политики и Gate не
кэшируются: они решают с учётом конкретного ресурса.

**Решение.** Ключ `digest(panel, subjectRef, contextKeys, stateToken)`. `fingerprint` — хэш определения панели,
каталога, ролей из кода, механик, хуков и их порядка: изменение кода не требует ручного сброса. Источник объявляет
`Volatility`: `Stable` (кэшируется между запросами), `Request` (в пределах запроса), `Volatile` (не кэшируется).
Результаты политик, ограничений и хуков не кэшируются.

---

<a id="d26"></a>
### D26 — Gate Laravel

**Кратко:** `@can` и `Gate::allows()` работают с правами AzGuard как обычно. Если право принадлежит панели, отвечает
AzGuard (он сам вызовет нужную политику). Если не принадлежит — AzGuard молчит, и Laravel решает как без него.

**Решение (Q4).** `GateBridge` в `Gate::before`: имя → панель по правилу D05 → право есть в каталоге панели → ответ
AzGuard `true`/`false`; иначе `null`. Режим по умолчанию — **authoritative**: это последовательно, потому что Policy и
Gate сами являются механиками панели (D53), и двух параллельных путей решения нет (N19). `additive` (AzGuard только
разрешает, запрет отдаёт Laravel) — настройка панели для постепенного перехода. Первый аргумент Gate → `on:`.
`PolicyAttributeRegistrar` (регистрация `Gate::define` на каждую ability) и `Gate::define('direct-grant')` удаляются.

<a id="d27"></a>
### D27 — Пакетная проверка с общим снимком

**Кратко:** можно спросить про тысячу объектов одним вызовом — дёшево и согласованно (одна версия данных).

**Решение.** `decideMany(iterable<AccessRequest>): DecisionSet` — один `StateToken`, одна загрузка из БД на
`(subject, panel)`, контексты группируются; политики вызываются на каждый ресурс. Нужен листингам интеграций и
таблицам Filament.

<a id="d28"></a>
### D28 — События

**Кратко:** события отправляются только после успешного сохранения, несут «кто, что, где, когда» и понятны без
загрузки моделей. На них можно подписаться, чтобы реагировать на изменения прав.

**Решение.** База `AccessEvent`: `eventId` (ULID), `occurredAt`, `panel`, `actor` (может быть `null`),
`correlationId`, `state`, `type(): EventType`. Каталог — [08 §6](08-data-model-and-migration.md#6-каталог-событий).
Отправка — после commit; журнал (плагин `azguard/audit`) — в той же транзакции. Нет изменения → нет события.
`AccessDecided` — только при включённой трассировке (диагностика).

<a id="d29"></a>
### D29 — Объяснение из той же проверки

**Кратко:** «почему нет?» показывает весь путь: какая панель, какие механики что дали, какая политика или ограничение
отказали.

**Решение.** `explain(AccessRequest): Explanation` = решение + трасса той же оценки: выбор панели, контекст, хуки,
суперадмин, вклады механик с происхождением, политика, ограничения, итог Gate. Повторного опроса источников нет (C05,
N24).

<a id="d30"></a>
### D30 — Filament: редакторы по схеме панели

**Кратко:** Filament показывает права и роли так, как их описала панель: что можно отметить галочкой, что решается
политикой и не редактируется, какие роли можно менять, какие поля заполнять.

**Решение.** Детали — [11-filament.md](11-filament.md). `AzGuardPlugin::make()->guardPanel('admin')->manages([...])`;
формы строятся по `PanelSchema` (D54); записи — через API панели; поле `class_name` удаляется (N02); ключи ресурсов —
по slug; страницы и виджеты закрыты, если права нет (N18). Кто может открыть редакторы — решают обычные права
Filament-ресурсов (D23).

<a id="d31"></a>
### D31 — Видимость записей: явный фильтр

**Кратко:** «покажи проекты, которые пользователь может видеть» — явный вызов. Без пользователя он показывает ничего,
при нескольких назначениях — все нужные записи.

**Решение.** Глобальный scope `HasScopedRoles` удаляется (N04, P04). `Project::query()->visibleTo($user, 'projects.view')`
(трейт `ContextAware`) или `AzGuard::panel($id)->visibility()->constrain(...)`. Механики, которые умеют фильтровать
запрос (БД, связи), дают условие; остальные — предупреждение в объяснении. Семантика —
[09 §10](09-authorization-semantics.md#10-видимость-visibleto).

<a id="d32"></a>
### D32 — HTTP: панель привязывается к маршрутам через middleware

**Кратко:** группу маршрутов привязывают к панели одной middleware. Она пускает только субъектов этой панели, делает
панель текущей (короткие имена прав работают без префикса) и определяет сущность из маршрута.

**Решение.**

- `azguard.panel:{id}` — вход в панель: субъект из auth guard'а панели; субъект принадлежит панели; если задано
  право входа (`->entry(CabinetPermission::Access)`), оно есть (суперадмин проходит); текущая панель и текущий
  контекст (резолверы панели). Иначе 403 или редирект, как задано на панели.
- `azguard.can:{permission}[,{routeParam}]` — проверка права для маршрута.
- Filament-плагин ставит текущую панель сам.
- Blade — обычные `@can`/`@cannot`. Удаляются `azguard.check`, `azguard.grant`, `azguard.panel_check`,
  `azguard.roles`, `check.access`, директивы `@az*`.

### D33 — Конфигурация

**Кратко:** в `config/azguard.php` — то, что общее для всех панелей, и значения по умолчанию. Всё особенное — в
провайдере панели.

**Решение.** Детали — [07-configuration.md](07-configuration.md). Файлы `config/azguard.php`, `config/azguard-filament.php`;
readonly `AzGuardConfig`; эффективные настройки панели: провайдер → плагины → значения по умолчанию (D45); ошибки

<a id="d34"></a>
### D34 — База данных и хранилища

**Кратко:** есть общее хранилище по умолчанию, где панели различаются колонкой `panel`. Панель может получить своё
хранилище: другое подключение к БД или свои таблицы.

**Решение.** Хранилище = подключение + префикс таблиц + тип ключей хоста + классы моделей (D46). По умолчанию —
`azguard.storages.default` (`connection: null`, `table_prefix: 'azg_'`) для всех панелей (Q19). Все модели, источники
и команды работают через `Storage` панели; arch-тест запрещает фасад `DB` и статические запросы к моделям AzGuard вне
`Storage\`.

<a id="d35"></a>
### D35 — Миграции

**Кратко:** таблицы общего хранилища создаёт пакет. Для своего хранилища команда генерирует миграцию в проект, и туда
можно дописать свои колонки.

**Решение.** Ядро загружает миграции общего хранилища. `azguard:storage:migration {name}` пишет миграцию в
`database/migrations` хоста. Параметры, влияющие на схему, фиксируются в таблице состояния хранилища; doctor сверяет.

<a id="d36"></a>
### D36 — Каталог прав

**Кратко:** список прав панели собирается из enum, классов и плагинов один раз при загрузке. Одинаковое имя с разным
описанием — ошибка. В production каталог читается из кэш-файла.

**Решение.** `PermissionCatalogBuilder` (`@spi`): enum, классы, плагины, Filament. Метаданные права —
`#[Describe(label:, group:, description:)]` на case. Коллизия имени → `DuplicatePermissionException`.
`azguard:catalog:cache` — снимок каталогов, ролей из кода и привязок политик (включая найденные discovery, D53).

<a id="d37"></a>
### D37 — Исключения

**Кратко:** у каждой ошибки стабильный машинный код. Отказ в доступе — стандартное исключение Laravel.

**Решение.** База `AzGuardException` (`code(): string`, `snake_case`). Ветки: `ConfigurationException`,
`DefinitionException`, `InvalidIdentityException`, `ChangeException`, `AuthorizationEngineException`,
`StorageException`, `PluginException`. Отказ — `Illuminate\Auth\Access\AuthorizationException`. Таблица —
[05 §10](05-php-api.md#10-исключения).

### D38 — Команды

свои проверки.

**Решение.** Детали — [12](12-operations-and-release.md). Формат `azguard:<area>:<verb>`; `--panel`, где нужно;
`--json` у читающих; `azguard:doctor` с проверками ядра и плагинов; планировщик — очистка истёкших выдач.

<a id="d39"></a>
### D39 — Тестовый набор

**Кратко:** приложение тестирует права простыми хелперами; авторы плагинов, источников и интеграций — готовыми

### D43 — Экосистема: общие инженерные правила, свои предметные слова

**Кратко:** AzGuard и Vaulter одинаково устроены снаружи (конфиги, команды, события, ошибки, тесты), но говорят на

<a id="d44"></a>
### D44 — Бюджет производительности

**Кратко:** известно, сколько запросов к БД стоит проверка, и это проверяется тестами.

| Сценарий | Бюджет |
|---|---|
| Первая проверка `(subject, panel, context)` в запросе, холодный кэш, механика БД | ≤ 3 запроса (версия, назначения, прямые права) + 1 на права ролей из БД |
| Повторная проверка того же в запросе | 0 |
| Первая проверка при тёплом межзапросном кэше | 1 (версия; 0 после первой при `state_refresh = request`) |
| `Gate::before` для не своей ability | 0 запросов, O(1) |
| `decideMany()` на N ресурсов одного субъекта и панели | ≤ 3 + число разных контекстов / 100 |
| Механики «код» и «политики» | 0 запросов со стороны AzGuard; стоимость политики — её собственная |
| Загрузка в production с `azguard:catalog:cache` | 0 обращений к ФС сверх подключения кэш-файла |

<a id="d45"></a>
### D45 — Настройки панели

**Кратко:** почти всё настраивается отдельно для каждой панели. Если панель не задала значение, берётся общий
конфиг. Несколько гарантий безопасности не отключаются никакой настройкой.

**Решение.** Эффективная настройка = **провайдер панели** → иначе **плагин** (в порядке подключения; конфликт двух
плагинов → ошибка) → иначе **значение по умолчанию** из `config/azguard.php`.

| Группа | Что на панели | Методы `PanelBuilder` |
|---|---|---|
| Идентичность | id, название, описание, по умолчанию ли | `id()`, `label()`, `description()`, `default()` |
| Субъекты | модели, auth guard, директория | `subjects()` |
| Маршруты | middleware входа, право входа, ответ при отказе | `middleware()`, `entry()`, `onDenied()` |
| Права | enum, классы, построители каталога | `permissions()`, `catalogBuilders()` |
| Механики | права всем, роли из кода, политики, Gate, БД, связи, свои источники | `grantToAll()`, `roles()`, `policies()`, `discoverPolicies()`, `gates()`, `database()`, `relation()`, `source()` |
| Контексты | политика, резолверы, членство | `contexts()`, `contextResolvers()` |
| Суперадмин | правило | `superAdmin()` |
| Хуки | before, ограничения, after, changing, changed | `before()`, `restrict()`, `after()`, `changing()`, `changed()` |
| Хранилище и модели | хранилище, классы моделей, поля для решений | `storage()`, `models()`, `decisionFields()` |
| Gate | режим | `gate()` |
| Кэш и консистентность | store, ttl, generation, `reads`, `state_refresh` | `cache()`, `consistency()` |
| Плагины | подключить, выключить | `plugin()`, `plugins()`, `withoutPlugin()` |
| Интерфейс | группы, иконки, подписи для Filament и своих UI | `presentation()` |

**Не настраивается:** грамматика имён и кодек идентичности; атомарность «запись + версия»; учёт сроков выдач;
«ошибка = отказ»; ограничения умеют только запрещать; проверка каталога при выдаче.

<a id="d46"></a>
### D46 — Хранилища, свои модели и свои поля

**Кратко:** панель может хранить данные в общих таблицах или в своих. Модели можно расширить своими полями; поля
проверяются при выдаче и могут участвовать в решении.

**Решение.**

- **Хранилище:** `->storage('default')` (по умолчанию), `->storage('backoffice')` (именованное из конфига),
  `->storage(Storage::own(prefix: 'admin_', connection: 'backoffice'))`. Панели в одном хранилище различаются колонкой
  `panel`; у каждой — своя строка версии.
- **Модели панели:** `->models(role: AdminRole::class, assignment: AdminRoleAssignment::class, directPermission: …)`.
  Классы наследуют базовые модели; идентификационные колонки и методы — `final`.
- **Свои поля:**
  - настоящие колонки — миграцией хоста (nullable в общем хранилище);
  - лёгкие поля — колонка `meta` (JSON, nullable, Q22) с типизированным кастом в модели панели;
  - запись — `$user->assignRole('editor', on: $project, fields: ['department_id' => 7])`;
  - правила — `azguardFields(): array` в модели (тип, подпись, правила валидации). Они же попадают в схему панели
    (D54), поэтому Filament и другие UI строят формы сами. Неизвестное поле → ошибка валидации;
  - участие в решении — поля из `->decisionFields([...])` загружаются вместе с выдачами и доступны ограничениям и
    хукам.
- Правильность `meta`: поле в `meta` нельзя индексировать и искать эффективно. Если по полю фильтруют или его
  проверяют ограничения на больших объёмах, это колонка. Doctor предупреждает, если поле из `decisionFields` лежит в
  `meta`.

<a id="d47"></a>
### D47 — Плагины панели

**Кратко:** плагин — класс, который подключают к панели. Он может принести права, роли, механики, политики, хуки,
поля и проверки doctor. Встроенные механики AzGuard — тоже плагины.

**Решение.**

```php
interface Plugin                                   // AzGuard\Contracts\Plugins\Plugin (@spi)
{
    public function id(): string;                  // 'vendor/name'
    public function register(PanelBuilder $panel): void;   // объявить вклад до заморозки
    public function boot(Panel $panel): void;               // рантайм-связи после заморозки
}
```

- Один плагин можно подключить к нескольким панелям; каждый экземпляр видит свою.
- Зависимости — `DependsOnPlugins::requires()`; отсутствие → ошибка при загрузке.
- Пространство имён — `->keyPrefix('blog')` (`BasePlugin`): права плагина становятся `blog.…` внутри панели.
- Встроенные: `azguard/code`, `azguard/database`, `azguard/policies`, `azguard/relations`, `azguard/audit`
  (выключен по умолчанию). Методы `PanelBuilder` вроде `->database()` — короткая запись подключения этих плагинов.
- Плагин не может отключить гарантии D45 и писать в хранилище в обход пайплайна изменений.

<a id="d48"></a>
### D48 — Пайплайн проверки

**Кратко:** проверка — это цепочка шагов. Каждый шаг умеет своё, поэтому механики и хуки расширяют проверку, но не
могут случайно её ослабить.

| Шаг | Что происходит | Кто участвует |
|---|---|---|
| 1. Панель | выбрать панель по правилу D05 | ядро |
| 2. Подготовка | контекст и ресурс из `on:`, политика контекстов | ядро, резолверы |
| 3. Before-хуки | суперадмин, затем свои хуки: «да», «нет» или «не знаю» | D19, D55 |
| 4. Решение | право привязано к политике или Gate → решает она; иначе → объединение вкладов механик | D52, D53 |
| 5. Ограничения | могут только запретить | D20 |
| 6. After-хуки и события | наблюдать, записывать | D55, D28 |

Ошибка на шагах 2–5 → отказ; на шаге 6 → лог, решение не меняется. Алгоритм — [09 §2](09-authorization-semantics.md#2-пайплайн-проверки-алгоритм).
Реализация — внутренний цикл без замыканий на горячем пути.

<a id="d49"></a>
### D49 — Пайплайн изменений

**Кратко:** любое изменение прав проходит одинаковый путь: проверка данных → хуки → запись → события. Хуки могут
дополнить изменение или отменить его.

| Шаг | Что происходит | Транзакция |
|---|---|---|
| 1. Проверка | панель принимает модель; роль существует и назначается вручную; право есть в каталоге и может выдаваться; тип контекста принят; свои поля по правилам | до |
| 2. Хуки `changing` | изменить (срок, поля), отменить с причиной (`ChangeCancelledException`) | до |
| 3. Запись | строки + версия панели + журнал (плагин) | **в** транзакции |
| 4. События и хуки `changed` | Laravel-события, свои реакции | **после** commit |

`Change` — неизменяемое описание операции (тип, панель, субъект, роль или право, контекст, срок, поля, актор, если
известен). Результат — `ChangeResult` (`applied` | `unchanged`). Подтверждение вторым человеком, запрет «выдавать
больше своего», уведомления — хуками (рецепты — [06 §4](06-extension-points.md#4-хуки-изменений)).

<a id="d50"></a>
### D50 — Модули и сторонние пакеты внутри приложения

**Кратко:** Laravel-модуль может принести свою панель или дополнить существующую. Какую именно — решает приложение.
Конфликты видны сразу при загрузке.

**Решение.**

- Своя панель модуля — обычный `PanelProvider`: `AzGuard::registerPanel(BlogPanelProvider::class)`.
- Дополнение чужой панели — `AzGuard::configurePanel('admin', fn (PanelBuilder $p) => $p->plugin(BlogAccessPlugin::make()->keyPrefix('blog')))`.
  Несуществующая панель → ошибка при загрузке. id панели модуль берёт из своего конфига, а не зашивает.
- Коллизия имён прав или ролей → ошибка с именами плагинов. `azguard:panels:list --sources` показывает, кто что
  принёс.

<a id="d51"></a>
### D51 — Контракт для пакетов-интеграций (Vaulter и другие)

**Кратко:** любой пакет может опираться на AzGuard через небольшой стабильный набор возможностей. Как он переводит
свои понятия в понятия AzGuard — его дело.

**Решение.** Детали — [10-integrations.md](10-integrations.md). AzGuard гарантирует (всё `@api`/`@spi`):

| Потребность интеграции | Что даёт AzGuard |
|---|---|
| Спросить «можно ли» | `AzGuard::panel($id)->decide()/decideMany()/explain()`, трейт, Gate |
| Понять, что изменилось | `StateToken` панели + события после commit |
| Встроиться в панель | `Plugin` + `configurePanel()`; пакет даёт плагин, хост выбирает панель |
| Свои права, роли, политики | enum, `CodeRole`, привязка политик в плагине |
| Свой источник прав или ограничение | `GrantSource`, `Restriction`, хуки |
| Описать себя для UI | вклад в `PanelSchema` (группы, подписи, поля) |
| Перевести свою сущность в контекст | `ContextRef::of(type, id)`, `ContextAware` |
| Проверить себя | `IntegrationContractTests` против настоящего AzGuard |

Правила: не импортировать `Internal\`/`Storage\`; не зашивать id панели; не копировать права AzGuard к себе;
кэшировать с `StateToken`; `require axiomasoft/azguard: ^1.0`.

<a id="d52"></a>
### D52 — Механики прав: из чего панель собирает права

**Кратко:** панель — конструктор. В неё подключают механики, которые дают права: правила в коде, роли-классы,
политики, базу данных, связи сущностей, свои источники. Их можно сочетать в любой пропорции и менять, не трогая код
проверок.

**Решение.**

| Механика | Где задаётся | Меняется во время работы | Пример |
|---|---|---|---|
| Права всем субъектам панели | `->grantToAll(...)` | нет | каждый покупатель видит свой профиль |
| Роль из кода, назначаемая вручную | класс `CodeRole` + назначение в БД | кому назначена — да, права — нет | «Менеджер» |
| Роль из кода, назначаемая автоматически | `CodeRole` + `appliesTo()` | нет | «Продавец» — всем с `is_seller` |
| Политика | метод Laravel Policy с `#[Decides(...)]` | нет (логика в коде) | «заказ можно смотреть только свой» |
| Gate | `->gates([Perm::X => 'ability'])` | нет | фича-флаг, бета-доступ |
| Роли и права в БД | `->database()` | да | роль «Поддержка» из Filament; Борису право на месяц |
| Связи сущностей | `->relation(Project::class, via: 'members', role: 'pivot.role')` | через данные приложения | участники проекта с ролью в pivot |
| Свой источник | `->source(new TokenAbilitiesSource)` | как решит автор | способности API-токена, LDAP-группы |

- Механики «дают права» (`GrantSource`). Итоговый набор — объединение их вкладов с учётом контекста и срока.
- Проверка не зависит от механики: `hasPermissionTo(CabinetPermission::OrdersView)` одинаково работает, пока право
  выдаётся ролью из кода, после переноса в БД и если решение передано политике (Q18).
- Механика может быть выключена на панели. Например, у панели `cabinet` нет БД-механики (ничего не редактируется), а у
  `admin` есть.
- Каждая встроенная механика — плагин (D47), её контракт открыт для своих реализаций ([06 §2](06-extension-points.md#2-свой-источник-прав)).

<a id="d53"></a>
### D53 — Laravel Policy и Gate как механика

**Кратко:** право можно отдать на решение методу обычной Laravel-политики. Политика получает пользователя и ресурс,
может сверить права из БД и решает. Так «жёсткие правила» и «редактируемые права» живут вместе.

**Решение.**

```php
final class OrderPolicy
{
    use ConsultsGrants;                                        // даёт $this->granted(...)

    #[Decides(CabinetPermission::OrdersView)]
    public function view(User $user, Order $order): ?bool
    {
        if ($order->user_id === $user->id) {
            return true;                                        // своё — всегда
        }
        return $this->granted(CabinetPermission::OrdersViewAny, $user, on: $order->store);  // чужое — по выданному праву
    }
}
```

- Привязка: `#[Decides(Perm::X)]` на методе политики; политики подключаются к панели `->policies(OrderPolicy::class)`
  или `->discoverPolicies(app_path('Policies/Cabinet'))` (результат попадает в кэш каталога).
- Возврат `true`/`false` — решение; `null` — «не знаю», тогда решают механики, дающие права.
- `granted()` спрашивает только механики, дающие права (без политик и хуков) — рекурсии нет.
- Право, решаемое политикой, по умолчанию **не выдаётся** через БД (иначе выдача обошла бы логику политики). Если
  нужно и то и другое: `#[Decides(Perm::X, assignable: true)]`; тогда политика сама решает, как учитывать выдачу.
- Gate: `->gates([CabinetPermission::Beta => 'beta-access'])` — AzGuard вызывает существующую ability Laravel.
- AzGuard не регистрирует политики в Laravel (`Gate::policy`) и не генерирует их: приложение само решает, какие
  политики ещё используются Laravel напрямую. Двух параллельных путей для одного права нет (N19).
- Текущие `#[GateAbility]`, `AuthorizesPermission`, `PolicyDiscovery` переходят в эту механику
  ([03](03-glossary-and-renames.md)).

<a id="d54"></a>
### D54 — Схема панели для интерфейсов

**Кратко:** панель умеет рассказать о себе: какие права есть и как они сгруппированы, какие можно выдать вручную,
какие решаются кодом или политикой, какие роли редактируются, какие поля заполнять. По этой схеме Filament (или любой
свой интерфейс) строит редакторы сам.

**Решение.** `AzGuard::panel($id)->schema(): PanelSchema` (`@api`, неизменяемое значение; `toArray()` для фронтенда):

| Часть схемы | Что в ней |
|---|---|
| `permissions()` | имя, подпись, группа, описание; **как получается**: механики, которые могут дать право (`database`, `code`, `relations`, …) или политика/Gate; `assignable` — можно ли выдать вручную; в каких типах сущностей |
| `roles()` | ключ, подпись; где определена (`code`/`database`); редактируются ли права; назначается вручную или автоматически; права |
| `fields()` | свои поля назначений и прямых прав: тип, подпись, правила, откуда (модель, плагин) |
| `contexts()` | типы сущностей: подпись, как искать (директория) |
| `subjects()` | модели субъектов, подпись, как искать |
| `writable()` | есть ли на панели механика, принимающая изменения (если нет — редакторы не показываются) |

Панель без механики БД — «только чтение»: схема есть (для документации и отладки), редактирования нет (Q20).

<a id="d55"></a>
### D55 — Хуки панели

**Кратко:** в любую проверку и любое изменение можно вмешаться без правки AzGuard: переопределить решение, запретить,
дополнить изменение, отреагировать на него.

**Решение.**

| Хук | Когда | Может | Контракт |
|---|---|---|---|
| `before` | до механик | сказать «да», «нет» или «не знаю» (как `Gate::before`) | `BeforeHook::before(AccessRequest, EvaluationContext): ?bool` |
| `restrict` | после механик | только запретить | `Restriction` (D20) |
| `after` | после решения | наблюдать | `AfterHook::after(AccessRequest, Decision): void` |
| `changing` | до записи | изменить или отменить изменение | `ChangingHook::changing(Change): Change` |
| `changed` | после commit | реагировать | `ChangedHook::changed(AppliedChange): void` |

- Хуки задаются на панели (замыкание в провайдере или класс), плагином или для всех панелей через
  `AzGuard::configurePanels()`.
- Порядок — порядок регистрации; суперадмин — всегда первый `before`.
- Laravel-события (D28) — второй способ реагировать, без изменения панели.
