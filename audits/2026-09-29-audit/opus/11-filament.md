# 11 — Filament: редакторы по схеме панели

Решения: [D23](02-decisions.md#d23), [D30](02-decisions.md#d30), [D46](02-decisions.md#d46), [D54](02-decisions.md#d54).
Находки: N02, N18, N19. Пакет `axiomasoft/azguard-filament` работает только через публичный API ядра: своей логики
прав и прямых записей в модели в нём нет.

## 1. Две разные «панели» — простыми словами

- **Панель Filament** — экран админки: меню, ресурсы, страницы (`/admin`).
- **Панель AzGuard** — конструктор прав части приложения.

Filament-плагин связывает их двумя настройками:

| Настройка | Что значит | Пример |
|---|---|---|
| `guardPanel('admin')` | права на ресурсы, страницы и виджеты **этой** Filament-панели живут в панели AzGuard `admin`; она же — текущая панель в запросах Filament | `admin:orders.view_any` |
| `manages(['admin', 'seller'])` | роли и выдачи каких панелей AzGuard можно редактировать из этой админки | сотрудник назначает роли и сотрудникам, и продавцам |

```
Filament /admin ──guardPanel──► AzGuard admin   (кто может открыть «Заказы» в админке)
        │
        └────────manages──────► AzGuard admin, seller   (чьи роли и выдачи редактируются отсюда)
```

Кто может открыть редакторы ролей и выдач — решают **обычные права** ресурсов Filament в `guardPanel`, как для любой
другой страницы админки ([D23](02-decisions.md#d23)). AzGuard не знает, кто в приложении «администратор».

## 2. Плагин

```php
// app/Providers/Filament/AdminPanelProvider.php (Filament)
->plugin(
    AzGuardPlugin::make()
        ->guardPanel('admin')
        ->manages(['admin', 'seller'])          // null = все панели AzGuard, в которых есть что редактировать
        ->enforce()                             // ресурсы без права закрыты
        ->abilities([...])
        ->resources(roles: true, assignments: true, directPermissions: true, panels: true, doctor: true)
        ->formExtensions(ReasonFieldExtension::class)   // поля от плагинов (§6)
)
```

- Состояние — только в экземпляре плагина; `config()` не перезаписывается (N18). Значения по умолчанию — из
  `config/azguard-filament.php` ([07 §4](07-configuration.md#4-configazguard-filamentphp)).
- Права ресурсов Filament попадают в каталог панели AzGuard обычным путём — плагином AzGuard `azguard/filament`,
  который Filament-плагин подключает к `guardPanel` через `AzGuard::configurePanel()`.
- `checkPolicyExistence(false)` на классах ресурсов не вызывается (это общее статическое состояние). `FilamentGate`
  отвечает на вопросы Gate по моделям ресурсов этой Filament-панели, поэтому отдельные политики не нужны (N19). Если
  у модели есть своя политика с `#[Decides]`, она работает как механика панели (D53).
- id Filament-плагина — `azguard`.

## 3. Ключи прав ресурсов, страниц, виджетов

Локальное имя `{resource}.{ability}` в панели `guardPanel`, где `resource` — `Resource::getSlug()`; страница —
`pages.{slug}`, виджет — `widgets.{kebab(class_basename)}` **с проверкой уникальности** (коллизия → ошибка при
загрузке с подсказкой задать `protected static ?string $azguardKey`). `class_basename` модели не используется (N18).
Подписи прав — из `getModelLabel()`/`getNavigationLabel()`, группа — из навигационной группы. Всё это попадает в схему
панели, как права из enum.

## 4. Проверки доступа

| Что проверяется | Как | Если субъекта или плагина определить не удалось |
|---|---|---|
| Ресурсы (viewAny, view, create, update, delete, …) | `FilamentGate` через `Gate::before`: ability Filament + модель → имя права → решение панели `guardPanel` | `false` при `enforce` |
| Страницы | `AuthorizesPage::canAccess()` → `hasPermissionTo()` в `guardPanel` | `false` при `enforce` (сейчас `true`, N18) |
| Виджеты | `AuthorizesWidget::canView()` | `false` при `enforce` |
| Вход в Filament-панель | `entry()` панели AzGuard (если задано) через `canAccessPanel()` | `false` |

## 5. Редакторы по схеме панели

Все редакторы работают с **выбранной панелью AzGuard** из `manages`. Панель выбирается фильтром в таблицах и первым
полем в формах. Всё остальное форма берёт из `AzGuard::panel($id)->schema()` ([D54](02-decisions.md#d54)): группы
прав, какие права выдаются галочкой, какие роли редактируются, какие поля заполнять. При смене панели форма
перестраивается. Панели без механики БД в `manages` не показываются (редактировать нечего), но видны на странице
«Панели».

### 5.1 `RoleResource`

| Что | Роль из кода | Роль из БД |
|---|---|---|
| ключ | только чтение | задаётся при создании, потом только чтение |
| подпись, описание | только чтение (из кода) | редактируется |
| права | список из кода, только чтение | галочки по группам схемы; права, которые решает политика или код, показаны с пометкой «решается политикой» и не отмечаются |
| свои поля роли | — | по схеме (§6) |
| как назначается | «вручную» или «автоматически: правило в коде» | вручную |
| удаление | нельзя (роль в коде) | `roles()->delete()` — вместе с назначениями, одной транзакцией |
| держатели | список назначений; снятие — `removeRole()` | то же |

Сохранение прав роли — `roles()->syncPermissions($key, $permissions, expectedFingerprint: …)`: если права успели
изменить в другой вкладке, форма просит обновить страницу. Поля `class_name` нет (N02): классов в данных нет вообще.

### 5.2 `RoleAssignmentResource` и `DirectPermissionResource`

- Таблицы — модели **панели** (включая свои модели вроде `AdminRoleAssignment`), только чтение. Фильтры: панель,
  роль или право, сущность, «истекает до», «кто выдал», свои поля. Подпись субъекта — `SubjectDirectory::describe()`,
  сущности — `ContextDirectory::describe()`.
- Создание: панель → субъект (поиск через директорию панели, лимит 50, без загрузки всех пользователей) → роль (только
  назначаемые вручную) или право (только `assignable`) → сущность (типы, которые принимает панель) → срок → свои поля.
- Сохранение — `$subject->inPanel($id)->assignRole(..., on:, expiresAt:, fields:)` / `givePermissionTo(...)`. Свои
  поля передаются в `fields:`, а не пишутся в модель.
- Массовый отзыв — одна транзакция, одна новая версия, событие на каждую строку.
- Редактирование строки — срок и свои поля.
- Автоматические роли и права из политик в этих таблицах не видны (их нет в БД). Чтобы понять, откуда у человека
  право, есть действие «Почему?» → `explain()`.

### 5.3 `PanelsPage` и `DoctorPage`

- `PanelsPage` — то же, что `azguard:panels:list --settings --sources`: панели, их механики, итоговые настройки и
  откуда взято каждое значение, схема прав. Только чтение.
- `DoctorPage` — `azguard:doctor --json` с группировкой по важности.

Доступ к обеим — обычные права страниц Filament.

## 6. Свои поля в формах

Поля берутся из схемы панели ([05 §8](05-php-api.md#8-схема-панели)); Filament-пакет заранее о них ничего не знает.

| Откуда поле | Как попадает в схему | Пример |
|---|---|---|
| Своя модель панели | `azguardFields()` модели | `department_id` у `AdminRoleAssignment` |
| Плагин AzGuard | плагин добавляет поле в панель (`$panel->fields(...)` в `register()`) | «причина выдачи» |
| Особая форма | `FilamentFormExtension` в Filament-плагине — когда нужен свой компонент Filament | выбор отдела деревом |

```php
namespace AzGuard\Filament\Contracts;

interface FilamentFormExtension
{
    public function appliesTo(PanelSchema $schema, FieldTarget $target): bool;     // Role | Assignment | DirectPermission
    /** @return array<string, Component> компоненты по имени поля схемы */
    public function components(PanelSchema $schema, FieldTarget $target): array;
}
```

Правила полей: значения уходят в `fields:`, запись — только через пайплайн изменений; серверная проверка —
`azguardFields()` и хуки `changing`, форма показывает те же правила как подсказку; поле, которого нет в схеме,
отклоняется (`InvalidChangeFieldsException`).

## 7. Генерация (`azguard:filament:generate`)

Создаёт enum прав для ресурса с локальными именами и `#[Describe]` и подключает его к `guardPanel`. Генерация
политик удаляется: Gate-мост делает их лишними (N19). Если приложению нужна логика «только свои записи», оно пишет
обычную политику с `#[Decides]`. Проверка «устаревший enum» (enum есть, ресурса нет) — в doctor.

## 8. Тесты пакета (обязательные)

| Сценарий | № в [14](14-verification.md) |
|---|---|
| `class_name`/`definition` не принимаются ни формой, ни Livewire-payload'ом; роль из кода нельзя изменить из UI | V23 |
| Две Filament-панели с разными `guardPanel` не влияют друг на друга (нет глобального конфига) | V24 |
| Страница с `AuthorizesPage` закрыта для пользователя без права и без `AzGuardSubject` | V25 |
| Поиск субъекта среди 10 000 пользователей — один запрос с `LIMIT` | V26 |
| Редактор ролей строит галочки по схеме: права из политики не отмечаются, роли из кода только читаются | V61 |
| Форма назначения показывает поля своей модели и плагина; при смене панели набор меняется; неизвестное поле отклоняется | V62 |
| Панель без механики БД не показывается в редакторах, но видна на странице «Панели» | V63 |
