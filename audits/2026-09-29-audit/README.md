# AzGuard — дополнительный архитектурный аудит и Research

Дата: **2026-09-29**. Автор дополнительного анализа: Codex. Исходный срез кода: `253cbf4cce0226545cd96ca8c6bcbefe329b1403`.

Материалы подготовлены для последующей глубокой проработки **Opus 5.5**, которому Perplexity может быть недоступен. Здесь собраны проверка исходного аудита, самостоятельные находки, варианты целевой архитектуры и исследования с сохранёнными запросами и ответами. Это исследовательский пакет, а не исполнительный план или согласованная спецификация нового API.

## Позиция владельца

В этой задаче **неприкосновенного кода нет**. Допускаются любые изменения структуры, классов, API и названий. Приоритеты: гибкость, конфигурируемость, архитектурная целостность, чистый API и понятный словарь. Совместимость и стоимость перехода нужно учитывать при сравнении вариантов, но они не запрещают выбрать лучшую новую архитектуру.

Поэтому ранние исследования R01–R23, сформулированные до этого уточнения и местами предпочитающие минимальные изменения, дополнены R25–R30 о свободном redesign. Их консервативные рекомендации не являются ограничением задачи.

## Как различать доказательства

- **Наблюдение по коду** — проверен конкретный участок текущего репозитория; это не обещание исчерпывающего покрытия.
- **Воспроизведено** — есть небольшой исполняемый probe и его сохранённый результат.
- **Условный риск** — сценарий следует из кода, но зависит от deployment/config/расширения; сквозная эксплуатация не заявляется.
- **Предложение** — мой архитектурный выбор, а не установленный дефект.
- **Perplexity synthesis** — сохранённый ответ внешней модели. Его отдельные утверждения не считаются проверенными автоматически; опорные факты сверены в [реестре первичных источников](Research/primary-sources.md).

## Передача Opus

Предлагаю Opus сформировать один согласованный итоговый аудит/дизайн: выбрать архитектурный вариант, зафиксировать семантику authorization и extension contracts, убрать противоречия между решениями и оценить переход. Не нужно автоматически реализовывать все найденные идеи или считать кодовые эскизы утверждённым API.

Самые важные вопросы: обязательные ограничения против additive grants; scope superadmin; истинная консистентность отзыва; инъективная идентичность контекста; trust boundary tenant membership; единый mutation API для CLI/UI/приложения; честная конфигурируемость persistence и extension composition.

## Ограничения

В этой задаче runtime-код пакетов не изменялся. Полный тестовый, mutation, DB/Redis и dependency-resolver matrix прогоны не выполнялись: это сбор аудита и исследований. Probe не обращается к БД или cache backend. Исторические зелёные отчёты не объявляются результатами этой сессии.

Все начальные изменения `.agents/` и `.codex/config.toml` сохранены для общего commit по просьбе владельца; это ранее существовавшие изменения окружения, а не результат архитектурного redesign.
