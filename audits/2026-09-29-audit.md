Полноценный аудит подтверждает: **AzGuard имеет сильную инженерную основу, но фиксировать API и выпускать 1.0 пока рано**. Главные препятствия — размытая граница публичного API, зависимость расширений от внутренних классов core, чрезмерно широкая поверхность Eloquent/traits и отсутствие сквозного контроля совместимости для `context` и `filament`.

## Критические блокеры

### API размечен не полностью

Автоматизированная классификация исходников показывает:

| Пакет | Типов | `@api` | `@internal` | Без статуса |
|---|---:|---:|---:|---:|
| core | 151 | 32 | 16 | 103 |
| context | 19 | 0 | 1 | 18 |
| filament | 25 | 0 | 0 | 25 |

То есть API snapshot защищает только небольшую подгруппу core. Для `context` и `filament` публичная граница фактически не определена.

Неразмеченный класс нельзя считать безопасным компромиссом. Для пользователя Composer-пакета любой autoloadable public class является потенциальным API, если документация и tooling не говорят обратного.

Нужно ввести исчерпывающую классификацию:

- `@api` — гарантированная SemVer-совместимость;
- `@spi` — extension points для интеграционных пакетов;
- `@internal` — запрещён для внешнего использования;
- `@experimental` — может изменяться только по явно описанной политике;
- `@deprecated` — содержит версию появления deprecation и planned removal.

CI должен падать, если autoloadable symbol не имеет одного из статусов. Модель «не отмечено — значит internal» недостаточно надёжна, пока это не закреплено тестом и документацией.

### Расширения используют internals core

`azguard-context` импортирует как минимум четыре `@internal` типа core:

- `RevisionedPermissionModelWrites`;
- `PermissionCache`;
- `PermissionStateRevision`;
- `SubjectIdentity`.

Кроме того, он зависит от нескольких неразмеченных типов:

- `PanelResolver`;
- `PermissionName`;
- `ResolvesUserModel`;
- базовых exceptions.

`azguard-filament` использует как минимум два internal-типа:

- `PermissionStateRevision`;
- `RequestState`.

Дополнительно он напрямую зависит от многочисленных неразмеченных классов:

- `AzGuardManager`;
- `Config`;
- `AzGuardDiagnostics`;
- `Role`;
- `RolePermission`;
- `DirectGrant`;
- `PanelResolver`;
- `RolePermissionSynchronizer`;
- concrete permission definitions.

Это означает, что core нельзя независимо рефакторить без риска сломать официальные пакеты. Изоляция сейчас существует на уровне Composer-манифестов, но не на уровне архитектурных границ.

Необходимо выделить стабильный SPI:

```php
interface PermissionCacheInvalidator
{
    public function forget(SubjectId $subject, PanelId $panel): void;

    public function invalidateAll(): void;
}

interface PermissionStateStore
{
    public function currentRevision(): int;

    public function advanceRevision(): int;
}

interface SubjectIdentifier
{
    public function identify(object $subject): SubjectId;
}

interface RoleAdministration
{
    public function permissions(RoleId $role): RolePermissionSet;

    public function replacePermissions(
        RoleId $role,
        RolePermissionSet $permissions,
    ): RolePermissionChangeSet;
}
```

После этого:

- context зависит только от SPI;
- Filament вызывает application services;
- Eloquent-модели и cache implementation остаются internal;
- architecture tests запрещают импорт `AzGuard\Internal`, `AzGuard\Runtime` и persistence implementation из других пакетов.

PSR-11 полезен как общий интерфейс контейнера, но сам по себе не решает проблему service locator: стандарт определяет только `get()` и `has()`, а не архитектурную границу приложения. Поэтому доменная часть не должна использовать глобальный `app()` даже при наличии стандартизированного контейнера. [php-fig](https://www.php-fig.org/psr/psr-11/)

### API snapshot неполон

Текущий snapshot — хорошая практика, но он проверяет главным образом:

- типы с `@api`;
- public methods;
- имена параметров;
- наличие default value;
- facade `@method` declarations.

Он не гарантирует стабильность:

- public constants;
- значений constants;
- enum cases и backed values;
- public properties;
- реализуемых interfaces;
- parent class;
- traits;
- attributes;
- generic annotations;
- exception contracts;
- фактических default values;
- `final`, `readonly`, `abstract`;
- variance;
- сериализованной формы DTO;
- событий;
- config keys;
- CLI commands;
- database schema.

Особенно опасно игнорирование значений по умолчанию. Изменение:

```php
public function check(bool $strict = false): bool
```

на:

```php
public function check(bool $strict = true): bool
```

не изменит текущий snapshot, но изменит поведение всех вызовов без аргумента.

Рекомендуется использовать два слоя:

1. Roave Backward Compatibility Check для PHP-level BC.
2. Собственный contract snapshot для семантики AzGuard.

Roave позиционируется именно как инструмент сравнения двух revisions API и обнаружения BC breaks. Его нельзя считать полной заменой собственным тестам, потому что config, migrations, event payload и permission grammar выходят за пределы обычного PHP API. [github](http://github.com/orgs/Roave/repositories)

### Модели являются неявным API

`Role`, `RolePermission`, `DirectGrant` и `ModelHasScope` доступны пользователю, используются Filament-пакетом и содержат public methods, relationships и scopes.

Это приводит к нескольким проблемам:

- невозможно безопасно переименовать колонку или relationship;
- пользователь может выполнять bulk update;
- persistence schema превращается в public contract;
- модельные events становятся частью корректности cache invalidation;
- Filament вынужден знать внутреннюю структуру хранения;
- смена Eloquent на другой storage становится практически невозможной.

Laravel официально предупреждает, что mass update и mass delete не вызывают model events, потому что модели не загружаются. Следовательно, invalidation через `created`, `updated` и `deleted` не может быть абсолютной гарантией. [laravel](https://laravel.com/docs/12.x/eloquent.md)

Нужно выбрать один из двух вариантов.

**Строгий вариант:**

- модели помечаются `@internal`;
- все записи выполняются application services;
- Filament работает через administration API;
- прямые записи в модели официально unsupported.

**Расширяемый вариант:**

- public contracts для repositories;
- default Eloquent implementation;
- пользователь может заменить хранилище;
- все writes обязаны идти через repository;
- cache revision управляется transaction coordinator.

Для стабильного пакета предпочтительнее строгий вариант. Публичные Eloquent-модели создают слишком большую поверхность совместимости.

### Установка запускает общую миграцию

`guard:install` публикует config и вызывает обычную команду `migrate`. Это может выполнить не только миграции AzGuard, но и любые pending migrations приложения и других пакетов.

Для install-команды библиотеки это слишком сильный побочный эффект.

Рекомендуемое поведение:

```text
php artisan guard:install
  - публикует config;
  - проверяет environment;
  - показывает pending AzGuard migrations;
  - не запускает общую migrate без явного подтверждения.

php artisan guard:install --migrate
  - требует confirmation;
  - в production требует --force;
  - явно предупреждает, что Laravel выполнит все pending migrations.
```

Нужен также отдельный документ:

- какие миграции можно публиковать;
- можно ли редактировать опубликованные миграции;
- как обновляется схема;
- когда допускается destructive migration;
- как поддерживаются custom table names;
- как обновляться с каждой опубликованной minor-версии.

### Идентичность роли нестабильна

Сейчас роль связана одновременно с:

- database ID;
- `name`;
- PHP `class_name`;
- классом, реализующим `RoleInterface`.

Это создаёт неоднозначность:

- является ли переименование класса переименованием роли;
- является ли `name` стабильным machine key или display name;
- что делать при переносе класса в другой namespace;
- как различать две роли с одинаковым коротким назначением;
- как выполнять aliases и migrations.

Следует ввести явный immutable identifier:

```php
final readonly class RoleId
{
    public function __construct(public string $value) {}
}
```

Например:

```php
final class EditorRole implements RoleDefinition
{
    public static function id(): RoleId
    {
        return new RoleId('documents.editor');
    }

    public function label(): string
    {
        return 'Documents editor';
    }
}
```

В БД должны храниться:

- `role_key` — стабильная идентичность;
- `label` или переводимый label — отображение;
- `definition_class` — текущая implementation binding;
- optional aliases для миграции старых ключей.

Class name не должен быть постоянным бизнес-идентификатором.

## Permission grammar

### Panel ID недостаточно валидируется

`Panel::id()` и `PanelResolver` проверяют длину, но не задают строгую грамматику ID.

Потенциально допускаются:

- пустая строка;
- точка;
- `*`;
- `**`;
- пробелы;
- control characters;
- строка, конфликтующая с permission separator;
- идентификатор с неоднозначной Unicode-нормализацией.

Поскольку panel ID становится первым сегментом permission key, его grammar должна быть строже общей permission grammar.

Рекомендуемый формат:

```regex
^[a-z][a-z0-9_-]{0,63}$
```

Дополнительно:

- lowercase canonical form;
- запрет `*`, `**`, `{...}`;
- запрет `.` внутри ID;
- запрет пустой строки;
- duplicate registration вызывает exception;
- explicit `replacePanel()` существует отдельно, если действительно нужен.

Сейчас повторная регистрация того же ID молча заменяет panel в массиве. Для boot-time registry это скрывает ошибки конфигурации.

### Строки и enums ведут себя по-разному

`PermissionName::resolve()` рассматривает обычную строку как уже полностью разрешённый key, тогда как enum или permission class проходит panel scoping.

Это создаёт неочевидную асимметрию:

```php
$user->hasPermission('documents.view', 'app');
$user->hasPermission(DocumentsPermission::View, 'app');
```

Два визуально эквивалентных вызова могут проверять разные keys.

Лучше разделить типы:

```php
Ability::qualified('app.documents.view');
Permission::local('documents.view');
```

Или разные методы:

```php
$authorizer->allows($subject, AbilityKey::from('app.documents.view'));
$panel->ability(PermissionKey::from('documents.view'));
```

Нельзя заставлять библиотеку угадывать, является строка local или qualified.

### Термины пересекаются

В коде одновременно используются:

- permission;
- ability;
- grant;
- direct grant;
- source;
- definition;
- permission key;
- permission name.

Нужен обязательный glossary:

| Термин | Рекомендуемое значение |
|---|---|
| Permission | Объявленная возможность, доступная для выдачи |
| Ability | Конкретный запрос авторизации |
| Grant | Источник разрешения для subject |
| Role | Именованный набор grants |
| Decision | Итог авторизации |
| Panel | Namespace разрешений |
| Context | Дополнительная область применения |
| Catalog | Набор объявленных permissions |
| Source | Поставщик grants |

После фиксации glossary названия классов должны быть приведены к нему.

## Public API

### Manager перегружен

`AzGuardManager` совмещает:

- panel registry;
- current panel state;
- permission resolution;
- catalog builders;
- grant factories;
- context bridge;
- abilities projection.

Это central service locator, а не одна ответственность.

Рекомендуемое разделение:

```php
interface Authorizer
{
    public function decide(
        Subject $subject,
        Ability $ability,
        ?AuthorizationContext $context = null,
    ): Decision;

    public function allows(
        Subject $subject,
        Ability $ability,
        ?AuthorizationContext $context = null,
    ): bool;
}

interface PanelRegistry
{
    public function register(PanelDefinition $panel): void;

    public function find(PanelId $id): ?PanelDefinition;

    /** @return list<PanelDefinition> */
    public function all(): array;
}

interface PermissionCatalog
{
    public function find(Ability $ability): ?PermissionDefinition;
}

interface DirectGrantService
{
    public function grant(GrantDirectPermission $command): DirectGrantId;

    public function revoke(RevokeDirectPermission $command): void;
}
```

Facade может оставаться удобным entry point, но должна делегировать узким сервисам.

### Getter naming непоследователен

Встречаются:

- `getPanels()`;
- `getId()`;
- `getLabel()`;
- `getBasePath()`;
- `getPermissionEnums()`;
- `currentPanel()`;
- `permissions()`;
- `panel()`.

Для нового API лучше выбрать единый стиль:

```php
$panel->id();
$panel->label();
$registry->panels();
$registry->find($id);
$context->current();
```

При этом fluent mutation и getter не должны иметь одно имя. Ещё лучше сделать definitions immutable и задавать их через named constructor или builder.

### Panel mutable после регистрации

`Panel` хранится в singleton manager, но остаётся изменяемым. Код, сохранивший ссылку, может после регистрации изменить:

- ID;
- label;
- namespace;
- base path;
- permission enums;
- role classes;
- scoping mode.

Это может нарушить соответствие между ключом массива registry и фактическим `Panel::getId()`.

Нужно:

- сделать `PanelDefinition` `final readonly`;
- использовать отдельный `PanelBuilder`;
- после `build()` возвращать immutable object;
- registry не должен принимать незавершённый mutable object.

### Builder выполняет операции

`GrantBuilder` и `ContextGrantBuilder` не просто строят value object, а выполняют database writes и dispatch events. Название `Builder` обычно предполагает подготовку объекта или запроса, но не application service.

Возможные названия:

- `DirectGrantService`;
- `DirectGrantManager`;
- `GrantIssuer`;
- `ContextGrantService`.

Если fluent API важен, следует разделить:

```php
$request = GrantRequest::for($user)
    ->permission($permission)
    ->panel($panel)
    ->expiresAt($expiresAt);

$grants->grant($request);
```

### Traits слишком велики

`HasRoles`, `HasPermissions`, `HasDirectGrants`, `HasScopedRoles` добавляют в host-модель значительное количество методов и Eloquent relationships.

Trait API трудно развивать:

- методы могут конфликтовать с приложением;
- return types зависят от Eloquent;
- метод нельзя удалить без BC break;
- внутреннюю реализацию сложно заменить;
- IDE показывает persistence API рядом с domain API.

Рекомендуемый user-facing trait должен быть тонким:

```php
trait HasAzGuard
{
    public function authorizationSubject(): Subject
    {
        return Subject::fromModel($this);
    }

    public function canAzGuard(Ability|string $ability): bool
    {
        return app(Authorizer::class)->allows(
            $this->authorizationSubject(),
            Ability::from($ability),
        );
    }
}
```

Relationships лучше вынести в internal persistence concern либо документировать как explicitly unstable.

## Gate integration

Core регистрирует глобальный `Gate::before()`. Это означает, что AzGuard оказывается перед всеми Laravel policies и gates.

Нужно формально определить:

- какие ability names принадлежат AzGuard;
- когда callback возвращает `null`;
- когда он может вернуть `false`;
- может ли отсутствие panel заблокировать unrelated Laravel Gate;
- что происходит для abilities, которых нет в catalog;
- как coexist с другими authorization packages.

Безопасная модель:

```php
if (! $azGuardAbilityClassifier->owns($ability)) {
    return null;
}

return $authorizer->allows(...);
```

Возврат `false` из `Gate::before()` является окончательным deny и не даёт policy обработать запрос. Поэтому unknown abilities должны давать `null`, если только пользователь явно не включил exclusive authorization mode.

Нужны integration tests:

- обычная Laravel policy без AzGuard;
- AzGuard ability;
- unknown ability;
- несколько `Gate::before`;
- super-admin;
- отсутствие panel;
- strict panel mode;
- queued job;
- Octane request reuse.

## Context package

### Context должен быть extension, а не privileged friend

Сейчас context знает о cache implementation, revision storage и subject identity core. Это делает его привилегированным модулем внутри monolith, несмотря на отдельный Composer package.

Core должен предоставить context extension API:

```php
interface PermissionLayer
{
    public function apply(
        Subject $subject,
        PanelId $panel,
        PermissionSet $base,
        ?AuthorizationContext $context,
    ): PermissionSet;
}

interface AuthorizationContextProvider
{
    public function current(): ?AuthorizationContext;
}

interface AuthorizationContextScope
{
    public function run(
        AuthorizationContext $context,
        Closure $operation,
    ): mixed;
}
```

Особенно важно иметь scope API:

```php
$contexts->run($context, function () {
    // context гарантированно восстановится через finally
});
```

Это безопаснее ручного `setCurrentContext()` и обязательно для:

- nested contexts;
- queue workers;
- Octane;
- tests;
- exceptions;
- concurrent fibers.

### Cache key должен учитывать контекст

Для contextual authorization cache identity должна включать как минимум:

```text
subject type
subject ID
panel ID
context type
context ID
merge strategy / policy version
permission-state revision
```

Если context влияет на итоговый `PermissionSet`, но отсутствует в cache key, возможна утечка permissions между workspaces.

Нужны property-based или matrix tests:

- subject A/context X;
- subject A/context Y;
- subject B/context X;
- context absent;
- global-plus-context;
- context-only;
- deny-without-context;
- context switch в одном long-running process;
- invalidation только одного context;
- bulk revoke.

## Filament package

### Filament напрямую работает с persistence

Filament-пакет импортирует модели, config internals, synchronizer, state revision и request state. Это делает UI зависимым от реализации storage.

Filament должен использовать отдельный administrative API:

```php
interface RoleAdministration
{
    public function search(RoleQuery $query): RolePage;

    public function get(RoleId $id): RoleView;

    public function updatePermissions(
        RoleId $id,
        RolePermissionSelection $selection,
    ): RolePermissionChangeSet;
}

interface GrantAdministration
{
    public function search(GrantQuery $query): GrantPage;

    public function revoke(DirectGrantId $id): void;
}
```

Filament Resources могут иметь собственные projection models или работать через service-backed pages. Если Eloquent Resources всё же сохраняются, зависимость должна идти на явно публичные adapter models, а не на core domain models.

### Filament API тоже нужно классифицировать

Следует решить, что является supported API:

- `AzGuardPlugin`;
- plugin configuration methods;
- page/widget traits;
- permission discovery hooks;
- generated enum schema;
- resource extension points;
- custom resource replacement.

Всё остальное нужно пометить `@internal`.

## События

События grants и roles потенциально являются публичной интеграционной поверхностью, поскольку документация предлагает использовать listeners для cache, audit и notifications.

Но они:

- не помечены как `@api`;
- передают Eloquent models;
- используют разные формы subject;
- не имеют event ID;
- не имеют occurred-at timestamp;
- не имеют causation/correlation metadata, кроме частичного `AccessDecision`;
- зависят от текущей serializable формы моделей.

Для стабильных integration events предпочтительны primitive/value payloads:

```php
final readonly class DirectGrantCreated
{
    public function __construct(
        public EventId $eventId,
        public SubjectId $subject,
        public PanelId $panel,
        public Ability $ability,
        public DirectGrantId $grantId,
        public DateTimeImmutable $occurredAt,
        public ?CorrelationId $correlationId,
    ) {}
}
```

Если события остаются только process-local Laravel events, это также нужно прямо указать. PSR-14 определяет общий механизм синхронной диспетчеризации событий и требует возвращать тот же event object, но переход на PSR-14 имеет смысл только при реальной цели framework interoperability. Для чисто Laravel-пакета важнее стабильный payload contract, чем формальное внедрение PSR-14. [php-fig](https://www.php-fig.org/psr/psr-14/)

## Persistence schema

### Имена таблиц непоследовательны

Текущие defaults смешивают:

- `roles`;
- `model_has_roles`;
- `model_has_scopes`;
- `az_guard_role_permissions`;
- `az_direct_grants`;
- `az_guard_permission_state`.

Пока пакет не вышел в production, стоит выбрать единый prefix:

```text
az_guard_roles
az_guard_role_assignments
az_guard_scoped_role_assignments
az_guard_role_permissions
az_guard_direct_grants
az_guard_permission_state
az_guard_context_roles
```

Причины:

- меньше collision с host application;
- меньше collision со Spatie;
- проще диагностика;
- проще backup/export;
- очевидная ownership schema;
- проще uninstall tooling.

### Pivot naming нужно нормализовать

`model_has_roles` и `ModelHasScope` используют разные грамматические модели. Лучше выбрать domain terminology:

- `RoleAssignment`;
- `ScopedRoleAssignment`;
- `DirectGrant`;
- `ContextGrant`.

Класс `ModelHasScope` звучит как технический pivot, а не domain concept. Рекомендуемое имя: `ScopedRoleAssignment`.

### Configurable tables не равны configurable schema

Table names настраиваются, но column names в implementation широко захардкожены:

- `model_type`;
- `model_id`;
- `grantable_type`;
- `grantable_id`;
- `panel_id`;
- `permission_key`;
- `scope_entity_type`;
- `scope_entity_id`.

Это нормально, если колонки объявлены частью стабильной schema. Не следует создавать иллюзию полной storage-customizability.

Нужно прямо решить:

- table names configurable;
- model classes replaceable;
- column names fixed;
- indexes fixed;
- morph key strategy configurable до первой миграции;
- изменение morph strategy после установки требует отдельной migration guide.

## Configuration

`Config` содержит около 40 static accessors и одновременно:

- валидирует model classes;
- читает table names;
- управляет feature flags;
- выбирает resolver/matcher;
- проверяет cache settings;
- определяет panels;
- управляет scaffold settings.

Он полезен как internal adapter к Laravel config, но не должен становиться публичным extension API.

Рекомендуется разделить immutable settings:

```php
final readonly class AuthorizationSettings {}
final readonly class PersistenceSettings {}
final readonly class CacheSettings {}
final readonly class PanelSettings {}
final readonly class ScaffoldSettings {}
```

Laravel service provider собирает их из `config()`, после чего domain/application services получают settings через constructor injection.

Это:

- облегчает unit testing;
- убирает hidden global state;
- позволяет валидировать config один раз;
- уменьшает число runtime config reads;
- делает зависимости класса видимыми.

## Package structure

Не рекомендуется немедленно создавать шесть-семь Composer-пакетов. Большое число пакетов увеличит release coordination и compatibility matrix.

Практичная структура — сохранить три публикуемых пакета, но строго разделить слои внутри.

```text
packages/
  core/
    src/
      Contracts/
        Authorization/
        Catalog/
        Grants/
        Panels/
        Roles/
        Cache/
      Domain/
        Ability/
        Decision/
        Panel/
        Role/
        Subject/
      Application/
        Authorization/
        Grants/
        Roles/
        Catalog/
      Infrastructure/
        Cache/
        Persistence/
          Eloquent/
        Registry/
      Laravel/
        Console/
        Facades/
        Http/
        Providers/
        Blade/
      Internal/

  context/
    src/
      Contracts/
      Domain/
      Application/
      Infrastructure/
        Eloquent/
      Laravel/
        Console/
        Http/
        Providers/
      Internal/

  filament/
    src/
      Contracts/
      Plugin/
      Resources/
      Pages/
      Support/
      Internal/
```

Namespace должен следовать PSR-4 и однозначно соответствовать файловой структуре. [php-fig](https://www.php-fig.org/psr/psr-4/)

Отдельный `azguard-contracts` стоит создавать только при выполнении хотя бы одного условия:

- планируется не-Laravel engine;
- contracts должны иметь другой release cadence;
- несколько независимых adapters используют один domain API;
- core требуется без Illuminate dependencies.

Иначе отдельный contracts package добавит complexity без достаточной пользы.

## Composer isolation

Root package autoloads и тестирует все packages вместе. Это удобно для разработки, но может скрыть:

- отсутствующую dependency в package composer.json;
- случайное использование root dev dependency;
- неправильный service provider discovery;
- несовместимость package autoload;
- неверные constraints;
- циклические optional dependencies.

Каждый package должен иметь отдельный CI job:

```text
composer install --working-dir=packages/core
composer install --working-dir=packages/context
composer install --working-dir=packages/filament
```

И отдельные test suites.

Для `context` и `filament` constraint `^0.3` означает совместимость только внутри линии `0.3.x`; Composer трактует caret для `^0.3.2` как диапазон до `0.4.0`, потому что major равен нулю. Нужно решить, выпускаются ли официальные пакеты lockstep или независимо. [getcomposer](https://getcomposer.org/doc/articles/versions.md)

Если lockstep:

- одинаковая версия всех пакетов;
- единый release;
- compatibility matrix не требуется между произвольными minors.

Если независимо:

- `context` и `filament` тестируются против lowest и highest supported core;
- новые SPI добавляются без немедленного повышения lower bound;
- changelog каждого пакета описывает minimum core version.

## Testing gaps

### Mutation score может быть завышен

Mutation gate использует:

- `--covered-only`;
- исключения для Commands и Facades;
- исключения Resources и Pages в Filament;
- исключения Commands в context.

Порог 99% выглядит убедительно, но не означает, что 99% всего поведения защищено. Uncovered code не мутируется, а значительная часть framework integration исключена.

Следует публиковать отдельно:

- line coverage;
- branch coverage;
- mutation score для covered code;
- долю source, включённую в mutation scope;
- список исключённых namespaces.

### Не хватает package-boundary tests

Нужны автоматические правила:

- context не импортирует `core/Internal`;
- context не импортирует `core/Infrastructure`;
- filament не импортирует `core/Internal`;
- filament не импортирует `core/Infrastructure/Persistence`;
- Domain не импортирует Laravel;
- Application не импортирует Facades;
- Contracts не импортируют implementation;
- Commands могут зависеть от Application, но не наоборот.

### Не хватает compatibility fixtures

Перед 1.0 нужно snapshot-тестировать:

- public PHP API;
- enum cases и values;
- config schema;
- migration schema;
- command names/options/exit codes;
- middleware aliases;
- Blade directives;
- event payloads;
- exception types;
- service container bindings;
- facade methods;
- permission grammar;
- cache key format, если он persistent;
- generated scaffold output.

### Нужна dependency matrix

Минимальная матрица:

| PHP | Laravel | Dependency mode |
|---|---|---|
| 8.3 | 11 | prefer-lowest |
| 8.3/8.4 | 12 | normal |
| поддерживаемая latest | 13 | normal |
| latest | latest | prefer-highest |

Для Filament отдельно проверяется каждая реально поддерживаемая minor-линия Filament 5.

## Release policy

### До 1.0

До первой стабильной версии допустимы breaking changes, но каждый change должен иметь classification:

- API break;
- behavior break;
- schema break;
- configuration break;
- serialization break;
- event break;
- security tightening;
- documentation correction.

Нужно выпустить `0.9.0` как freeze candidate:

- новые public symbols не добавляются случайно;
- все типы классифицированы;
- migrations считаются release candidate schema;
- начинается реальное dogfooding;
- минимум один полный upgrade rehearsal;
- проводится внешний API review.

### После 1.0

Рекомендуемая политика:

- patch — bug fixes без intentional behavior break;
- minor — backward-compatible additions;
- major — removal и intentional breaking changes;
- deprecation минимум две minor-версии;
- security exceptions описываются отдельно;
- aliases для переименованных symbols;
- migration guides для каждого major;
- no silent semantic changes.

Composer использует VCS tags для определения версий библиотек; hardcoded `version` в `composer.json` не нужен и может конфликтовать с tags. [getcomposer](https://getcomposer.org/doc/02-libraries.md)

## Приоритетный план

### Этап 1: API inventory

1. Разметить каждый symbol как `@api`, `@spi`, `@internal` или `@experimental`.
2. Добавить CI, запрещающий unclassified symbols.
3. Создать `docs/api-policy.md`.
4. Создать glossary.
5. Составить список documented entry points.
6. Убрать из public API implementation classes.

Критерий готовности: для любого класса можно однозначно ответить, имеет ли пользователь право от него зависеть.

### Этап 2: Package boundaries

1. Выделить SPI для cache invalidation.
2. Выделить SPI для permission-state revision.
3. Выделить subject identity abstraction.
4. Создать administrative APIs для Filament.
5. Удалить imports внутренних core classes из context и filament.
6. Добавить architecture tests.

Критерий готовности: internal refactor core не требует изменения context или filament.

### Этап 3: Schema reset

1. Унифицировать prefix таблиц.
2. Переименовать `ModelHasScope`.
3. Ввести стабильный `role_key`.
4. Зафиксировать length и grammar всех keys.
5. Проверить indexes под MySQL и PostgreSQL.
6. Написать migration compatibility policy.
7. Изменить install command.

Критерий готовности: схема считается кандидатом на долгосрочную поддержку.

### Этап 4: API redesign

1. Разделить manager.
2. Сделать Panel immutable.
3. Разделить local permission и qualified ability.
4. Переименовать operational builders.
5. Сократить trait API.
6. Зафиксировать exception hierarchy.
7. Зафиксировать event contracts.

Критерий готовности: public API объясняется без знания Eloquent и service provider internals.

### Этап 5: Compatibility gates

1. Добавить Roave BC Check.
2. Расширить custom snapshot.
3. Добавить package-specific snapshots.
4. Добавить schema snapshot.
5. Добавить config snapshot.
6. Добавить CLI snapshot.
7. Добавить lowest/highest dependency CI.
8. Добавить independent install CI.

Критерий готовности: breaking change не может незаметно пройти pull request.

### Этап 6: Release candidate

1. Выпустить `0.9.0`.
2. Проверить реальные приложения с single и multiple panels.
3. Проверить Octane.
4. Проверить queue workers.
5. Проверить Redis cache.
6. Проверить PostgreSQL и MySQL.
7. Проверить context switching.
8. Проверить Filament admin flows.
9. Выполнить upgrade rehearsal с предыдущей версией.
10. Заморозить API перед `1.0.0`.

## Первые изменения

Если начинать рефакторинг немедленно, оптимальный порядок такой:

1. Ввести классификацию API без изменения поведения.
2. Добавить architecture tests для межпакетных imports.
3. Спроектировать core SPI.
4. Перевести context с internal classes на SPI.
5. Перевести Filament на administration services.
6. Переименовать таблицы, пока нет production.
7. Ввести `RoleId`/`role_key`.
8. Сделать panels immutable и строго валидируемыми.
9. Разделить local permissions и qualified abilities.
10. Только затем менять facade, traits и user-facing naming.
11. После стабилизации — добавить полный BC tooling.
12. Выпустить 0.9 release candidate.

Наиболее важное архитектурное решение: **не пытаться заморозить существующую поверхность целиком**. Сначала нужно существенно уменьшить public API, выделить SPI для официальных расширений и скрыть persistence/runtime implementation; только после этого snapshot и SemVer начнут защищать действительно осознанный контракт, а не случайно сложившуюся структуру классов.
