## A — P4.12's forbidden digest

Both clean full real-DB logs fail `Tests\\ArchTest`: the security preset rejects the
`sha1()` call in `AzGuard\\Database\\Schema\\MorphColumns::morphIndexName()`.
The concrete failure is at `MorphColumns.php:98`; it is independent of the database
driver. The targeted P4.12 proof therefore did not cover the project's architecture
gate. The index-name contract itself remains valid: the helper needs a deterministic,
short, table-aware identifier, not a weak digest.

Evidence: `/tmp/azguard-p410-pgsql.log:929-937` and
`/tmp/azguard-p410-mysql.log:929-937`.

## B — PostgreSQL rollback test transaction abort

The tight reproduction is:

```text
PGSQL_PORT=25432 composer test:pgsql -- --filter='T5 — migration 000004 down\\(\\) rollback'
```

It was run against the healthy host PostgreSQL container (`127.0.0.1:25432`) and the
`azguard_test` database. It deterministically exits 2 after 2 tests: the first test
correctly triggers the expected `QueryException` from migration 000004, but PostgreSQL
marks the ambient `RefreshDatabase` transaction aborted. Laravel's later migration
repository query then fails with `SQLSTATE[25P02]`. The positive sibling test alone is
green.

This is test-isolation recovery, not a new migration-000004 portability defect. The
minimal recovery seam is the expected-failure test: execute `migration->down()` inside
Laravel's nested `DB::transaction()` so PostgreSQL rolls back a savepoint while the
outer `RefreshDatabase` transaction stays usable; then assert a normal query succeeds.
The exact same test remains green on SQLite/MySQL, whose transaction/DDL behaviour is
different. No migration, driver branch, or production API change is justified.

Evidence: `/tmp/azguard-p410-pgsql.log:358-360,944-955`; current
`tests/Feature/ScopeClassMigrationRollbackTest.php`; current
`packages/core/database/migrations/2026_01_01_000004_make_scope_class_nullable_on_model_has_scopes.php`.
