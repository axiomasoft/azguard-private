# Дорожка усиления пакета до эталонной надёжности

## Назначение

Этот шаблон превращает существующий пакет экосистемы в предсказуемый релизный продукт:
сначала фиксирует фактические дефекты и публичные швы, затем исправляет их, канонизирует
структуру, замораживает API, углубляет доказательства корректности и только после этого
выпускает версию. Шаблон рассчитан на отдельный мастер-план пакета и исполняется по skill
`plan-protocol`; он не заменяет этот протокол и не дублирует его схемы статусов, handoff и
закрытия items.

Обязательная последовательность:

```text
аудит → ремедиация → структурный канон → release-готовность
      → тест-углубление → релиз и архивация
```

Переходить к следующей ступени можно только после терминальности предыдущей и её независимой
сверки. Один исполнитель пишет в рабочее дерево; reviewer читает конкретный diff и доказательства.
Для full-review допустимы не более двух циклов `review → fix → re-review`, после чего
неснятая содержательная находка переводится в redesign, а не маскируется продолжением.

## Как выбрать маршрут

Используйте provider-neutral классы из `plan-protocol`:

| Класс работы | Model class / effort | Когда применять |
|:--|:--|:--|
| Открытое решение, канон флота, необратимая семантика | `frontier/high` | Дизайн, синтез, развилки публичного контракта |
| Финальная независимая сверка фазы | `frontier/xhigh` | Adversarial audit доказательств и статусов |
| Реализация по уже принятому решению | `implementation/high` | Security, миграции, SemVer и иной риск при frozen spec |
| Детерминированная реализация | `implementation/medium` | Инфраструктура, тестовый harness, механические изменения |
| Read-only разведка или механическая бухгалтерия | `economy/low` или `implementation/low` | Только ограниченные чтение, grep, status/handoff операции |

Маршрут задаётся на каждый item, а не на фазу целиком, если items неоднородны. Full-review
обязателен для security, миграций, публичных контрактов, конкурентности и канона, которому
последуют другие пакеты.

## 1. Аудит read-only

**Цель.** Получить проверяемую картину продукта без исправления кода. Минимальные оси:
безопасность и корректность; интеграционная поверхность и DX; расширяемость и fluent API;
структура, качество и тестовые дыры. Для пакета со специальным риском добавьте отдельную ось,
но не смешивайте аудит с ремедиацией.

Каждая ось начинается закрытым чек-листом `C1..Cn`. Для каждого критерия обязателен ровно
один verdict из `pass | fail | partial | n/a`, якорь `file:line` или проверяемая команда и
краткое обоснование; критерий без verdict не считается проверенным. `fail` и `partial`
порождают запись REGISTER либо явную связь с уже существующей записью, `n/a` объясняет
неприменимость к этому пакету.

**Вход:** бриф владельца; исходный код, тесты, документация и CI; список публичных точек входа;
внешние первоисточники для несущих API/DX-утверждений.

**Типовые items:** RAG внешних prior art; по одному закрытому чек-листу на ось; консолидация
находок в единый `REGISTER.md`; дедупликация, severity и разбиение на волны. Независимые оси с
детерминированной Validation оркестрируйте одной workflow-сессией; итоговый реестр синтезирует
один writer.

**Выход:** находки с `file:line`, сценарием отказа, severity и источником; единый REGISTER;
ранжированный backlog; явные исключения и вопросы дизайна. Код, тесты и CI остаются без diff.

**Гейты владельца:** утвердить backlog, судьбу спорных находок и границы следующей волны.
Без этого гейта ремедиация не начинается.

**Routing:** осевые read-only исследования — `frontier/high`; синтез и приёмка backlog —
`frontier/high`; независимая сверка закрытой фазы — `frontier/xhigh`.

## 2. Ремедиация

**Цель.** Закрыть утверждённый backlog волнами от Blocker к Nit, сохранив происхождение каждой
правки и возможность атомарного отката.

**Вход:** утверждённые REGISTER и backlog; воспроизводимые тесты для дефектов; принятые владельцем
security/default-политики.

**Типовые items:** W0 для Blocker; W1..Wn по severity и общему корню; тест, сначала
воспроизводящий дефект; финальный adversarial review всей волны. Каждая находка получает
отдельный Files-scoped commit, даже если несколько находок имеют общий корень: связь
`finding → commit → test` должна позволять независимо ревьюить и откатывать её исправление.
Группируйте находки в волну по корню проблемы и file ownership, но не объединяйте их коммиты.

**Выход:** исправленные находки; тесты на failure scenarios; таблица `finding → commit → test`;
явно отложенные остатки с домом в будущей ступени.

**Гейты владельца:** подтверждение спорного изменения поведения, принятие material deviation и
решение о находке, которая выходит за утверждённые Files/Scope. Ошибка исходной спецификации
оформляется новым решением и redesign, а не правкой ТЗ исполнителем по ходу.

**Routing:** обычные fixes по frozen backlog — `implementation/medium`; security, tenant isolation,
сложные миграции и SemVer — `implementation/high`; итоговый review — `frontier/high` или audit
`frontier/xhigh`.

## 3. Структурный канон

**Цель.** До стабильного релиза сделать модули глубокими и границы понятными: убрать catch-all
каталоги, определить дома контрактов, унифицировать fluent-грамматику и отделить `@api` от
`@internal`.

**Вход:** закрытая ремедиация; карта публичной поверхности; фактические интеграционные швы;
решённые вопросы владельца по breaking-изменениям.

**Типовые items:** contract-first развилки и ADR; роспуск `Support/`, `Utils/` и сходных корзин;
унификация builders/facades/middleware; уточнение типов и контрактов; docs-parity; архитектурные
тесты. Пре-1.0 допускает breaking, но не освобождает от списка миграций потребителя.

**Выход:** доменная структура; ADR решений и отклонённых альтернатив; глоссарий; консистентный
fluent API; target-спека публичной поверхности для следующей ступени.

**Гейты владельца:** каждая load-bearing развилка канона и каждый намеренный breaking-выбор.
Гейт фиксирует решение до реализации; исполнитель не выбирает вариант внутри code item.

**Routing:** открытые развилки — `frontier/high`; реализация утверждённого канона —
`implementation/high`; docs/arch-test консолидация — `implementation/medium`; full-review обязателен
для публичных контрактов.

## 4. Release-готовность

**Цель.** Зафиксировать, что именно обещает версия, и сделать дрейф этого обещания видимым до
релиза.

**Вход:** target-спека после структурного канона; перечень всех breaking-изменений; зелёные
проверки структуры и поведения.

**Типовые items:** cut-line `@api`/`@internal`; снимок публичных типов и сигнатур, включая имена
параметров; тест, который краснеет при дрейфе snapshot; SemVer-политика; upgrade guide; каталог
известных ограничений. Регенерация snapshot разрешена только вместе с явным решением и version
bump — никогда автоматически для «починки» красного теста.

**Выход:** SSOT публичной поверхности; защищающий её snapshot/arch gate; SemVer-политика;
полный маршрут миграции; список честно принятых ограничений.

**Гейты владельца:** approve cut-line и публичной классификации; approve любой регенерации
замороженного snapshot; подтверждение целевой версии.

**Routing:** выбор cut-line или механизма freeze — `frontier/high`; исполнение уже замороженной
спеки и SemVer-документация — `implementation/high`; независимый phase audit — `frontier/xhigh`.

## 5. Углубление тестирования

**Цель.** Проверять не только happy path, но и переносимость, параллелизм, конкурентность и
чувствительность тестов к ошибочным изменениям.

**Вход:** замороженная публичная поверхность; зелёный базовый suite; поддерживаемая матрица PHP,
framework, СУБД, cache/queue drivers; список известных окруженческих ограничений.

**Типовые items и порядок:**

1. Воспроизводимый docker-стенд и реальные DB/cache services.
2. Матрица SQLite + приоритетная production СУБД + остальные first-class драйверы.
3. Paratest/random-order и изоляция process/static state.
4. Кросс-процессные race-тесты для epoch, locks, cache invalidation и worker state.
5. Mutation baseline на совместимом runner и ratchet, который может двигаться только вверх.
6. Portability/collation/index-length/rollback проверки и полный clean-vendor CI proof.

**Выход:** локально и в CI воспроизводимая union-матрица; детерминированные race-тесты;
mutation baseline и blocking ratchet; зафиксированные driver-specific ограничения и обходы.

**Гейты владельца:** состав поддерживаемой матрицы; допустимость driver-specific workaround;
смена mutation runner или формулы порога. Красная обязательная lane не называется «soft».

**Routing:** harness и детерминированные тестовые items — `implementation/medium`; миграции,
data integrity и concurrency — `implementation/high`; независимый review рискованного diff —
`frontier/high`; итоговый аудит доказательств — `frontier/xhigh`.

## 6. Релиз и архивация

**Цель.** Выпустить только доказанное состояние, дождаться внешних release signals и сохранить
историю решений как долговечный источник причин.

**Вход:** GREEN-аудит тест-углубления; frozen version и release scope; полный upgrade guide;
готовые CI release jobs и перечень внешних интеграций/секретов.

**Типовые items:** bump внутренних constraints/version maps; полный pre-tag check; guard для
намеренно отключённых split/publish jobs; owner-approved annotated tag; push и наблюдение release
CI; проверка release notes/CHANGELOG; перенос долговечных материалов из plan `root/` в проектные
docs; terminal audit; отдельная команда архивации плана.

**Выход:** тег и release, прошедшие CI; согласованные манифесты; опубликованный migration guide;
документированный список отложенной публикационной инфраструктуры; мастер-план в архиве, а его
долговечный канон — в docs.

**Гейты владельца:** явный approve непосредственно перед push тега; отдельное решение о публичной
публикации/split/registry; только GREEN terminal audit разрешает archive.

**Routing:** release-механика по frozen решению — `implementation/medium`; push выполняется только
после owner gate; финальный audit — `frontier/xhigh`; архивная бухгалтерия —
`implementation/low`.

## Вариативность по типу пакета

| Характеристика | Библиотека без собственного runtime | Сервис с HTTP runtime |
|:--|:--|:--|
| Обязательные ступени | Все шесть | Все шесть |
| Нагрузочная ось | Обычно не нужна; измерять hot paths микробенчмарком | Добавить отдельный load-поток |
| Инфраструктура | Реальные СУБД/cache только для поддерживаемых adapters | Полный app stack, ingress, workers, queue, storage |
| Performance contract | Алгоритмические инварианты и regression benchmark | SLO/SLI, k6-сценарии, серверные метрики и деградация |
| Race scope | Cache/locks/static worker state | Плюс HTTP concurrency, queues, retries, idempotency |
| Опциональные items | e2e/browser и load, если нет соответствующего runtime | Только неприменимые adapters; HTTP/load обычно обязательны |

Load-поток сервиса строится design-first: SLO как контракт, reference environment, realistic
seed, blocking/advisory thresholds, клиентские и серверные assertions, baseline и CI regression.
Не переносите k6 в библиотеку только ради единообразия: отсутствие управляемого HTTP runtime
делает результат шумом, а не доказательством.

## Protocol-hooks

1. **Constitution gate.** Для нового пакета сначала примените `axioma-doctrine`, затем
   `ecosystem-reuse-gate`: существующий компонент, контракт или пакет переиспользуется до решения
   строить новый.
2. **Слои знания.** Храните исходный запрос владельца в `brief/`, сырые recon/RAG-доказательства
   в `findings/`, авторский синтез в `research/`, решения — в D-log/ADR/`root/`. Исполнитель читает
   репозиторий, а не исчезнувший chat context.
3. **Audit orchestration.** Три и более независимые оси с детерминированной Validation запускайте
   одной workflow-группой; синтез REGISTER остаётся последовательным и single-writer.
4. **Snapshot freeze.** Снимок регенерируется только под новым D# и совместно с требуемым bump;
   «обновить expected, чтобы тест стал зелёным» запрещено.
5. **Ratchet only upward.** Baseline измеряется честно в воспроизводимой среде; новый порог не
   понижается ради прохождения CI. Несовместимый runner меняется явным решением с новым baseline.
6. **Owner gates.** Минимум три обязательных остановки: backlog после аудита; load-bearing развилки
   канона; approve перед push тега.
7. **Двухкоммитное закрытие.** Scope item и bookkeeping плана коммитятся раздельно, явными путями;
   review-fix идёт отдельным коммитом, без amend.
8. **Опциональный RUNBOOK-оркестратор.** Для цепочки нескольких мастер-планов создайте durable
   runbook: порядок, ready-команды, требуемый route, owner gates и ссылки на handoff каждого плана.
   Handoff конкретного плана всегда старше общей карты.

## Уроки исполнения

- **Счётчики recon — гипотеза, не контракт.** Предварительные количества публичных методов и
  контрактов расходились с фактом. Сработал гейт по полному перечислению и воспроизводимому grep;
  в новом плане acceptance должна проверять покрытие множества, а не доверять ожидаемому числу.
- **`Files` нужно строить по реальному dependency cone.** Исправления интерфейса затрагивали его
  реализации, stubs, регистрацию тестов и docs; узкие списки давали material deviation даже при
  корректном результате. До старта item сверяйте contracts ↔ implementations ↔ tests ↔ generated
  artifacts и не расширяйте список молча во время исполнения.
- **Спецификацию опровергает код, а не уверенность автора.** Предположительно мёртвые методы имели
  внутренних потребителей, а безопасным считался Eloquent-путь, который всё же проходил через
  mass assignment. При расхождении нужен recon и новый D#, а не буквальное исполнение опасного ТЗ.
- **SQLite не доказывает переносимость.** Реальные PostgreSQL/MySQL lanes выявили boolean,
  transaction-abort, collation, index-length и rollback различия. Поддержка нескольких СУБД требует
  union-доказательства на чистом окружении, а не самоскипа DB-specific веток.
- **Чистота dependency environment — часть доказательства.** Повреждённый ignored `vendor/` давал
  ложные или противоречивые результаты. Финальную матрицу нужно воспроизводить через fresh install в
  isolated worktree/CI, не копированием локального vendor.
- **Тестовый инструмент тоже проверяется на совместимость.** Выбранный mutation runner не дошёл до
  мутаций из-за несовместимого test protocol; честный переход на поддерживаемый native runner был
  полезнее имитации прежней метрики. Порог после измерения сохранил правило ratchet-only-upward.
- **Race-тест обязан учитывать production baseline.** Формула ожидала нулевой epoch, тогда как
  runtime начинал с ненулевой версии. Тест должен фиксировать наблюдаемую семантику до параллельного
  действия и выводить expected из неё, не из удобной абстракции.
- **Аудит закрывает разрыв между зелёным item и зелёной фазой.** Сквозная независимая проверка
  находила пропущенные upgrade notes, routing drift и красный refactor gate после формально
  закрытых items. Следующая ступень открывается verdict'ом аудита, не суммой оптимистичных отчётов.

## Критерий готовности шаблона пакета

Держатель пакета должен без доступа к чужому мастер-плану ответить для каждой ступени:
что читать и запускать; какой артефакт является входом; какой проверяемый выход производится;
где требуется решение владельца; какой route и review depth назначены; что опционально именно
для этого runtime. Если хотя бы один ответ живёт только в чате, дорожка ещё не готова.
