## Adversarial seams and structural quality

1. **Blocker, P2.1/P2.2/P3.2 — stale allow after official UI revoke.** Stock Filament delete/attach/detach and bulk actions bypassed `PermissionStateRevision`; a warmed reader could retain the old allow. Role creation/edit also used two writes without a transaction. Those actions now use the synchronizer, subject mutation APIs, or revision transactions. Role deletion additionally clears dependent rows under a locked role because SQLite with foreign keys off reproduced an orphan-based allow. Regression: `tests/Feature/Filament/MutationRevisionTest.php` and P2 focused suite.
2. **Major, P2.3 — partial allow on source failure.** `EffectivePermissionResolver` skipped a throwing source with the default setting, even if another source allowed the same action. That contradicted P2.3's fail-closed clause. The catch was removed; the historical config method/key remain syntactically compatible but no longer weaken authorization. Cache transport fallback now avoids both durable and request-local persistence after get/put/epoch failures. Regression: resolver and transport tests.
3. **Blocker, P2.2/P2.3 — raw model revoke during cache outage.** `DirectGrant` and `ContextRole` instance observers only bumped the cache epoch after the SQL write; epoch failure was swallowed and the unchanged DB revision permitted a stale allow. Individual model save/delete now run with the same-connection revision in a DB transaction, including nested operations, while no-op saves leave revision unchanged. An epoch bump failure is returned to callers rather than logged as success. Query-builder bulk writes remain explicitly outside this model-event contract and require `guard:cache-reset`. Regression: raw model rollback/no-op/cache-failure and D13 process tests.
4. **Major, P3.1/P3.2 — configured model guarantees.** A custom `RolePermission` connection still read its pivot from the default connection; split config could be swallowed by the source catch; doctor crashed for an invalid scope model. Connection-aligned read, pre-cache alignment check, live-role existence check, and structured doctor output close these routes. New tests exercise one shared nondefault connection, split config, orphan rows, and invalid models.
5. **Blocker, P4.2 — Filament panel isolation.** `forPanel('tenant')` did not reach the catalog and Gate bindings, which kept the default `admin` panel; one panel's `enforce(false)` could also affect another. Catalog/discovery/resource Gate/page-widget checks now read the linked plugin for the current panel, and registration freezes each plugin's own defaults. A no-policy `Resource::canViewAny()` regression proves an admin-only grant cannot open a tenant resource.
6. **Major, P4.1/P4.2/P5.1 — lifecycle and validation.** Nested `PanelCheckAccess` discarded the outer panel; strict Gate/default paths accepted unknown final panels; a subclass domain model lost its scope; `class_name=''` was treated as DB-only. These now have focused success/failure regressions. The current-panel state remains scoped and job/request tests pass.
7. **Major, P6.2 — migration portability and downgrade.** PostgreSQL dropped a custom-schema index without schema qualification. MySQL `down()` could remove exact indexes before discovering that valid NULL-vs-zero tuples cannot fit the legacy sentinel index. It now rejects the downgrade before any drop. This is a safe refusal, not a promise that every upgraded database can return to the old identity contract.
8. **Major, P7.1/P7.2 — qualification and release discipline.** Earlier reports called P7 green while the clean grid and docs build were unrun and release package constraints still targeted `^0.3`. The fixed scripts and CI ordering now expose rather than conceal gaps. The current candidate graph resolves at 1.0.0; the tag check remains intentionally red against HEAD until a reviewed candidate commit exists.

The main code-quality weakness was integration coverage at mutation, connection, and lifecycle boundaries: many unit/feature suites passed while official UI paths, invalid configuration, and downgrade failure modes were absent. New regressions target observable authorization outcomes and rollback, not merely implementation counters. The schema helper retains explicit engine branches and the MariaDB refusal; no speculative abstraction or production migration was added.
