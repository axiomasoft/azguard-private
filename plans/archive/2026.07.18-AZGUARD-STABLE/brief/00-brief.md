## Исходный запрос (переформулировка)

1. **Провести аудит проекта (пакет azguard).** Всё найденное аудитом — в план.
2. **Главная цель — максимально стабильный публичный API, покрывающий все наши
   потребности.** Особый акцент: **интеграционная поверхность** («интеграция стен») —
   по ощущению владельца это сейчас наименее проработанная часть пакета.
3. Пакет должен быть **максимально гибким и максимально надёжным**.
4. **Общий план — до финала**: сначала API становится стабильным, затем идёт углубление
   именно в написание тестов.
5. **Образец — проект vaulter** (`~/projects/packages/vaulter`): там сделано так же —
   сначала стабилизация, потом жёсткое погружение в тестовую инфраструктуру (докер,
   тестирование «кусков кода», параллельные прогоны тестов). Владелец хочет, чтобы **все
   наши пакеты были такими же надёжными**.
6. **Переиспользуемость плана как шаблона.** После стабилизации пакет станет
   «ролчатом» (эталоном/ролевой моделью); надо строить план так, чтобы потом было легко
   понять, как сделать такой же план для любого другого пакета экосистемы.
7. **Полная свобода изменений**: сейчас последняя итерация, когда можно всё — любые
   переименования, любые изменения структуры папок; если доменная структура «хромает» —
   менять её. Проект молодой, потребителей мало, миграция без проблем.
8. **Финал плана — тег новой версии**, ориентир **0.3.0** (пока предварительно, владелец
   подтвердит).
9. **Fluent API нужен идеальный**; проверить максимальные современные практики по DX и
   гибкости (владелец явно просит свериться с внешними best practices — RAG).
