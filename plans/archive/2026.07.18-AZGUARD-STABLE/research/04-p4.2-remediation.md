# 04 — Ремедиация portability-багов P4.2: консолидация root-cause и структура items

> Слой 2. Авторский синтез под ре-дизайн P4.2 (эскалация §10). Опирается на:
> findings/P4.2-db-portability-failures.md (список сбоев лейна),
> findings/P4.2-remediation-anchors-2026-07-18.md (точные якоря),
> findings/recon-db-portability-2026-07-18.md (портируемость by design).

## 1. Консолидация: 8 симптомов → 4 корня (2 из «классов» — каскады)

Разбор якорей (findings/P4.2-remediation-anchors §6/§5) показал: два из заявленных
«независимых классов» — НЕ самостоятельные баги, а следствия миграционных сбоев:

| Симптом лейна | Корень | Тип |
|:--|:--|:--|
| PG: `COALESCE types character and integer cannot be matched` (model_has_scopes_unique) | **R1** — fallback-литерал `0` в COALESCE не зависит от morph-type (char vs int) | migration 000005, PG |
| PG: `ModelHasRolesScopes...` transaction aborted (каскад) | **R1** (отравленная транзакция после сбоя индекса) | каскад R1 |
| PG: wildcard-суперадмин `false` (`AuthorizerExtendedTest`/`HasAzGuardTest`) | **R1** (seed не прошёл в отравленной транзакции; boolean-DB-сравнения в пути НЕТ — §6) | каскад R1 |
| MySQL: `Cannot drop index ... needed in a foreign key constraint` (down()) | **R1** — порядок drop в `down()` не учитывает MySQL FK-covering-index | migration 000005, MySQL |
| MySQL: `Base table already exists: az_guard_context_roles` (~40 ошибок) | **R1/R2** (RefreshDatabase не откатывает после первого сбоя down/create) | каскад |
| MySQL: `Specified key too long (3072 bytes)` (az_direct_grant_unique, az_ctx_roles_unique) | **R2** — 6× varchar(255) под utf8mb4 > лимит ключа | migrations 000002+000010, MySQL |
| MySQL: `Data truncated for column 'model_id'` (ULID) | **R2'** — morph-config `ulid` не применён до миграций (config-timing) | migration/test, MySQL |
| MySQL: `LIKE ... ESCAPE '\\'` syntax error | **R3** — raw `ESCAPE '\\'` не переносится на MySQL-грамматику | filament query |
| PG/MySQL: `column expires_at does not exist` (`ContextTableNameConfigTest`) | **R4** — тест-фикстура строит кастом-таблицу без `expires_at` (реальная 000011 её создаёт) | ТЕСТ, не app |

**Итог:** реальных корней — 4 (R1 миграция 000005; R2 key-length 000002/000010 + R2' morph-timing;
R3 filament LIKE; R4 тест-фикстура). Каскады PG-boolean и MySQL-table-exists закрываются фиксом
R1 — отдельных items под них НЕ заводим (verify после ремедиации).

## 2. Структура items (file-ownership split — без двойного редактирования миграций)

Разбивка по ВЛАДЕНИЮ файлом (каждая миграция правится ровно одним item'ом → нет конфликта
двух правок одного файла; принцип coupling-минимизации SKILL §5):

| Item | Владеет | Корни | Пакет |
|:--|:--|:--|:--|
| **P4.2** (re-scope) | тест-харнесс + `ContextTableNameConfigTest`-фикстура | R4 | tests |
| **P4.8** (new) | migration **000005** (COALESCE + down-order) + morph-timing диагностика | R1, R2' | core |
| **P4.7** (expand) | migrations **000002 + 000010** (key-length + collation) | R2 + collation-hardening D24 | core+context |
| **P4.9** (new) | filament `DirectGrantResource` LIKE-запрос | R3 | filament |
| **P4.12** (new) | `MorphColumns` explicit short morph-index identifiers + UUID regression proof | R5 | core/tests |
| **P4.10** (new) | green-proof обоих лейнов + CI-джоб `test-db-matrix` + baseline→resolved | — (интеграция) | ci/tests |

Почему key-length живёт в P4.7, а не в P4.8: P4.7 (D24) уже правит collation ключевых колонок в
000002/000010 — те же колонки, тот же файл. Слить длину и collation в один проход по 000002/000010
дешевле и безопаснее, чем два независимых редактирования (P4.7 иначе обязан не откатить длины P4.8).
000005 (COALESCE/down) collation не касается → отдельный владелец P4.8.

## 3. Порядок исполнения (последователен — общий docker-стенд, каскад-сцепка)

`P4.2 → P4.8 → P4.7 → P4.9 → P4.12 → P4.10` (портируемость), затем sqlite-лейн/race
`P4.3 → P4.4 → P4.5 → P4.6`.

Почему НЕ оркестрация (§7-критерий НЕ сработал, как и вся P4): (а) один физический docker-стенд —
одна PG-БД + одна MySQL-БД; parallel-прогоны против общей БД под RefreshDatabase коллидят;
(б) MySQL-каскад «table exists» маскирует нижележащие сбои — пока R1 (teardown) не починен, чисто
валидировать R2/R3 на MySQL нельзя (первый сбой отравляет весь suite). Значит R1 (P4.8) обязан идти
ПЕРВЫМ, дальше строго последовательно. Данные-сцепка = manual item-by-item.

R5 обнаружен P4.10 после закрытия R1–R3: `MorphColumns` оставляет Laravel генерировать index
identifier из configurable table name. Его UUID fixture сознательно длинный и повторяет migration
000000; короткая fixture скрыла бы production defect. Поэтому P4.12 обязан завершиться до
P4.10 full MySQL proof. RAG:— (repo-grounded:
findings/P4.10-uuid-morph-index-name-2026-07-22.md).

## 4. SemVer / заморозка P3

Все фиксы — в МИГРАЦИЯХ и query-builder-реализации, НЕ в @api-PHP-поверхности (миграции не @api,
снапшот P3.2 не индексирует схему БД). Значит:
- @api-снапшот `tests/Unit/ApiBoundaryTest.php` фикстур НЕ трогается; если тронулся — §10 (D# с bump P3).
- Правки — edit-in-place существующих миграций (git-тегов нет, свежие инсталы — recon §CI, канон P4.7 D24).
- Поведенческий bump: fix едет в планируемый **v0.3.0** (P5.2), отдельного тега не требует.
- **Breaking для существующих MySQL-инсталов** (pre-mortem §5): utf8mb4_bin делает ключи
  case-sensitive — прод-MySQL, полагавшийся на CI-схлопывание регистра, начнёт отвергать «дубли».
  Это НАМЕРЕННО (fail-closed D10), но требует строки в UPGRADING/known-limitations (P3.3 закрыт →
  добор в P4.10 deliverable или follow-up-заметка).

## 5. Pre-mortem (schema-critical, эталон-план флота — high-stakes)

«Через 6-12 мес фикс провалился — почему»:
- **Key-length подобран так, что длинный FQCN `model_type` (>N симв) обрезается → коллизия ключей.**
  Митигация (P4.7): НЕ резать `model_type` вслепую — префикс-индекс на длинную колонку ИЛИ полная
  колонка + короткие прочие; доказать расчётом «сумма байт < 3072» в Completion Notes.
- **COALESCE-fallback захардкожен под один morph-type → mixed-key инсталл ломается.** Митигация
  (P4.8): fallback выводить из `Config::morphType()` консистентно (int→0, ulid/uuid→'').
- **CI-джоб добавлен, но flaky-сервисы → красный борд маскирует реальные падения.** Митигация
  (P4.10): healthcheck + retries, добавлять джоб ТОЛЬКО зелёным.
- **utf8mb4_bin молча меняет поведение прод-MySQL (регистр теперь значим).** Митигация: явная
  строка в UPGRADING (§4).
