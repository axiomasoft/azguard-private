## Scope Included

Typed subject identity `morph type + canonical string id` во всех request/durable/epoch/invalidation/scoped-role cache paths; безопасное кодирование panel/context dimensions и новая cache namespace version.

Аддитивный absolute `validUntil` в effective `PermissionSet`, minimum-deadline merge, versioned durable envelope и проверка `now >= validUntil` на каждом request/durable cache hit. Built-in direct/context reads передают ближайший deadline без изменения сигнатур `GrantSource` и `PermissionLayer`.

## Scope Excluded

Атомарность мутаций P2; переименование или breaking change public `PermissionSet`/`GrantSource`/`PermissionLayer`; новые DB tables; обещание expiry для legacy custom source, который не передаёт deadline; полная cache failure/transaction consistency P2.

## Acceptance

User#1 и Admin#1 разделены при request/durable hits, epoch bump, old-identity invalidation и scoped-role lookup; morph aliases, UUID/ULID и separator-containing values не создают коллизий, а `1`/`"1"` совпадают как одна persistence identity.

На `now >= expires_at` истёкший direct/context вклад исчезает без prune в том же long-lived scope и в durable cache; независимый действующий вклад в то же право сохраняет allow. Minimum deadline не теряется при merge/filter/wildcard/context strategy. Raw v1 и malformed envelope не считаются cache hit. Legacy custom sources не ломаются и сохраняют configured TTL; новый additive deadline API покрыт API snapshot.

## Validation strategy

P1.1: resolver/cache regression для двух authenticatable types с ID=1; morph aliases, UUID/ULID, separators; request cache, named persistent store, epoch/invalidation и `ScopedRoleCache`. Существующий Redis carrier запускается только при доступном изолированном Redis и не подменяется skip-результатом.

P1.2: frozen-clock direct/context expiration до TTL, на границе и внутри одного long-lived scope; нескольо contributors и одинаковое permission; wildcard/filter/context strategies; legacy custom source; raw v1, malformed и already-expired envelope.

Конкретные test files/команды и expected outcomes закреплены в item Validation.
Reproduction и исправление выполняются в одном owning item; не коммитить
полную красную suite как отдельную обязательную фазу.
