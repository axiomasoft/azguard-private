### P2.3 — Проверить отказ backend и безопасный сброс

D13 transaction rule (normative): Cache-failure fallback never consults or
populates request/durable/scoped-role caches at positive transaction level on the
authorization connection, even when an entry was warmed before the transaction.
Resolve fresh on that connection without stale relations, or fail closed. Check
failure injection inside a nested transaction and after outer rollback/commit;
the 7→uncommitted 8→rollback→unrelated committed 8 scenario must not expose stale allow.

**Intent:** Сделать cache backend отказоустойчивым ускорителем и заменить destructive store flush точечным AzGuard generation/reset contract.
**Why:** RAG:— `findings/verification.md` F8: lock/cache exception возникает рядом с mutation, а `guard:cache-reset` очищает весь configured store. D13 переносит correctness в DB revision и оставляет один итоговый seam review.
**Scope Included:** Read/write/lock fault policy; uncached recompute/fail-closed boundary; explicit deployment generation in key; revision-based `guard:cache-reset`; local request reset; operator output/docs; one focused review P2 role-sync/revision/failure seams.
**Scope Excluded:** Durable retry worker/outbox; store-wide key enumeration/delete; production cache/DB writes; generic circuit-breaker/metrics platform; automatic deployment discovery; повторные item/phase reviews.
**Inputs:** terminal GREEN `phases/P2/P2.2.state.md` · `plan.md` · `phases/P2/P2.md` · F8 · D13 · `docs/reference.md` · `research/P2-design.md` · `research/P2-design-rag.md` · `artifacts/P2-design/examples.md`.
**Files:** `packages/core/src/Registry/Resolver/PermissionCache.php` · `packages/core/src/Commands/CacheResetCommand.php` · core cache config/`Config.php` and provider bindings · `tests/Feature/CacheResetCommandTest.php` · new targeted cache-failure/generation tests · affected RU/EN cache/operations docs · root `CHANGELOG.md`.
**Required Reads:** 1) `packages/core/src/Registry/Resolver/PermissionCache.php` 2) `packages/core/src/Commands/CacheResetCommand.php` 3) `packages/core/config/az-guard.php` 4) `packages/core/src/Configuration/Config.php` 5) `tests/Feature/CacheResetCommandTest.php` 6) `tests/Feature/PermissionCacheEpochLockWarningTest.php` 7) `tests/Feature/PermissionCacheCrossProcessRaceTest.php` 8) `docs/advanced/configuration.md`.
**Implementation Rules:** Read DB revision before consulting either cache tier. Catch only cache-store operations: on get/remember/put/lock failure clear matching local entry and recompute from authoritative sources without persisting; source/DB failure propagates and denies authorization. Never return a previously warmed request value unless its revision/generation matches the just-read current values. Add an explicit scalar deployment generation with safe default, canonical digest and docs; a changed value creates a new namespace. `guard:cache-reset` increments DB revision transactionally and reports the new generation/revision; it must not call store `flush()` or delete by prefix. Keep existing CLI signature/options compatible where harmless. Old entries expire naturally under the finite-TTL invariant. One light review inspects only the three named integration seams and repairs material findings in owning item.
**Code Guidance:** Separate cache transport exceptions from callback/source exceptions so a DB bug is not silently treated as cache miss. Array store follows the same revision/generation identity even without durable entries. Real Redis test is conditional on an isolated service; fault-injection fake is the deterministic acceptance path.
**Validation:** 1) throwing cache get/put/lock never returns warmed stale allow and either recomputes current DB state or throws; 2) source/DB exception is not swallowed; 3) revision bump failure leaves reset command nonzero and state unchanged; 4) changed deployment generation misses old request/durable entry; 5) `guard:cache-reset` invalidates AzGuard entries through revision while a sentinel foreign key in the same store survives; 6) retry after backend recovery serves only current revision; 7) `vendor/bin/pest tests/Feature/CacheResetCommandTest.php <targeted-cache-failure-test> tests/Unit/Registry/PermissionCacheTest.php` plus isolated Redis race carrier when available; 8) affected PHPStan/Pint, `git diff --check`, API/CLI snapshot if output changed, and one light seam review with no automatic follow-up stage.
**Deliverables:** Advisory-cache failure policy; deployment generation keying; namespace-only reset command; foreign-key/fault/recovery regressions; RU/EN operations docs and root CHANGELOG; one recorded light review result.
