### P1.1 — T1: panel-aware Eloquent global query-scope

**Status:** 🟠 Done with deviations
**Intent:** `HasScopedRoles::bootHasScopedRoles()` регистрирует Eloquent global scope,
который для АУТЕНТИФИЦИРОВАННОГО пользователя фильтрует запросы по `scope_class` каждого
назначенного scoped-role — но НЕ учитывает `panel_id` строки при выборе, какие scopes
применять. Сделать этот путь panel-aware ТОЛЬКО когда панель активна: при УСТАНОВЛЕННОЙ
текущей панели строка с `panel_id !== null`, не совпадающим с ней, не применяется к
query-фильтрации; строка с `panel_id === null` остаётся «любая панель» (back-compat). Когда
текущая панель НЕ установлена (`PanelResolver::resolve(null) === null` — норма для
Filament-запросов и роутов без middleware `azguard.panel`), применяются ВСЕ scopes, как и до
этой правки (D5): сужение по панели — строго аддитивное, срабатывает лишь при известной
панели. Это НЕ буквальная копия правила `hasScopedPermission()`: там панель никогда не бывает
`null` (check-путь всегда резолвит конкретную через `resolveDefault(null)` → config ?? `'app'`,
`HasScopedRoles.php:202-207`), здесь — бывает, и именно этот `null`-случай закрывает D5.
Плюс к panel-awareness item НЕСЁТ второй, co-located фикс (D9, bundle-решение владельца):
внутренний фетч scopes (`HasScopedRoles.php:63`, `->with('scopeEntity')`) eager-загружает
`scopeEntity`, который САМ — модель с `HasScopedRoles`, → повторно входит в ЭТОТ ЖЕ global
scope → **бесконечная рекурсия** на ЛЮБОМ `Project::all()` при `runningInConsole()===false`
(реальный HTTP) и ≥1 scope-row для запрашиваемого типа. Это первичный сценарий T1 — реальный
прод-краш, замаскированный тем, что под тестами `runningInConsole()===true` глушит замыкание.
Фикс — грузить `scopeEntity` БЕЗ этого scope: `->withoutGlobalScope(self::SCOPE_KEY)` (проверено
прогоном EXP D: реальный fetch зелёный, `apply()` срабатывает, phpstan level 6 + pint чисты).
**Why:** RAG:— (repo-grounded: `HasScopedRoles.php:46-75`, `hasScopedPermission():200-257`
в этом же файле). Permission-check путь УЖЕ изолирован по панели (F8, closed PR #91):
`hasScopedPermission()` строка 222-224 делает `whereNull('panel_id')->orWhere('panel_id',
$panelId)` при выборке `$scopedRoleIds`. Query-**filtering** путь (`bootHasScopedRoles`,
строки 59-73) фетчит ВСЕ scopes пользователя по `scope_entity_type` БЕЗ фильтра по
`panel_id` и применяет `apply()` КАЖДОГО — если у пользователя есть scoped-роль под
панелью A и под панелью B на одном и том же типе сущности, запрос, выполняемый под
панелью B, всё равно применит scope-фильтр панели A. Тот же класс бага, что F8 закрывал
для check-пути — просто другая труба (query-фильтрация vs permission-проверка).
**Scope Included:** правка `bootHasScopedRoles()` — ДВА co-located изменения в одном
методе (D9): (1) фильтрация применяемых `$scopes` по текущей панели перед вызовом `apply()`
(panel-awareness, D5); (2) `->withoutGlobalScope(self::SCOPE_KEY)` на eager-load `scopeEntity`
(фикс рекурсии — прекондиция: без него тест на РЕАЛЬНОМ fetch-пути уходит в бесконечную
рекурсию). Regression/feature-тест, доказывающий изоляцию именно на query-filtering пути
(сейчас `ScopeInterface::apply()` НЕ упражняется НИ ОДНИМ существующим тестом в репо —
`grep -rn "implements.*ScopeInterface" tests/ packages/` пуст — потому что console-guard

**Implementation Rules:** использовать `PanelResolver::resolve(null)` (НЕ
`resolveDefault()`): D5-ветка «панель не установлена → применить ВСЕ scopes» опирается на
ИСТИННЫЙ `null` от `resolve()`. `resolveDefault(null)` замаскировал бы отсутствие панели под
конфиг-дефолт/`'app'` и тем самым (а) уничтожил бы возможность отличить «панель не
установлена» от «активна панель app», сломав D5, и (б) под ложным `'app'` начал бы
отбрасывать scopes, назначенные ЯВНЫМ панелям ≠ app, в контекстах вообще без панели — ровно
та утечка-наоборот, что нашёл аудит A1. (Прежнее обоснование «`resolveDefault` отбрасывал бы
консьюмерские сетапы без Filament-панелей» — ЛОЖНО и удалено: у таких сетапов `panel_id ===
null` (`assignScopedRole` без `panelId`, `HasScopedRoles.php:106`), а первый конъюнкт guard'а
(`$scope->panel_id !== null`) освобождает такие строки при ЛЮБОМ резолвере.) RAG:—
(repo-grounded: `PanelResolver.php:33-42,90-93`; guard-логика ниже). Фильтрация — ПОСЛЕ фетча
(внутри `foreach ($scopes as $scope)`, до вызова `apply()`), НЕ в SQL-запросе
`$user->scopes()->where(...)`: кеш-ключ `ScopedRoleCache` (`{userId}|{entityClass}`, БЕЗ
панели) НЕ трогать — один и тот же фетч переиспользуется вне зависимости от активной панели,
фильтрация по панели дешёвая (in-memory, коллекция уже в памяти) и не требует новой
размерности кеш-ключа. RAG:— (repo-grounded: `ScopedRoleCache.php`, докблок явно объясняет
назначение кеша — не расширять его схему без необходимости).
Фикс рекурсии — МИНИМАЛЬНЫЙ и локальный: единственная правка строки 63 —
`->with('scopeEntity')` → `->with(['scopeEntity' => fn ($q) => $q->withoutGlobalScope(self::SCOPE_KEY)])`.
НЕ вводить re-entrancy-флаг/статик (Octane-класс проблемы), НЕ трогать `ScopedRoleCache`, НЕ менять
`apply()`-контракт. `self::SCOPE_KEY` доступен в замыкании (оно в статическом методе трейта). RAG:—
(repo-grounded + проверено прогоном EXP D: `HasScopedRoles.php:63`; форма зелёная на реальном fetch,
phpstan level 6 + pint чисты). Тест-драйв: console-guard `HasScopedRoles.php:49` вычисляется В МОМЕНТ
ЗАПРОСА (внутри замыкания global scope), поэтому его достаточно сбросить в теле теста ДО запроса —
env/кеш-сброс НЕ нужны (значение уже закешировано в `Application::$isRunningInConsole` при boot'е, но
свойство перезаписывается напрямую). Форма — в Code Guidance; проверена прогоном (EXP A/C/D: под
форсом замыкание исполняется, `apply()` срабатывает). RAG:— (repo-grounded:
`vendor/laravel/framework/src/Illuminate/Foundation/Application.php:800-806`).
**Code Guidance:** внутри `foreach ($scopes as $scope)` перед `if ($scope->scope_class
!== null && …)` добавить проверку панели:
`if ($currentPanelId !== null && $scope->panel_id !== null && $scope->panel_id !== $currentPanelId) { continue; }`.
Первый конъюнкт (`$currentPanelId !== null`) реализует D5: панель НЕ установлена → НИ ОДНА
строка не отбрасывается, применяются все scopes. БЕЗ него guard молча расширил бы видимость
в Filament-запросах (отдал бы `Model::all()` вместо доступного подмножества — находка A1).
`$currentPanelId = PanelResolver::resolve(null);` вычисляется ВНУТРИ замыкания global scope
(того, что передаётся в `addGlobalScope()`), ОДИН РАЗ до `foreach`, а НЕ до вызова
`addGlobalScope()` и НЕ в цикле: вычисление до `addGlobalScope()` заморозило бы панель на весь
процесс (Octane-класс проблемы — у репо есть `tests/Unit/OctaneScopingTest.php`), вычисление в
цикле — лишние идентичные вызовы. Не менять сигнатуру `bootHasScopedRoles()` (статический
метод, вызывается Eloquent-буткодом — не принимает параметров). Не вводить новую
абстракцию/трейт ради одной проверки. ЗАПРЕЩЕНО молча ослаблять существующий null-панель
back-compat (`assignScopedRole` без `panelId` обязан по-прежнему матчить ЛЮБУЮ панель) — тест
обязан явно проверить оба случая (null матчит всё; explicit panel матчит только свою). Новый
stub-класс роли (`ScopedFilterRole`) — реализация `apply()` должна ДЕЙСТВИТЕЛЬНО фильтровать
Eloquent-билдер наблюдаемым образом (например, `$builder->where($entity->getKeyName(),
$entity->getKey())` — сужает до одной сущности), иначе тест не может отличить «scope
применился» от «scope не применился». Тест обязан покрывать ТРИ кейса: (1) scope панели A НЕ
влияет на выборку под панелью B — вторая (независимая) сущность, видимая БЕЗ scope-фильтра
панели A, должна остаться видимой при активной панели B; (2) scope с null-панелью продолжает
применяться под ЛЮБОЙ панелью (back-compat, не регресс); (3) **ПАНЕЛЬ НЕ УСТАНОВЛЕНА (D5,
ОБЯЗАТЕЛЬНЫЙ)** — scope с ЯВНОЙ панелью (`panel_id !== null`) при отсутствии текущей панели
(middleware `azguard.panel` не отработал — как в любом Filament-запросе; в тесте: НЕ звать
`AzGuard::setCurrentPanel()`) ВСЁ РАВНО применяется: сущность, ограниченная этим scope, остаётся
ограниченной, а НЕ становится полностью видимой. Этот кейс — прямой guard против регрессии A1;
без него Validation дырява (кейсы 1-2 гоняются с УСТАНОВЛЕННОЙ панелью и «панель null» не
упражняют).

Тест-драйв (ВСЕ три формы проверены прогоном — НЕ импровизировать):

(1) **Обход console-guard.** Global query-scope `bootHasScopedRoles():49` при
`app()->runningInConsole()===true` (истина в каждом Pest/Testbench-прогоне) молча выходит —
`apply()` не зовётся, любая assertion фильтрации проходит вакуумно. Guard вычисляется ВНУТРИ
замыкания (в момент запроса), поэтому в теле теста ДО первого запроса форсировать флаг в false
через bound-closure (обычная функция, НЕ arrow — arrow не даёт rebind; scope замыкания → класс
`Application`, иначе protected-свойство недоступно):

```php
(function (): void {
    $this->isRunningInConsole = false;
})->call(app());
```

`->call(app())` (без 2-го аргумента) — scope замыкания автоматически = класс объекта
(Testbench `Application`, наследник `Illuminate\Foundation\Application`), поэтому protected
`$isRunningInConsole` доступен. НЕ передавать `Application::class` 2-м аргументом: у
`Closure::call` 2-й параметр — АРГУМЕНТ замыкания, а не scope (обе формы проверены прогоном;
эквивалент через явный scope — `Closure::bind($fn, app(), Application::class)()`). Это
ЛЕГИТИМНАЯ симуляция HTTP-рантайма (query-scope по замыслу работает только вне консоли), НЕ
ослабление ассертов. `actingAs($user)` обязателен — иначе второй конъюнкт guard'а
(`! Auth::check()`) снова глушит замыкание.

### P1.2 — T6: atomic epoch bump в PermissionCache (снять increment()/put() гонку)

**Status:** 🟢 Done
**Intent:** `PermissionCache::forgetForUser()` (строки 95-99) делает `add()` →
`increment()` → `put()` НЕ атомарно как единый блок: между `increment()` (атомарен на
большинстве стораджей) и `put()` (НЕ атомарен — read-modify-write гонка через PHP)
возможна гонка при конкурентных `forgetForUser()` на одном `$epochKey` — поздний `put()`
может откатить эпоху НАЗАД. Обернуть три вызова в атомарную секцию (лок), чтобы
конкурентные форгеты сериализовались.
**Why:** RAG:— (repo-grounded: `PermissionCache.php:81-99`, докблок самого метода
описывает ИСТОРИЮ фикса TTL — `e3e33c3` — но не осознаёт, что решение TTL-проблемы
введением `put()` после `increment()` создало НОВУЮ гонку: поток A инкрементит эпоху до
5, поток B инкрементит до 6, но `put()` потока A выполняется ПОСЛЕ `put()` потока B —
эпоха откатывается на 5 в сторадже. Эффект: отозванный грант (через
`forgetForUser` → epoch bump → `keyFor()` строит НОВЫЙ ключ с бОльшим `v{epoch}`) может
не инвалидироваться немедленно — старый `PermissionSet` под старым (откаченным) эпоха-ключом
продолжает обслуживаться до истечения его собственного TTL.
**Scope Included:** атомарность ТОЛЬКО последовательности `add()`→`increment()`→`put()`
внутри `forgetForUser()`; regression-тест, доказывающий сериализацию (не полагаться
только на существующий однопроцессный `tests/Feature/
PermissionCacheEpochInvalidationTest.php`, который гонку физически не воспроизводит —
`array`-стор однопроцессный).
**Scope Excluded:** `currentEpoch()`/`keyFor()`/`rememberForRequest()`/
`loadFromStore()` — логика чтения эпохи не меняется; выбор кеш-стораджа (`Config::
cacheStore()`) — не меняется; `forgetRequestCache()`/`forgetAll()` (in-process only) —
race там невозможна (нет стораджа), вне scope.
**Inputs:** `Illuminate\Contracts\Cache\LockProvider`/`Illuminate\Contracts\Cache\Lock`
(Laravel Cache Lock API). ВАЖНО: `lock()` объявлен на `LockProvider` (и на конкретных
`Store`-реализациях), но НЕ на контракте `Illuminate\Contracts\Cache\Repository`, который
возвращает `cache()->store($store)` — поэтому доступ к локу идёт ЧЕРЕЗ

`cache()->store($store)->lock()` падает phpstan level 6 `[method.notFound]`, находка A3).

эпоха-блока — именно так устроен существующий тест

['driver' => 'array']`, `az-guard.cache.store => 'azguard_test'`). Все стандартные сторы

поэтому тест на сериализацию МОЖНО писать прямо на array-сторе тестового окружения, ложной
дилеммы «у array lock() no-op» НЕТ (находка A4). RAG:✅ (2026-07-17 — прогон phpstan level 6

implements LockProvider`). Кастомный драйвер без `LockProvider` → `instanceof`-fallback

**Implementation Rules:** атомарность через Laravel Cache Lock API (`LockProvider::lock()
→ Lock::block()`) — стандартный фреймворковый примитив «read-modify-write под одним
ключом». RAG:✅ (2026-07-17: форма API и её phpstan-корректность на level 6 проверены
прогоном + чтением vendor, см. Inputs/Code Guidance — НЕ по памяти). Лок-ключ — ОТДЕЛЬНЫЙ от
`$epochKey` (`$epochKey.':lock'`), чтобы не конфликтовать со значением эпохи. Таймаут
`block()` — короткий (секция критична, ожидаемая работа — три быстрых cache-вызова), но НЕ
ноль (0 = не ждать вовсе, что превратило бы конкурентные forgets в тихие потери
инвалидации). На таймаут — НЕ глотать `LockTimeoutException` молча (тихий проглот здесь
означает «грант не инвалидирован и никто не узнал»). Не менять публичную сигнатуру
`forgetForUser()`.
**Code Guidance:** обернуть ИМЕННО последовательность `add()`→`increment()`→`put()` в лок
через `getStore()`-форму, проходящую phpstan level 6 (прямой `$epochStore->lock(...)` НЕ
проходит: `lock()` не объявлен на `Repository`-контракте, `[method.notFound]`, находка A3 —
проверено прогоном). Точная форма (проверена прогоном `vendor/bin/phpstan analyse` level 6 —
0 ошибок):

```php
use Illuminate\Contracts\Cache\LockProvider;
// …
$epochStore = cache()->store($store);
$bump = function () use ($epochStore, $epochKey): void {
    $epochStore->add($epochKey, 1, Config::cacheTtl());
    $epoch = $epochStore->increment($epochKey);
    $epochStore->put($epochKey, $epoch, Config::cacheTtl());
};
$lockStore = $epochStore->getStore();
if ($lockStore instanceof LockProvider) {
    $lockStore->lock($epochKey.':lock', 5)->block(2, $bump);
} else {
    $bump();
}
```

5 сек TTL самого лока (на случай упавшего держателя), 2 сек ожидание захвата. `instanceof
LockProvider` — и phpstan-guard, и корректная деградация: кастомный драйвер без
`LockProvider` выполняет три вызова БЕЗ лока (гонка остаётся — но это ровно статус-кво до
этого фикса, без краха), стандартные сторы (ВКЛЮЧАЯ array) реализуют `LockProvider` и идут
через лок. Не оборачивать в лок весь метод `forgetForUser()` (in-process
`unset($this->requestCache…)` в локе не нуждается). ЗАПРЕЩЕНО «упростить» удалением
`add()`-seed шага (докблок строк 81-85 объясняет его роль — без него `increment()` на
отсутствующем ключе даёт неверную семантику первого форгета); лок решает ТОЛЬКО гонку
конкурентности, не заменяет seed-логику.

Тест на сериализацию: НЕ гонять параллельные PHP-процессы (нет portable механизма) — вместо
этого доказать, что лок ВЗЯТ вокруг read-modify-write. array-стор тестового окружения
РЕАЛИЗУЕТ `LockProvider` (см. Inputs, находка A4) — прежней ложной дилеммы «у array lock()
no-op → эскалировать» НЕТ, пиши тест прямо на нём. Детерминированный кейс: spy/декоратор над
`Store` (или над `Lock`), подменённый через сервис-контейнер, фиксирующий что (1) `lock()`
вызван с ключом `{epochKey}:lock` ПЕРЕД `increment()`; (2) `add()`/`increment()`/`put()`
выполнены ВНУТРИ колбэка `block()`, а не до/после. Реальную кросс-процессную сериализацию
array-лок не даёт (в памяти одного процесса) — и не требуется: тест доказывает НАЛИЧИЕ
лок-обёртки, а не физическую гонку (реальный Redis-тест на гонку — за scope, см. Pending
Work / handoff deferred). Escalation по «rule conflict» здесь БОЛЬШЕ НЕ предусмотрен: ложное
основание (array=no-op) снято A4.

**Implementation Rules:** `removeScopedRole()` меняет ТОЛЬКО null-ветку — из
`->when($panelId !== null, fn (Builder $query): Builder => $query->where('panel_id',
$panelId))` в форму с явным `default`-колбэком `when()` (Laravel `Conditionable`
поддерживает третий аргумент — default-колбэк на `false`-условие; НЕ городить отдельный
`if/else` вокруг всей цепочки — `when(..., ..., ...)` короче и остаётся одной цепочкой
query-builder'а). Explicit-`panelId`-ветка (`where('panel_id', $panelId)`) НЕ меняется —
она УЖЕ матчит только свою панель (не `whereNull OR panel_id=X` — это паттерн
`hasScopedRole()`, не `removeScopedRole()`; не путать два разных `when()` в файле).

`removeScopedRole(panelId=null)`). Оба метода зовут `$this->flushPermissions()` БЕЗ
аргумента (как и сейчас) — не сужать инвалидацию до конкретной панели, семантика

```php
    /**
     * Remove a scoped role for a specific entity.
     *
     *   $user->removeScopedRole('editor', $project);
     *   $user->removeScopedRole('editor', $project, panelId: 'admin');
     *
     * A null $panelId (the default) removes ONLY the any-panel row
     * (panel_id IS NULL) — symmetric with assignScopedRole(), where a null
     * $panelId also targets the any-panel row. Pass an explicit $panelId to
     * remove only the assignment scoped to that panel. To remove the role
     * across EVERY panel in one call, use removeScopedRoleEverywhere().
     *
     * @see removeScopedRoleEverywhere()
     */
    public function removeScopedRole(string|Role $role, Model $entity, ?string $panelId = null): static
    {
        $roleModel = $this->resolveRole($role);

        if ($roleModel === null) {
            return $this;
        }

        ModelHasScope::query()
            ->where('model_type', $this->getMorphClass())
            ->where('model_id', $this->getKey())
            ->where('scope_entity_type', $entity->getMorphClass())
            ->where('scope_entity_id', $entity->getKey())
            ->where('role_id', $roleModel->getKey())
            ->when(
                $panelId !== null,
                fn (Builder $query): Builder => $query->where('panel_id', $panelId),
                fn (Builder $query): Builder => $query->whereNull('panel_id'),
            )
            ->delete();

        $this->flushPermissions();

        return $this;
    }

    /**
     * Remove a scoped role for a specific entity across EVERY panel,
     * regardless of panel_id.
     *
     *   $user->removeScopedRoleEverywhere('editor', $project);
     *
     * This is the pre-D10 removeScopedRole(panelId: null) behavior, split
     * out into its own explicit method now that removeScopedRole(panelId:
     * null) targets only the any-panel row.
     */
    public function removeScopedRoleEverywhere(string|Role $role, Model $entity): static
    {
        $roleModel = $this->resolveRole($role);

        if ($roleModel === null) {
            return $this;
        }

        ModelHasScope::query()
            ->where('model_type', $this->getMorphClass())
            ->where('model_id', $this->getKey())
            ->where('scope_entity_type', $entity->getMorphClass())
            ->where('scope_entity_id', $entity->getKey())
            ->where('role_id', $roleModel->getKey())
            ->delete();

        $this->flushPermissions();

        return $this;
    }
```
