# D9 — Поправки P2 после P2.1: `PermissionKey::prefixed()` не создаётся, `replace()` применяется при сборке, выдержки решений досье

**Actor:** owner (сообщения 2026-10-02 «метода prefixed не будет, есть метод resourcePrefix» и «ты сначала должен пофиксить все хвосты») / Claude Opus 5.5 (frontier)
**Evidence:** D6 п.1 (перенос `PermissionKey::prefixed()` в P2.2), D8 п.5 (форма `prefixed(?string $prefix)`); RAG:— `05-php-api.md` §5 (строка `prefixed()`), `02-decisions.md` D84 («выбранная панель сама добавляет presentation prefix; default `resourcePrefix` — `id()`»), D06 («`replace()` — явная замена до заморозки»), `04-packages-and-layout.md` §5 (провайдеры из конфига регистрируются в `boot()` ядра); `findings/P2-execution.md` «Наблюдение для P2.6 и Review P2»; `plan-weight plan` на HEAD `0571df3`: `02-decisions.md` — 30 646 оценочных токенов при лимите 25 000 на чтение, P2.7 — 107 183 при пороге пункта 100 000.

## Solution

1. **`PermissionKey::prefixed()` не создаётся** — ни в форме досье (05 §5, без аргумента), ни в форме D8 п.5
   (`prefixed(?string $prefix)`). Префикс имён — свойство панели: его задаёт `PanelBuilder::resourcePrefix()`,
   отдаёт `Panel::prefix()`, а `PanelResolver` снимает при разборе имени (P2.2). Kernel имя с префиксом не строит.
   Если потребителю понадобится форма `admin.orders.view` для показа, её собирает пункт-владелец этого вывода из
   `Panel::prefix()` и `PermissionKey::local()`; публичного метода под это решение не вводит.
   Отменяются: строка D6 п.1 «`PermissionKey::prefixed()` → P2.2» и второй пункт D8 п.5. Остальное в D6 и D8 в силе.
   Плагинный `BasePlugin::prefixed(string): static` (06 §3, D47, D84 — отдельное пространство имён ключей плагина,
   P2.4/P2.6/P2.8) этим решением **не затрагивается**.
2. **`PanelRegistry::replace()` применяется при сборке.** До заморозки `replace(class)` запоминает замену; при
   сборке она подставляется на место зарегистрированного провайдера с тем же id (позиция панели сохраняется,
   последняя замена побеждает). Id без регистрации → `UnknownPanelException` при сборке — так же, как у
   `configure(id)`. Проверки «класс — `PanelProvider`», грамматика id и заморозка остаются немедленными.
   Реализует **P2.2** (`Panels\PanelRegistry` и контракт входят в его `Files`); правило P2.1 «неизвестный id →
   `UnknownPanelException`» сохраняется, меняется только момент.
3. **Выдержки решений досье.** `brief/P2-dossier-decisions.md` — дословные выдержки решений D05, D11, D36, D44, D45,
   D47, D50, D52, D56, D58, D72, D73, D78 из `02-decisions.md` с номерами строк источника; раздел `N` = решение
   `DNN`. `Required Reads` пунктов P2.2–P2.8 и P2.10 ссылаются на разделы выдержек (`§N`) вместо целого файла с
   уточнением прозой. Нормативен исходный файл досье. Спецификация закрытого P2.1 не меняется.

## Why

П.1 — решение владельца: у префикса один владелец (панель) и одно имя настройки (`resourcePrefix`); метод Kernel,
которому панель неизвестна, требовал либо аргумент (D8 п.5), либо знание панели в значении (05 §5). Решение принято
до старта P2.2, код P2.1 метода не содержит.

П.2 — хвост P2.1: `replace()` панели из `azguard.panels.providers` срабатывал только из `boot()` провайдера,
загруженного после ядра, и падал из `register()` модуля, потому что провайдеры конфига попадают в реестр в `boot()`
ядра. Перенос их регистрации в `register()` ядра сломал бы тесты потребителей на Testbench (конфиг теста задаётся
после `register()` провайдеров). Отложенная замена убирает зависимость от порядка загрузки, не меняя досье:
«явная замена до заморозки» остаётся верной.

П.3 — селектор раздела в `Required Reads` понимает только `§ <номер>` по заголовку; заголовки `### DNN` файла
решений им не выбираются, а уточнение прозой взвешивалось как весь файл. Ошибки read budget стали видны только
после перехода P2 в «In progress». Выдержки дают исполнителю ровно нужные решения и возвращают пункты в бюджет.

## Consequences

Спецификации P2.2 (Why, Scope Included, Files, Implementation Rules, Code Guidance, Deliverables), `Required Reads`
P2.3–P2.8 и P2.10, Phase Context/Contract/Scope `phases/P2/P2.md` изменены в сессии исполнения B2a после закрытия
P2.1; спецификация P2.1 и её terminal evidence не затронуты. Receipt батча B2a с прежним `spec_digest` недействителен:
остаток `P2.2 P2.3` допускается заново. Печать дизайна фазы (`finalize-design --phase P2`) отстаёт от этих правок до
следующего вызова `task:plan-design … P2`; исполнение она не блокирует (`Design Audit: not-required`).
`PermissionKey` и `tests/Unit/Kernel/Identity/PermissionKeyTest.php` выходят из `Files` P2.2. Документация P8.2 и
таблица 05 §5 описывают `PermissionKey` без `prefixed()`. В D8 «Consequences» фраза про смену сигнатуры `prefixed()`
теряет силу. Review P2 (P2.10) проверяет `replace()` по п.2.
