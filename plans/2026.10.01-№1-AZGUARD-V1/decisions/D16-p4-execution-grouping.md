# D16 — Группировка исполнения P4 и маршруты исполнителя/reviewer

**Actor:** Codex / design; модель и effort текущей сессии не аттестованы.
**Evidence:** RAG:— указание владельца от 2026-10-04 внести группировку в план для однозначного запуска;
исполнитель `gpt-6.1-sol`, reviewer `grok-4.7`. D15 §1, спецификации P4.2–P4.23, Required Reads,
текущий Task `task_contract.compile_batch_routing()`/`admit_batch()`, журнал закрытого P4.1.

## Solution

1. **Уточнение D15 §1 только для исполнения.** Разделение контрактов P4.16–P4.23, владельцы,
   приёмка и порядок D15 сохраняются. Вместо всеобщего `solo` разрешены рекомендованные батчи:

   | Batch | Порядок | Общий контекст |
   |---|---|---|
   | B4a | P4.2 → P4.3 | Каталог, роли, политики, 8 общих Required Reads |
   | B4e | P4.10 → P4.11 | Explain/Gate, ScenarioGenerator, паритет, 8 общих Required Reads |

   Routing каждого участника начинается с `recommended:`. Один пункт закрывается со всеми
   собственными Validation/Deliverables до начала следующего; общий GREEN на батч их не заменяет.
   Остальные Routing rows остаются `solo` с конкретным основанием отдельного допуска.

2. **Три последовательности переиспользования контекста.** P4.17 → P4.5 (9 общих Required Reads),
   P4.19 → P4.7 (8), P4.16 → P4.18 (8) рекомендуются для продолжения в той же root-сессии.
   Они не являются Routing-батчами: текущий compiler сортирует номера и требует сплошной числовой
   диапазон. Прежнее предложение пяти Routing-батчей с этими парами не проходит preflight.
   Каждый пункт этих последовательностей имеет свою строку запуска и отдельный `prepare`;
   потребитель начинается после GREEN производителя и своего успешного допуска.
   Продолжение в одном root допустимо только внутри явно авторизованного scope, например
   фазового `task:plan-run <PLAN-ID> P4`; отдельный запуск первого пункта не разрешает второй.
   При нехватке контекста штатный continuity reducer сохраняет checkpoint и выбирает переход.

3. **Маршруты.** Рекомендуемый исполнитель реализации — `gpt-6.1-sol/high`; semantic minima
   существующих Routing rows сохраняются. Reviewer — `grok/grok-4.7/high` в независимой read-only
   сессии. Выбор фиксируется в Phase Context, roadmap и handoff; `Routing.Review=none` сохраняется
   как исходный minimum, а переданный `--reviewer grok/grok-4.7 --review-effort high` требует
   автоматического независимого ревью каждого implementation item перед закрытием.
   Все execution-sheet строки задают базовые membership/route; reviewer selector добавляется
   к выбранной команде при запуске и передаётся в `prepare` каждого её implementation item.
   P4.13 и P4.14 остаются отдельными read-only review-пунктами: verdict составляет именно Grok,
   исполнитель не сертифицирует собственную реализацию и не запускает ревью reviewer-отчёта.

4. **Границы.** P4.13 — после P4.15, перед P4.8; P4.14 — после P4.23. Тяжёлые DB/boundary/cache/
   transaction/batch/predicate/visibility реализации и CRM/engine qualifications не объединяются.
   СУБД, Redis, replica, type coverage, arch/API и остальные проверки каждого пункта сохранены.
   P4.1 уже GREEN и не переисполняется. Эта правка авторизует планирование, а не выполнение P4.

## Why

Батчи экономят повторное чтение и подготовку без объединения item-контрактов. Для непоследовательных
номеров переиспользуется root-контекст, но не обходится существующий batch gate. В оставшейся P4
20 канонических execution-sheet строк вместо 22; при достаточном контексте три solo-последовательности
дают ещё три места для переиспользования одной сессии. Это счёт команд/границ, не измерение стоимости.
Количество owner-requested item reviews и обязательных проверок от группировки не уменьшается.

## Consequences

Обновлены plan Routing, P4 Phase Context/порядок, roadmap и handoff; D16 добавлен в Inputs всех
не начатых P4 item. Исторические спецификация, state, bundle и runtime evidence P4.1 сохраняются.
Decision/status views и доступные будущие bundles регенерируются owning Task writer; допуск B4a,
компиляция B4e и execution-sheet проверяются без implementation start. Неготовый будущий item
не заявляется runnable только потому, что его membership корректен.
