### P1.6 — Authority semantics, кодовые роли и структурные SPI областей

**Intent:** Зафиксировать до API freeze смысл двух authority modes как чистую функцию Kernel, кодовую роль `BaseRole` с атрибутами как единственный способ определить роль, и структурные SPI области назначения, tenant и субъекта, чтобы P2–P5 опирались на готовые контракты, а не изобретали их.
**Why:** RAG:— D53/D83 и 19 §2 (PolicyOnly: policy true → allow, null/false → deny, назначения не читаются и запрещены; RequiresGrant: qualifying grant AND policy ≠ false; superadmin — authority только в Grants; BeforeResult не authority); D19/D80 и 05 §6 (роль — PHP-класс, атрибут и метод равнозначны, БД хранит только назначения); D59/D60/D84 и 06 §7 (`AssignmentScopeDefinition` type/model/resolve, `QueryableAssignmentScopeDefinition` query/tenantOf, `ResolvedAssignmentScope`, scopes()/scopeRequired(), aliases вместо FQCN); 18 §5, §10 (`AssignmentScopePhase`); V89/V117/V119 (части P1); D6 (что перенесено в F2/P4/P5).
**Scope Included:** Методы `PermissionAuthority`: `readsAssignments(): bool`, `acceptsAssignments(): bool`, `superAdminIsAuthority(): bool`, `allows(?bool $policy, bool $qualifiedContribution): bool` — таблица 19 §2 без boundary (boundary всегда AND снаружи). `AzGuard\Roles\BaseRole` (abstract: `key`, `label`, `permissions` abstract, `formerKeys`, `grantable`, `superAdmin`, `scopes` = `[]`, `scopeRequired` = false, `level`), `AzGuard\Roles\Attributes\{Role,SuperAdmin,NotGrantable,FormerKeys}`, `AzGuard\Roles\GrantedAutomatically`, `AzGuard\Roles\SuperAdminRole` (`#[Role('superadmin', label: 'azguard::roles.superadmin')]`, `#[SuperAdmin]`, пустые права). `AzGuard\Contracts\Scopes\` (`@spi`): `AssignmentScopeDefinition`, `QueryableAssignmentScopeDefinition`, `ResolvedAssignmentScope` (final readonly), `ResourceScopeResolver`, `ProvidesAccessScope`, `TenantMembership`, `TenantResolver`, `AssignmentScopeResolver`, `AssignmentScopeMembership`, `ProvidesAssignmentScope`; `AzGuard\Contracts\Subjects\SubjectResolver` (`@spi`). `AzGuard\Scopes\AssignmentScopePhase` (`@api` тегом). Перегенерация манифеста.
**Scope Excluded:** всё, что D6 переносит: `AssignmentScopeRuntime`, `LookupContext`, `AssignmentScopeFilter`, `ConfigurableAssignmentScopeDefinition`, `BaseAssignmentScope`, directories и Option-значения (F2), `PluginContext` (P2.4), `ChangeContext` (P5.2), `GrantCondition` (P4.1), `GrantFilter/GrantPage/GrantRecord` (P5.3). Компиляция роли против панели (enum → ключ, проверка шаблонов, `scopeRequired` без scopes, дубликаты ключей — P2.5/P2.8); перевод `label()` проверяется только в Laravel-контейнере теста. Атрибуты прав `RequiresGrant`/`PolicyOnly` и выбор mode у enum (P2.8/P2.5). Пайплайн, использующий `allows()` (P4.1).

**Implementation Rules:** `allows`: `Policy` → `$policy === true` (аргумент `$qualifiedContribution` игнорируется — PolicyOnly не собирает grants); `Grants` → `$qualifiedContribution && $policy !== false` (отсутствие политики передаётся как null = pass). `readsAssignments`/`acceptsAssignments`/`superAdminIsAuthority`: Policy → false, Grants → true. `BaseRole`: значения атрибутов читаются рефлексией один раз на класс (статический кэш по FQCN, без Laravel cache); метод равнозначен атрибуту и может быть переопределён; `key()` — `#[Role(key)]` либо override, отсутствие или нарушение грамматики роли → `InvalidRoleKeyException`; `formerKeys()` проверяются той же грамматикой и не содержат текущий ключ; `label()` — `__($label)` из атрибута, иначе ключ; `scopes()` — `list<AssignmentScopeDefinition|class-string<AssignmentScopeDefinition>>`, `[]` = только tenant-wide; `scopeRequired()` по умолчанию false. Роль не имеет `roleModel`/`field`/`fields`/`make`/`options` (D80/D81). Хранимая идентичность области — alias `type()` по грамматике type alias кодека, не FQCN. `ResolvedAssignmentScope(ref, tenant, ?Model record)` — `final readonly`, без логики сверки (сверку ref/tenant делает core в P4.6). SPI-интерфейсы повторяют сигнатуры 06 §7 дословно (`TenantResolver::resolve(Request)`, `SubjectResolver::resolve(mixed): SubjectRef`, `model(SubjectRef): ?Model`, ...), каждый с docblock `@spi` и одной строкой назначения без кодов задач. `AssignmentScopePhase` — string-backed `access|assignment|revocation|inspection`. Переводы — `loadTranslationsFrom(__DIR__.'/../resources/lang', 'azguard')`. После изменений — `composer api:manifest` и проверка, что diff манифеста содержит только новые классы P1.6.
**Code Guidance:** V119 (часть P1) — Pest dataset по таблице 19 §2: mode × policy {true, null, false} × qualified {true, false} → ожидание (12 строк) плюс флаги `readsAssignments`/`acceptsAssignments`/`superAdminIsAuthority`. V117 (часть P1) — роль определяется только PHP-классом: тест фикстур `SellerRole`/`AnalystRole`/`RootRole` (атрибуты и override метода дают одинаковый результат; роль без ключа → исключение). V89 (часть P1) — две роли ссылаются на один фикстурный `ProjectScope implements QueryableAssignmentScopeDefinition` (экземпляр и class-string), alias `crm.project` одинаков, FQCN нигде не нужен для идентичности; фикстура `query()` может вернуть Builder на `Illuminate\Database\Eloquent\Model`-заглушке без БД.
