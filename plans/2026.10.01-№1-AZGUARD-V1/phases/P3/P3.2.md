### P3.2 — Миграции с префиксом хранилища на PG/MySQL/MariaDB/SQLite

**Intent:** Построить схему хранилища 08 §2 одним построителем для всех СУБД — назначения, opt-in динамические права, состояние панели и хранилища — с точным побайтовым сравнением идентификаторов, полным ключом выдачи, CHECK пар NULL и таблицей состояния схемы; загрузить миграцию общего хранилища из ядра и генерировать миграцию своего хранилища в проект.
**Why:** RAG:— 08 §2 (таблицы, колонки, UNIQUE, INDEX, CHECK, `ID(n)`, HK, бюджет ≈1039 байт, запрет префиксных индексов, версии-кандидаты), §6 («нет roles/role permissions/context config таблиц»); D08, D13, D35 (ядро грузит миграции общего хранилища; `azguard:storage:migration {name}` пишет миграцию хоста; параметры схемы — в таблице состояния); 07 §1 п.2; 13 «Уточнения пятого прохода» (tenant/context columns, grant identities, origin — в P3.2); V105, V113 (часть: нет FK на PHP-класс роли); D12 п.2, п.4, п.6, п.7.
**Scope Included:** `Storage\Schema\StorageSchema` (`@api`): `create(string $storage)`, `drop(string $storage)` — таблицы `{p}permissions`, `{p}role_grants`, `{p}permission_grants`, `{p}panel_state` (из P3.1), `{p}storage_state` строго по 08 §2, явные имена индексов/ограничений, CHECK пар (PG/MySQL/MariaDB — constraint; SQLite — триггеры), запись строки `storage_state`. `HostKeyColumns` — колонки HK (`string` ASCII 64, `bigint`, `uuid`, `ulid`) и `ID(n)` с collation по D12 п.6. Сверка `storage_state` при первом `mutate`/`state` хранилища — `StorageMismatchException` (`storage_mismatch`, родитель `StorageException`). Миграция ядра `packages/core/database/migrations/` для хранилища `default` и тег публикации `azguard-migrations`. Команда `azguard:storage:migration {name}` и stub. Сервис `mariadb` (10.11) в `docker-compose.yml`, соединение `mariadb` в `TestCase`, script `test:mariadb`. DDL-снимки на 4 СУБД.
**Scope Excluded:** Модели и свои колонки хоста (P3.3: тест своей колонки добавляет её миграцией в фикстуре). Запись выдач и проверка I4–I7 (P5.2). Doctor-сверка `storage_state` с конфигом (P6.4). Минимальные версии СУБД и CI-матрица (P8.4). Публикация остальных ресурсов (P6.3).

**Implementation Rules:** Колонки и ограничения — дословно 08 §2; порядок колонок unique не меняет смысл, но фиксируется снимком. `ID(n)` — `string(n)` + `charset('ascii')->collation('ascii_bin')` на MySQL/MariaDB, `collation('C')` на PG; HK `string` — тот же `ID(64)`; `bigint` — `bigInteger`; `uuid` — `uuid` (PG native); `ulid` — `char(26)` ASCII binary. Время — `dateTime` (D12 п.6). `meta` — `json` nullable. Без FK на внешние таблицы и на классы ролей. Без префиксных индексов. Имена индексов/ограничений/триггеров — `{prefix}{pm|rg|pg|ps|ss}_<смысл>`, ≤ 63 байт; тест проверяет длину для префикса максимальной длины. CHECK: `(tenant_key = 'global') = (tenant_type IS NULL AND tenant_id IS NULL)` и `tenant_type IS NULL = tenant_id IS NULL` (то же для context) — формулировка, эквивалентная 08 «обе NULL ⇔ key = 'global'»; на SQLite — триггеры `BEFORE INSERT`/`BEFORE UPDATE OF …` с `RAISE(ABORT, 'azguard: …')`. `storage_state`: одна строка `id = 1`, `schema` — JSON по D12 п.6 с упорядоченными ключами; `Storage` сверяет её один раз на объект при первом `mutate`/`state` (отсутствие строки/таблицы или расхождение `prefix`/`host_keys`/`storage_id`/`identity_codec`/`version` — `StorageMismatchException` с ожидаемым и найденным). Миграция ядра — анонимный класс: `up()` → `StorageSchema::create('default')`, `down()` → `drop('default')`; грузится `loadMigrationsFrom` и публикуется тегом `azguard-migrations`. Генератор: `name` — настроенное хранилище, не `default` (его создаёт ядро) — иначе ошибка команды с объяснением; файл `database/migrations/<Y_m_d_His>_create_azguard_<name>_storage.php` из stub; существующий файл `*_create_azguard_<name>_storage.php` не перезаписывается. Stub после подстановки `default` побайтно равен миграции ядра — тест; комментарий в stub показывает, где дописывать свои колонки (`Schema::connection(...)->table(...)` после `create`). `StorageSchema` — `@api`, одна строка назначения в docblock; `HostKeyColumns` остаётся внутренним.
**Code Guidance:** `StorageSchemaTest` (SQLite): после `create` таблицы с префиксом ровно пять (`permissions`, `role_grants`, `permission_grants`, `panel_state`, `storage_state`), таблиц `roles`/`role_permissions`/`role_contexts` нет (V105); две строки, отличающиеся только `origin`, допустимы, полный дубликат — нарушение unique; `tenant_key = 'global'` с `tenant_type` — отказ CHECK, `tenant_key = 'org:1'` без `tenant_type` — отказ; `Editor` и `editor`, `a` и `a ` — разные строки unique. `StorageStateTest`: смена `host_keys` в конфиге после миграции → `StorageMismatchException` при первом `mutate`; без миграции — то же. `TwoStoragesTest`: хранилища `azg_` и `adm_` в одной базе мигрируются, пишутся и удаляются независимо; повтор той же пары под другим именем — `invalid_configuration.storage`. Engines (`StorageDdlTest`): снимок `Schema::getColumns/getIndexes` + CHECK/триггеры + collation по каждой таблице, нормализованный JSON против `tests/Fixtures/Storage/ddl/<engine>.json` (перезапись снимка — `AZGUARD_UPDATE_SNAPSHOTS=1`, в коммите только сверка); HK `uuid` и `bigint` дают свои снимки по одной таблице; unique `permission_grants` на MySQL/MariaDB создаётся с HK `string` (бюджет); отчёт пишет `innodb_page_size`, collation, версию СУБД. `StorageConstraintsTest` повторяет инварианты `StorageSchemaTest` на сервере.
