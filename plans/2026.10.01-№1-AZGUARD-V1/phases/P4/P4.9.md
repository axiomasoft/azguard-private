### P4.9 — decideMany

**Intent:** Дать пакетную проверку, равную поэлементной: `Authorizer::decideMany()` группирует запросы по `(storageId, panel, subject, tenant)` и режиму, читает DB-назначения всех пачек группы (contexts пачками по 100) между одним `T_before`/`T_after`, использует один `now` на пакет, вызывает политики/restrictions/условия на каждый запрос и возвращает решения в исходном порядке с картой состояний по панелям; панель каждого запроса выбирает `PanelResolver`.
**Why:** RAG:— 09 §9 (пакетная оценка), §16 (mixed batches partition по panel/mode/store, ключи карты состояний), §1 (один resolver для `decideMany`); D27, D44, D64 досье; 20 F24; V64 (строка `decideMany`), V99 (пачки), V120 (mixed batch); R58 (бюджет, часть), R68; D8 п.7, D14 п.2, п.3 плана.
**Scope Included:** Внутренний `Authorization\BatchEvaluation` и `Authorizer::decideMany(list<AccessRequest> $requests, ?ActorRef $actor = null): DecisionSet`; `Authorizer::resolve(Model|SubjectRef $subject, UnitEnum|string $permission, ?string $panel = null): array{Panel, PermissionKey}` через `PanelResolver` (общий для `decideMany` и Gate P4.11); проверка в `decide()`: панель аргумента равна панели `PermissionKey` запроса, иначе `ConflictingPanelException`; разбиение: PolicyOnly-запросы не втягивают DB-чтения, Grants-запросы группы с fenced источником — один fence на все пачки по 100 контекстов (`grants($subject, $chunk, …)`), повтор перечитывает все пачки; `DecisionSet::states()` — карта `IdentityCodec::compose(['code', panel, buildId])` → `CodeStateToken` и `IdentityCodec::compose(['storage', storageId, panel])` → `StateToken`; кэш P4.8 используется по группам; бюджет D44 `2 state reads + ≤2c grants queries` на группу; CRM-кейс R68.
**Scope Excluded:** Публичный `decideMany` трейта/`SubjectAccess` (P5.1) и фасада (P6.1); `BatchRestriction` (необязательная оптимизация досье, не вводится); видимость (P4.12).

**Implementation Rules:** State keys — existing IdentityCodec::compose, не склейка code:/storage:.  Batch prepare загружает raw subject/actor и structural context/owner snapshots set-based по unique group/refs, не запросом на каждый Client. Queryable definitions используют fresh query with whereKey IN chunks + tenantOf; generic external resolve — один на unique ref, а не на resource. Common/native role eligibility применяются grouped batch query или allowsMany для конкретного runtime witness; решения/условия/policy/before всё равно выполняются по каждому запросу, raw host snapshot не итог Allow.  Для каждого запроса `decideMany(...)[i]` равно `decide(...)` на тех же authority inputs и том же `now` (паритет — главное свойство). `now` фиксируется один раз на вызов. Политики, restrictions, условия, before/after вызываются на каждый запрос, включая два запроса к одной модели с разными ресурсами; memo по `(permission, model id)` запрещён. Группа — `(storageId, panel, subject, tenant)` для Grants-запросов с fenced источником; PolicyOnly и code/relation-only запросы не создают DB-зависимостей. Пачка контекстов — до 100; все пачки группы читаются между одним `T_before` и одним `T_after`; несовпадение — повтор всех пачек (до 3), затем `ConsistencyError` у всех запросов группы. Ошибка Grants-ветки одного права не скрывается соседним успешным правом и не влияет на независимые группы. Порядок результатов — исходный. Решения разных панелей не делят токен.
**Code Guidance:** Паритет — генератор P4.16: 200 случайных пакетов, сравнение с поэлементным `decide` при замороженном времени. Budget — 250 контекстов одного субъекта одной панели: `2` чтения `panel_state` и `≤ 2 × 3` запросов выдач (`DB::listen`), политика вызвана 250 раз. Mixed batch (R68) — PolicyOnly + Grants + relation-only, две панели, один `now`: в карте состояний compose([code,panel,buildId]) для PolicyOnly/relation и compose([storage,storageId,panel]) только для DB-панели; подключение хранилища, бросающее на любой запрос, не ломает PolicyOnly-часть. `BatchFenceRaceTest` (`->group('engines')`) — barrier между пачками 1 и 2, параллельный revoke: целый набор или `ConsistencyError`. V64 — `resolve()` для enum одной панели, полного имени, явной панели, конфликта сигналов — то же, что `PanelResolver` (P2.2). V45 минимум 1000 resource entities с полными ids/совпадением scalar/no SQL на каждый Client; пример250contexts не заменяет эту приёмку.
