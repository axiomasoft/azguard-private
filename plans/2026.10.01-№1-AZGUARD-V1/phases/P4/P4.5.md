### P4.5 — RelationSource и видимость через связи

**Intent:** Дать панели встроенный источник ролей из связей моделей хоста без таблиц AzGuard: `RelationSource::make(model, via, role, scope)` превращает членство субъекта в сущности (pivot-роль, статичная роль или замыкание) в scoped `RoleContribution` известной PHP-роли, а для видимости отдаёт выбор сущностей через ту же связь (`FiltersQueries`).
**Why:** RAG:— 05 §4.1 (`RelationSource::make(string $model, string $via, string|Closure $role, ?Closure $scope = null)`), 06 §1.1 (capabilities), §1.2 (роли, на которые ссылаются выдачи, существуют), §2.1 (связи сущностей), 09 §2 (role contributions разворачиваются ядром), §8 (relation source — Request по умолчанию, Stable требует revision), 19 §3, 20 F06; D52, D62 досье; V69, V90; R14, R42; D14 плана п.3.
**Scope Included:** `@api` `Sources\Relation\RelationSource implements ProvidesRoleGrants, FiltersQueries, DescribesSchema` с `make(string $model, string $via, string|Closure $role, ?Closure $scope = null)`, внутренний `Sources\Relation\RelationBinding` (нормализованная конфигурация); `$model` — класс Eloquent-модели или `AssignmentScopeDefinition` (тогда модель и `type` берутся из определения); `role` — имя роли (`'owner'`), путь атрибута pivot (`'pivot.role'`) или `Closure($pivot|$related): ?string`; `id()` — `relation:<type>`; `roleGrants()` — сущности, связанные с моделью субъекта через `$via`, в запрошенных scopes, → `RoleContribution::of(role, AccessScope::in(tenant, AssignmentScopeRef(type, key)), source: id, origin: 'relation')`; `volatility()` — `Request`; `contextsCovering()` — `AssignmentScopeSelection::in([...])` по той же связи для роли, покрывающей право; проверки сборки: статичная роль существует в каталоге панели, `$via` — отношение модели (`BelongsToMany`/`HasMany`/`BelongsTo`/`HasOne`/`MorphToMany`), повтор `id()` — ошибка P2.5.
**Scope Excluded:** Tenant-резолвинг сущности через `TenantPolicy`/`ModelAssignmentScopeDefinition` и фильтры областей (P4.6 — здесь tenant берётся из определения `tenantOf()` или `TenantRef::global()` для модели); исполнение выбора в SQL видимости (P4.12); doctor `panels.relations` (P6.4); revision-контракт Stable (P4.8 — здесь только Request).

**Implementation Rules:** Только публичные контракты. Значение pivot/замыкания, которому нет роли в каталоге, прав не даёт и пишется в трассу (`unknown relation role`), не ошибка; исключение отношения/замыкания — исключение источника → `Deny(SourceError)`. Источник не создаёт определений ролей и не пишет данных. Чтение — один запрос на источник за проверку: связанные сущности субъекта, ограниченные scopes запроса (ключи контекстов из scope; для global context — все связанные сущности выбранного tenant). Identity сущности — `AssignmentScopeRef` с `type` определения (или morph alias модели) и каноничным ключом `IdentityCodec`; `$scope`-замыкание дополнительно сужает запрос и не может его расширить (применяется к fresh Builder в группе `where`). Роль из связи разворачивается ядром по компилированной роли (P4.1), источник не знает прав роли. Один экземпляр на панель; модель субъекта — из `EvaluationContext::subjectModel()`.
**Code Guidance:** V69 — участник `project.members` с pivot `role = editor` получает права роли `editor` в `project:7` и не получает в `project:8`; `contextsCovering` для `projects.edit` возвращает `in([project:7])`. Статичная `role: 'owner'` для `Store::owner` — владелец получает роль `owner`; несуществующая статичная роль — `DefinitionException` при сборке; pivot-значение `ghost` — ноль прав, трасса. Замыкание `fn ($pivot) => $pivot->is_lead ? 'lead' : 'member'`. V90 (часть) — relation pivot role разворачивается через ядро: права роли меняются в коде роли без изменения источника. R42 (часть, без revoke): relation membership и ручная выдача P4.4 на одно право — оба вклада видны в трассе.
