# P4: аудит выполненной авторизации, кэша, источников и exact visibility

Дата: 2026-10-08. Область: P4 без Storage и Folder/SourceManager, которые проверяются соседними исполнителями. Правки не закоммичены. Все три приведённые находки подтверждены локальными RED-воспроизведениями и исправлены; исторический GREEN плана не использован как доказательство отсутствия дефектов.

## Исправленные находки

### P4-A1 — Major — пакетная проверка обходила структурный resolver области

Владелец: P4.9, связанный контракт P4.6/P4.19. Файл: `packages/core/src/Authorization/BatchInputs.php`, `loadScopes()`, строки 118–139.

`QueryableAssignmentScopeDefinition` предоставляет также `resolve()`. Реализация `BaseAssignmentScope::resolve()` публична и допускает override. Scalar-проверка вызывает resolver и отказывает при `null`/исключении. Batch-проверка любого queryable descriptor вместо этого читала `query()` и конструировала `ResolvedAssignmentScope` напрямую через `tenantOf()`. Это теряло специфичную для приложения проверку структурного существования/доступности владельца.

Воспроизведение: в projects существует id=1, есть tenant-wide grant, custom resolver возвращает `null` либо бросает исключение. `decide()` возвращает соответственно `AssignmentScopeNotAccepted` / `AssignmentScopeFilterError`, `decideMany()` до исправления возвращал `Granted` в обоих случаях. Оба RED наблюдались в новом `tests/Feature/Authorization/Batch/DecideManyScopeResolverTest.php`.

Исправление: grouped read оставлен только для унаследованной реализации `BaseAssignmentScope::resolve()`. Собственный resolver вызывается один раз на уникальную область, его отказ/ошибка попадают в прежний scalar pipeline. Публичный SPI не расширен. Подтверждено сохранение batch query budget существующим `DecideManyBudgetTest`.

### P4-A2 — Major — native OR/UNION внутри EXISTS обходил корреляцию и запрет

Владелец: P4.22, интеграция P4.12/P4.23. Файлы: `packages/core/src/Authorization/Query/PredicateCompiler.php`, `constrain()` и `assertCorrelatedQueries()`; `packages/core/src/Authorization/Visibility.php`, окончание `build()`.

Корневой host query уже проверялся на OR/UNION, но ограничения native relation и deferred scopes Laravel присоединяет при `whereHas()` позднее. Итоговый подзапрос не проверялся. Связь с `whereRaw('active = ? or active = ?', [true, false])` давала SQL, где последняя OR-ветка обходила ключ корреляции и вложенный `deny()`.

Два наблюдённых RED:

- `AccessPredicate::exists('rawProject', AccessPredicate::deny())`: ожидалось `[]`, фактически `[1,2,3,4,5]`, включая ресурс без проекта.
- Та же форма в resource→context `belongsTo`, единственная выдача project=1: ожидался клиент 101, `visibleTo()` возвращал `[101,102,103,104]`.

Исправление: проверяется конечное дерево correlated EXISTS после применения native constraints/scopes; непрогруппированные OR/raw/expression и UNION отвергаются до присоединения результата к caller builder. Повторная проверка собранного visibility query покрывает resource→context mapping, добавленный после компиляции AST. Нативные raw-предикаты внутри явной группы продолжают работать. Исходные SQL/bindings caller query при отказе не изменяются.

Регрессии в `PredicateCompilerTest.php`: raw OR, обычный OR, deferred global scope с raw OR, deferred UNION, nested relation, положительный grouped raw и `deny()`. Интеграционная регрессия в `VisibleToTest.php` проверяет опасную связь контекста и атомарность отказа. Это fail-closed ограничение намеренно требует группировать нестандартные native relation predicates; произвольный raw SQL не анализируется эвристическим парсером.

### P4-A3 — Major — fallback visibility обходил custom resolver области

Владелец: P4.12/P4.23, структурная семантика P4.6/P4.19. Файл: `packages/core/src/Authorization/Query/VisibilityScope.php`, `owner()`, строки 192–211.

Для queryable descriptor без exact owner adapter ограниченный fallback перечислял records и проверял только `tenantOf()`. Custom `resolve()` не вызывался. Scalar отказывал ресурсам отвергнутого context, а list/count включали их.

Воспроизведение `ScopeResolverTest.php`: resolver отвергает project=1, scalar результат `[102,103,104]`, visibility до правки `[101,102,103,104]`. Во втором RED resolver бросает исключение, но visibility раньше возвращала запрос вместо `VisibilityNotSupportedException`.

Исправление: fallback вызывает custom resolver и проверяет ref, tenant, необязательные record model/key, исключая отвергнутые области; исключение переводится внешней границей в `VisibilityNotSupportedException`. Путь стандартного inherited resolver сохраняет загрузку через `tenantOf()` без дополнительных resolve-запросов. Существующий бюджет 1000 областей сохранён. Явный `FiltersAccessQueries` остаётся контрактом точной эквивалентности адаптера; произвольная ложная реализация такого адаптера не может быть доказана ядром.

Новых подтверждённых дефектов кэша/DatabaseSource/RelationSource в этой области не найдено. Это результат прочитанных путей и коротких checks, не доказательство отсутствия всех возможных гонок.
