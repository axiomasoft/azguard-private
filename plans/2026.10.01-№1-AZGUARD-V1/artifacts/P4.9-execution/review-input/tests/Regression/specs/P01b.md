# P01b — Суперадмин-признак симметричен для code- и DB-ролей

**Probe:** P01b
**Finding:** N01
**Owning item:** PLAN2.P4.7
**Scenarios:** V15
**Defect in 0.3:** Тот же `*`, записанный в права DB-роли, оставался в своей панели, а у class-роли пересекал панели: два источника вели себя по-разному. Тест: `audits/2026-09-29-audit/opus/evidence/probes/OpusAuditProbesTest.php`, `it('P01b: the same * stored on a DB role stays on its own panel (asymmetry)')`.
**Required behavior:** Голый `*` нельзя записать ни в DB-роль, ни в прямое право; суперадмин возникает только через роль с признаком, одинаково для любого источника и только в своей панели.
**Status:** covered: tests/Regression/P01bTest.php::P01b rejects bare wildcard contributions rather than manufacturing superadmin

## Сценарий на целевом API

```php
expect(fn () => $user->guard('test')->grantPermission('*'))
    ->toThrow(InvalidPermissionKeyException::class);

// суперадмин-роль из кода и роль, выданная через DatabaseSource, дают одинаковый результат
foreach (['code-super', 'db-super'] as $role) {
    $user->guard('test')->grantRole($role);
    expect($user->guard('test')->isSuperAdmin())->toBeTrue()
        ->and($user->hasPermission(AdminUserPermission::Delete, guard: 'admin'))->toBeFalse();
    $user->guard('test')->revokeRole($role);
}
```

## Покрытие текущего слоя

Грамматика отклоняет `*` и `**`; повреждённый contribution custom source даёт `SourceError`, даже рядом с корректной code superadmin ролью. DB-строки с теми же wildcard, записанные через `Storage::mutate`, тоже дают `SourceError`. Одинаковый compiled superadmin-признак проверяется для custom source и DatabaseSource. Публичный subject mutation API относится к P5.2.
