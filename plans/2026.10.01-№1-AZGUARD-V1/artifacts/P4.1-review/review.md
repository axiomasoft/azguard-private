Один Major в привязке reserved-входов `RuntimeInvoker`: при одном PHP-классе user и resource движок может отдать политике дважды один и тот же экземпляр. Обхода «выдача без grant», чтения назначений в PolicyOnly и подмены NotGrantable строкой source нет. Blocker нет.

Проверка read-only по телам исходников. Команды не запускались. Приведённые exit code 0 этому Major не противоречат: существующий тест покрывает только имена, которые не совпадают с `user` и `resource`.

## Находки

### 1. Major — один и тот же экземпляр попадает в оба аргумента политики

- Файл: `packages/core/src/Policies/RuntimeInvoker.php:30-38` и `:79`
- Владелец: P4.1
- Уверенность: высокая

Слот выбирается по имени параметра, и это совпадение не смотрит в `$used`. Позиция 0 и 1 затем снова назначают `user` и `resource`, тоже не смотря в `$used`. Метка «уже использован» пишется только после присваивания, на ветке policy она ни на что не влияет.

Триггер. Два разных `User`, входы `user` = субъект id 1 и `resource` = ресурс id 2.

```php
fn (User $agent, User $user): array => [$agent->getKey(), $user->getKey()]
```

Имя `$user` забирает субъект. Позиция 0 тоже забирает субъект. Оба аргумента — id 1, ресурс id 2 отброшен.

```php
fn (User $resource, User $other): array => [$resource->getKey(), $other->getKey()]
```

Имя `$resource` забирает ресурс. Позиция 1 снова забирает ресурс. Оба аргумента — id 2, субъект отброшен.

Дальше `Container::call` передаёт аргументы по имени параметра и коллизию не исправляет.

Следствие. PolicyOnly и veto в RequiresGrant решают по двум ссылкам на одну модель. Проверка вида `$agent->is($user)` или «владелец и цель — один человек» истинна для любого второго экземпляра. Это прямой Allow там, где личности различны.

Контракт. D15 §2: reserved-слоты привязываются по документированным именам и по позиции user/resource; при одном PHP-классе экземпляры различаются позицией, а не глобальным FQCN. Code guidance P4.1: user и resource одного класса с разными id и с произвольными именами. Инвариант «не подменять reserved-модель» здесь нарушен не контейнером, а повторным выбором того же слота.

Покрытый тест `fn (User $who, User $target)` зелёный, потому что ни одно имя не равно `user` или `resource`. Подписи `fn (User $user, User $model)` тоже проходят: имя и позиция не спорят. Ломается смесь одного документированного имени и одного произвольного.

### 2. Minor — повтор `key()` restriction не всегда `DefinitionException`

- Файл: `packages/core/src/Authorization/Pipeline/AccessPipeline.php:38-44`, проверка ключей в `packages/core/src/Authorization/Pipeline/Stages/RestrictionStage.php:33-37`
- Владелец: P4.1
- Уверенность: высокая

`RestrictionStage::resolve()` вызывается только если кандидат уже Allow. Два restriction с одним `key()` при `NotGranted`, отказе before или границе none/none дают обычный Deny и не бросают. Тот же список при квалифицированной выдаче бросает `DefinitionException` с текстом `duplicate restriction key`.

Контракт P4.1 относит повтор ключа к ошибкам конфигурации direct API, рядом с `UnknownPermissionException` и `SubjectNotAcceptedException`, а не к отказу шага. На запрещающих входах ошибка описания панели скрыта. Allow из-за этого не появляется.

## Что проверено и держится

- Стадии идут Prepare, Boundary, Before, Authority, Restrictions, After. Отказ границы не вызывает before и источники. After видит уже посчитанный отказ, включая сбой загрузки субъекта, и своё исключение решение не меняет.
- PolicyOnly не вызывает `ProvidesGrants` / `ProvidesRoleGrants`. Состояние — `CodeStateToken`. `true` и allow-`Response` дают Allow(Policy); `false`, `null` и deny-`Response` дают Deny(Policy).
- RequiresGrant без квалифицированного вклада — Deny(NotGranted), политика при этом не вызывается. Это совпадает с тестом `RuntimePolicy::$calls === 0` и с порядком в правилах P4.1. Ложный Allow одной политикой без выдачи нет.
- Вклады одного grant соединены AND, вклады между собой — OR. Условие чужой строки не добирает поля соседней. `expiresAt <= now` уже истекло. Чужой `beta:root` до lookup по локальному ключу — SourceError. Бывший и неизвестный ключ роли дают ноль прав. `StoresGrants` и `NotGrantable` смотрят тип адаптера, не строку `contribution.source`.
- Суперадмин квалифицирует любое Grants-право, не заменяет veto политики и не действует в PolicyOnly. Witness `qualifiedSuperAdmin` не выводится из reason. Обычная выдача exemption не снимает. Restrictions проверяют и Policy, и SuperAdmin; `exemptsSuperAdmin()` сам по себе Policy не пропускает.
- Ошибка любого источника, в том числе ленивого итератора после уже прочитанного Allow, — Deny(SourceError). Неверный тип вклада, чужая панель паттерна и scope вне запрошенного — тоже SourceError, вклад не отбрасывается молча.
- Неизвестное статичное право и непринятый субъект выходят исключением. Morph alias сверяется с `Panel::subjectModels()` через `getMorphClass()`; отсутствие строки — `null`, не новая модель.
- `now` один `DateTimeImmutable` UTC на проверку; `forContribution()` и `withAuthority()` его не подменяют. Кадр копируется на вклад. `matchingGrants()` — только прямые покрывающие `Grant`, для PolicyOnly пусто.
- Повтор того же кадра из политики снаружи даёт Deny(PolicyError), в логе класс `RecursionDetectedException`, стек снимается. Другое право из политики разрешено. Явный и опущенный global scope — один кадр.
- Списки before/after/restrictions/grantConditions проверяются на компиляции с origin. Class-string restriction режется контейнером на операцию, не на сборке.
- Arch: источники не импортируют `AzGuard\Authorization`; `AuthorityStage` не вызывает `transaction()`.

Отдельно не требуют как дефект P4.1: полная граница tenant/context и фильтры областей (P4.6, P4.19), class-string аргумент и denial details `Response` (P4.3), кэш и `StateToken` (P4.8), `decideMany`, explain, Gate, видимость, генеративная матрица V15 (P4.16).
